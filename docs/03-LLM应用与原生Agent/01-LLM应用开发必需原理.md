# LLM 应用开发必需原理

> 预计 6 小时｜目标：掌握会影响 Agent 设计的原理，不陷入模型训练数学细节。

## 1. 生成并不是查答案

模型按上下文预测下一个 Token。它能生成流畅文本，但默认不知道你的实时业务数据，也不保证事实、格式或指令执行正确。Agent 工程的职责是用上下文、工具、状态机、验证和评测约束这种不确定性。

需要掌握：

- Token 与上下文窗口：历史、系统指令、工具定义、检索片段、工具结果共同占用窗口。
- temperature：影响采样随机性，不是“事实准确度旋钮”；生产任务还要靠证据与验证。
- system/user/tool 消息：信任等级不同，工具返回和文档内容都是不可信数据。
- 推理模型：可能更擅长复杂规划，但延迟与成本更高，仍需要停止条件和权限边界。

## 2. 幻觉的工程分类

1. 知识缺失：用 RAG 或实时 Tool。
2. 上下文冲突：明确指令优先级，减少噪声。
3. 引用不忠实：回答句子绑定证据 ID，做忠实度评测。
4. 工具臆造：工具名、参数、结果都做结构校验。
5. 业务规则遗漏：关键规则落在确定性代码/工作流，不只写 Prompt。

## 3. 模型选型方法

先建 20～50 条代表性样本，测任务成功率、结构正确率、P95 延迟、单任务成本、安全违规率，再选模型。日常开发用低价模型，复杂规划按条件升级；不要用榜单代替自有评测。

## 4. 项目任务

用相同 20 个设备维护问题对比千问与 DeepSeek，记录成功、拒答、引用、延迟、Token、费用。形成一页选型 ADR。

## 5. 练习与答案

### 练习 1：把 temperature 设为 0 是否绝对可复现？

**答案：**不能保证。服务端实现、模型版本、并发和底层数值都可能变化；关键逻辑必须靠测试、Schema 与工作流保证。

### 练习 2：模型上下文很长，是否应放入全部维修手册？

**答案：**不应。长上下文增加成本和噪声，相关信息可能被淹没；应检索、过滤、去重并保留引用。
