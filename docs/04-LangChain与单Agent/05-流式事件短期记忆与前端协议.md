## 1. 本章从哪里开始

第 4 章结束时，`create_agent` 已经能跑通动态工具循环，Middleware 也把身份、工具白名单、费用观测这些横切策略挂到了调用链上。但还有一个从第 2 阶段第 4 章就埋下的问题没被正面回答：**Agent 的内部运行是异步、多步、带中间状态的，前端怎么在不泄密、不乱序的前提下把它"直播"出来？**

| 对象 | 所在位置 | 作用 |
| --- | --- | --- |
| SSE 核心事件契约 | 第 2 阶段第 4 章 `api/` | `run.started`/`message.delta`/`tool.*` 等四个核心事件 |
| `create_agent` + Middleware | 第 3/4 章 `agent/` | 产生 LangChain 内部流（`updates`/`messages`/`custom`） |
| `AgentContext` | 第 3 章 `schemas`/`agent` | 运行时身份（`user_id/tenant_id/scopes/request_id`） |

LangChain 内部流和我们要给前端的流是**两套协议**：前者是框架实现细节（节点名、Checkpoint State、完整 Tool 参数），后者必须是一个**稳定、安全、可去重**的公开契约。本章用 `stream_adapter.py` 一个文件把两者隔开，并补上"短期记忆"这个让多轮对话能成立的另一半。

完成后你应该能回答：

1. 为什么前端绝不应该直接解析 LangGraph 的节点名和 Checkpoint State？
2. SSE 事件里，哪些字段能发、哪些必须裁剪？裁剪的默认规则是什么？
3. `conversation_id`/`thread_id`/`run_id`/`request_id` 四个 ID 分别指什么？为什么不能混用？
4. 客户端断开后，Agent 是取消还是继续？这个决策由谁做、依据什么？

## 2. 本章完成标准

必须同时满足：

- `stream_adapter.py` 用 Allowlist 把 LangChain 三种 Stream Mode（`updates`/`messages`/`custom`）映射为自有 SSE 事件，未识别事件**不发送**；
- 12 个 SSE 事件命名与[企业级项目蓝图](../01-总览与使用方式/03-企业级项目蓝图.md)完全一致，终态互斥且只发送一次；
- 工具参数默认裁剪为"工具显示名 + 阶段 + 安全摘要"，不把完整 `arguments`、模型推理内容、Checkpoint State 推给前端；
- 短期记忆按 Token 预算保留近期消息与关键事实，重要业务事实（告警状态、审批结果）从权威系统重读而非依赖摘要；
- `uv run pytest` 全绿：契约测试覆盖"事件不泄密 / 顺序可测 / 终态不重复 / 断线策略明确"，真实 API 调用次数为 0。

## 3. 流式的三类信息

一次 Agent 运行对外要表达三类信息，它们的消费方和敏感度完全不同：

| 类别 | 例子 | 消费方 | 敏感度 |
| --- | --- | --- | --- |
| 模型文本增量 | 答案逐字出现 | 打字机效果 | 低（但推理过程除外） |
| Agent 状态更新 | 步骤完成、工具开始/结束 | 进度条/状态灯 | 中（工具参数可能敏感） |
| 自定义进度 | "检索中"、"等待审批" | 业务提示 | 低 |

三类信息不能混在一起发。前端要的是一个**类型化的事件流**，而不是"把所有内部日志原样转发"。因此第一步是建立 `stream_adapter.py` 的 Allowlist 映射：**白名单之外的内部事件一律丢弃**。这对应第 1 章"框架不是架构"的延续——框架的内部结构可以随便重构，只要公开协议不变，前端就不受影响。

## 4. 安全裁剪：默认不发送，而不是默认发送

安全原则是**默认裁剪、显式放行**。下面几类内容绝不出现在公开事件里：

- 模型推理内容（思维链）；
- Tool 的完整 `arguments`（可能含设备编号、查询条件、内部字段名）；
- Checkpoint State / 内部节点名；
- 未识别的框架事件。

工具事件默认只发三个字段：工具显示名、当前阶段（如"查询中"）、一段安全摘要。要发送更细的信息（如"共命中 3 条手册"）必须显式构造并经过 `stream_adapter` 的允许规则。这样即使未来有人往工具里加了敏感参数，默认行为也是"不发"，而不是"忘了删就漏了"。

## 5. LangChain 三种 Stream Mode 与 v2 Streaming

`create_agent` 返回的 Agent 通过 `astream` 暴露流。当前常用三种 Stream Mode：

| Mode | 含义 | 对外建议 |
| --- | --- | --- |
| `updates` | 每个 Agent Step 的 State Update | 映射为安全的阶段进度 |
| `messages` | 模型 Token/内容块及元数据 | 只发送允许展示的文本块 |
| `custom` | 业务代码主动发送的进度 | 映射为检索、审批等业务事件 |

当锁定的 LangGraph 版本支持 v2 Streaming 时，显式使用 `version="v2"`，统一按 `type/ns/data` 结构读取，避免 v1 的字段差异：

```python
# api/stream_adapter.py
class StreamAdapter:
    """把 LangChain 内部流映射为自有 SSE 事件；白名单之外不发送。"""

    ALLOWED_UPDATES = {"messages"}  # 只认这些 namespace，其余丢弃

    def to_public_event(self, part: dict) -> dict | None:
        kind = part.get("type")
        if kind == "messages":
            return self._message_event(part)
        if kind == "custom":
            return self._custom_event(part)
        return None  # updates 等未识别类型：不发送

    def _message_event(self, part: dict) -> dict | None:
        chunk = part.get("data", {})
        text = chunk.get("text") or chunk.get("content")
        if not text:
            return None
        return {"type": "message.delta", "text": text}

    def _custom_event(self, part: dict) -> dict | None:
        data = part.get("data", {}) or {}
        name = data.get("name")
        if name not in {"progress", "input_required", "approval_required"}:
            return None
        return {"type": name, "detail": data.get("detail", "")}


async def stream_agent(agent, command):
    adapter = StreamAdapter()
    async for part in agent.astream(
        {"messages": [{"role": "user", "content": command.message}]},
        context=command.context,
        stream_mode=["messages", "custom"],
        version="v2",
    ):
        event = adapter.to_public_event(part)
        if event is not None:
            yield event
```

注意 `stream_adapter` 不是"透传"，而是"翻译 + 过滤"：`updates` 里带完整 State 的部分被 `ALLOWED_UPDATES` 之外的规则挡掉，`messages` 里带推理元数据的块被 `_message_event` 裁剪成纯文本。**框架内部节点名、Checkpoint State、完整 Tool 参数，永远不出现在公开事件里。**

## 6. 自有 SSE 事件契约

课程对外 SSE 协议从第 2 阶段第 4 章的四个核心事件出发，本章随 Agent 能力扩展为完整集合（与蓝图事件契约一致）：

```text
run.started        # 核心事件（第 2 阶段第 4 章已落地）
message.delta      # 文本增量（命名与第 2 阶段一致）
run.progress       # 稳定业务阶段（如"检索中"），不是节点名
tool.started       # 第 2 阶段预留的工具事件命名
tool.completed
tool.failed
input.required     # 需要用户补充信息
approval.required  # Human-in-the-loop 审批等待
run.completed
run.failed
run.cancelled
run.execution_limit_reached
```

三条硬规则：

1. **终态互斥**：`run.completed`/`run.failed`/`run.cancelled`/`run.execution_limit_reached` 四个终态事件只出现其中一个、且只发送一次；
2. **顺序**：`run.completed` 到达后不能再出现任何 `message.delta`；
3. **去重**：每条事件带 `run_id + seq`，客户端据此去重；Tool 重试不应让 UI 误显示重复副作用。

## 7. 短期记忆：多轮对话的上下文边界

短期记忆服务于一个 Thread 内的连续交互。它的核心是**边界**，而不是"把历史无限追加"：

- 按 Token 预算保留近期消息、关键事实和状态；
- **摘要也是模型生成数据**，可能遗漏或改写；告警状态、审批结果等业务事实必须从权威系统重新读取；
- 记忆的写入要可控、可删除，为后续第 5 阶段的隐私与合规留接口。

四个 ID 必须分清楚，混用会导致状态串线：

| ID | 语义 | 生命周期 |
| --- | --- | --- |
| `conversation_id` | 产品会话标识 | 一次用户对话 |
| `thread_id` | Graph 持久化运行上下文 | 一次可恢复的任务线程 |
| `run_id` | 一次执行 | 单次 `ainvoke`/`astream` |
| `request_id` | 一次 HTTP 请求 | 单次请求-响应 |

一个 `conversation_id` 可以跨越多次 `run_id`（多轮），一个 `thread_id` 可以被多次 `run_id` 复用（断点续跑）。

## 8. 断线与背压

流式接口有两个容易被忽略的工程问题：

- **背压**：客户端消费慢时，要限制缓冲，不能让服务端无限堆积待发送事件；
- **断线**：客户端断开后，是取消 Agent 还是后台继续，是**用例决策**，不是技术默认值。

交互式问答可以取消以释放资源；进入审批或需要可靠后台交付的任务则应继续，并让客户端能通过 Run API 查询最终状态。这个策略必须显式写出来并测试，而不是靠"断开连接会怎样"的直觉。

## 常见错误与诊断顺序

### 前端解析了 LangGraph 节点名

现象：改了图里的节点名，前端进度条就崩了。根因是把框架内部实现当成了公开协议。诊断：确认 `stream_adapter` 是否拦截了 `updates` 里的节点名，前端是否只依赖 12 个公开事件名。

### 终态事件重复发送

现象：`run.completed` 出现两次，或 `run.completed` 之后又冒出 `message.delta`。根因是终态判断散落在多处。诊断：终态由单一出口发送，发送后置标志位；契约测试断言"终态互斥且只出现一次"。

### 工具参数原样转发

现象：前端抓包能看到完整 `arguments` 里的设备编号或内部字段。根因是默认透传而非默认裁剪。诊断：确认 `tool.started`/`tool.completed` 只带显示名 + 阶段 + 安全摘要，完整参数只进服务端 Trace。

### 摘要当成业务事实源

现象：对话很长后，Agent 把"某告警已处理"（其实是摘要里的旧信息）当成现状。根因是让模型摘要承担了事实存储。诊断：业务事实一律从 `domain`/数据库重读，摘要只用于压缩上下文、不用于裁决。

## 练习题与答案

### 练习 1：为什么前端不应解析 LangGraph 节点名？

**答案：**节点属于框架内部实现，重构图（改名、拆节点、换路由）就会破坏客户端。前端只依赖稳定的业务事件（`run.started`/`tool.completed`/`run.completed` 等），框架怎么改都不影响协议。

### 练习 2：对话摘要能当业务事实源吗？

**答案：**不能。摘要是模型生成数据，可能遗漏、简化或改写；告警状态、审批结果必须从权威系统重新读取。摘要只用于压缩对话上下文、降低 Token 成本，不作为事实裁决依据。

### 练习 3：客户端断开是否一定要取消 Agent？

**答案：**不一定。交互式问答可取消以释放资源；进入审批或需要可靠后台交付的任务可能要继续，并让客户端通过 Run API 查询最终状态。这个策略要按用例明确、做成可配置项并测试，而不是默认行为。

## 面试追问

### "你们的流式接口怎么保证不泄露敏感信息？"

回答框架：用 `stream_adapter` 做 Allowlist 映射 + 默认裁剪。模型推理内容、Tool 完整参数、Checkpoint State、内部节点名默认不发送，工具事件只发显示名 + 阶段 + 安全摘要；完整数据只进服务端 Trace。前端依赖的是 12 个稳定事件，而不是框架内部结构。

### "多轮对话的上下文怎么管理？"

回答框架：短期记忆按 Token 预算保留近期消息与关键事实；但要分清 `conversation_id`（会话）、`thread_id`（可恢复运行）、`run_id`（单次执行）、`request_id`（单次请求）四个 ID。摘要只是压缩手段，业务事实（告警状态、审批结果）从权威系统重读，不把模型摘要当事实源。
