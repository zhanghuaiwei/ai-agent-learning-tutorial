# 学习环境与第一个模型网关

> 所属阶段：第 1 周  
> 预计用时：8～10 小时  
> 项目产出：可以切换千问/DeepSeek 的最小模型网关 CLI  
> 资料验证日期：2026-08-31

## 1. 本章为什么不从 LangChain 开始

LangChain、LangGraph 都建立在模型 API 之上。如果第一步就使用框架，遇到错误时很难判断问题来自：

- API Key 或地域；
- 模型名称；
- OpenAI-compatible 协议差异；
- 网络、超时或限流；
- LangChain Provider Adapter；
- Prompt；
- Agent 本身。

本章只做一件事：建立最薄的模型访问层，直接理解一次请求的输入、输出、Usage 和错误。

完成后你应该能回答：

1. OpenAI-compatible 到底兼容什么？
2. `api_key`、`base_url`、`model` 各自控制什么？
3. 为什么业务代码不应该直接依赖千问或 DeepSeek SDK？
4. 为什么成功输出一段文字还不算完成模型网关？
5. 怎样在不重复付费的情况下测试大部分代码？

## 2. 本章完成标准

必须同时满足：

- Python 项目由 `uv` 管理；
- API Key 没有写入源码或 Git；
- 千问完成一次非流式调用；
- 千问完成一次流式调用；
- DeepSeek 至少完成一次连通性调用；
- 只修改环境变量就能切换供应商；
- 输出中可以看到模型、Token 和请求 ID（供应商未返回时允许为空）；
- 能区分 401、429、超时和模型不存在；
- 本章真实 API 调用不超过 5 次。

## 3. 先理解四个对象

### 3.1 SDK

SDK 是帮助我们构造 HTTP 请求和解析响应的客户端库。这里使用 `openai` Python SDK，不代表我们必须调用 OpenAI 模型。

千问和 DeepSeek 都提供 OpenAI-compatible 接口，因此可以复用相同 SDK，通过更换配置访问不同服务。

### 3.2 API Key

API Key 用于认证和计费。它不是普通配置：

- 不写入代码；
- 不提交 Git；
- 不打印到日志；
- 不放到前端；
- 泄漏后立即吊销，而不是只删除 Git 中的新版本。

### 3.3 Base URL

`base_url` 决定请求发往哪个模型服务。

```text
SDK + 千问 Base URL + 千问 Key → 千问
SDK + DeepSeek Base URL + DeepSeek Key → DeepSeek
```

千问的 API Key 与地域/业务空间存在绑定关系，Key 与 Base URL 不匹配可能返回认证错误。必须以百炼控制台和当前官方文档为准。

### 3.4 Model

`model` 决定供应商内部使用哪个模型。模型名称变化速度比课程快，所以不能把“当前最新模型名”写进长期业务逻辑。

本项目通过环境变量配置模型：

```text
LLM_PROVIDER
LLM_API_KEY
LLM_BASE_URL
LLM_MODEL
```

## 4. OpenAI-compatible 不等于完全相同

通常兼容的是请求结构，例如：

- `messages`；
- `model`；
- `stream`；
- `tools`；
- `response_format` 的部分能力；
- Usage 的常见字段。

但不同供应商仍可能在以下方面不同：

- 支持的模型和参数；
- Tool Calling 的严格程度；
- Thinking/Reasoning 参数；
- Responses API 的兼容范围；
- 错误码和响应 Header；
- Token 统计；
- 是否支持 `stream_options`；
- 速率限制和价格。

因此，统一 SDK 只是第一层复用，仍然需要 Provider Adapter、能力声明和契约测试。

## 7. 配置对象

创建 `src/agent_service/config.py`：

```python
from __future__ import annotations

import os
from dataclasses import dataclass


@dataclass(frozen=True, slots=True)
class LLMSettings:
    provider: str
    api_key: str
    base_url: str
    model: str
    timeout_seconds: float = 30.0

    @classmethod
    def from_env(cls) -> "LLMSettings":
        required_names = (
            "LLM_PROVIDER",
            "LLM_API_KEY",
            "LLM_BASE_URL",
            "LLM_MODEL",
        )
        values: dict[str, str] = {}
        missing: list[str] = []

        for name in required_names:
            value = os.getenv(name)
            if value:
                values[name] = value
            else:
                missing.append(name)

        if missing:
            joined = ", ".join(missing)
            raise RuntimeError(f"缺少必要环境变量: {joined}")

        return cls(
            provider=values["LLM_PROVIDER"],
            api_key=values["LLM_API_KEY"],
            base_url=values["LLM_BASE_URL"],
            model=values["LLM_MODEL"],
        )
```

为什么不直接在 `main.py` 里读取？

- 配置读取有独立职责；
- 缺失项可以一次性报告；
- 后续可以替换为 Pydantic Settings；
- 测试时可以直接构造 `LLMSettings`，不依赖真实环境；
- `frozen=True` 降低运行期间被意外修改的概率。

这还不是最终企业配置，只是刻意保持可理解的第一版。

## 8. 最小模型网关

创建 `src/agent_service/gateway.py`：

```python
from __future__ import annotations

from dataclasses import dataclass
from typing import Iterator

from openai import OpenAI

from agent_service.config import LLMSettings


@dataclass(frozen=True, slots=True)
class ChatResult:
    text: str
    provider: str
    model: str
    input_tokens: int
    output_tokens: int
    request_id: str | None


class OpenAICompatibleGateway:
    def __init__(self, settings: LLMSettings) -> None:
        self._settings = settings
        self._client = OpenAI(
            api_key=settings.api_key,
            base_url=settings.base_url,
            timeout=settings.timeout_seconds,
            # 本章先关闭 SDK 自动重试，确保能观察原始失败。
            # 第 3 周会重新设计有限重试。
            max_retries=0,
        )

    def chat(self, user_text: str) -> ChatResult:
        response = self._client.chat.completions.create(
            model=self._settings.model,
            messages=[
                {
                    "role": "system",
                    "content": "你是设备维护知识助手。信息不足时明确说明，不编造事实。",
                },
                {"role": "user", "content": user_text},
            ],
        )

        text = response.choices[0].message.content or ""
        usage = response.usage

        return ChatResult(
            text=text,
            provider=self._settings.provider,
            model=response.model,
            input_tokens=usage.prompt_tokens if usage else 0,
            output_tokens=usage.completion_tokens if usage else 0,
            request_id=getattr(response, "_request_id", None),
        )

    def stream_chat(self, user_text: str) -> Iterator[str]:
        stream = self._client.chat.completions.create(
            model=self._settings.model,
            messages=[
                {
                    "role": "system",
                    "content": "你是设备维护知识助手。信息不足时明确说明，不编造事实。",
                },
                {"role": "user", "content": user_text},
            ],
            stream=True,
        )

        for chunk in stream:
            # 某些兼容供应商可能发送不含 choices 的统计/控制 Chunk。
            if not chunk.choices:
                continue
            delta = chunk.choices[0].delta.content
            if delta:
                yield delta
```

### 8.1 为什么网关返回自己的 `ChatResult`

如果业务代码直接使用 SDK Response，供应商或 SDK 变化会沿整个系统扩散。

内部 `ChatResult` 只保留当前业务需要的稳定字段：

- 文本；
- 供应商和模型；
- Token；
- Request ID。

这就是 Anti-Corruption Layer 的最小雏形：外部协议可以变化，内部契约尽量稳定。

### 8.2 为什么本章关闭自动重试

SDK 自动重试在生产中可能有价值，但入门时会隐藏：

- 第一次请求是否失败；
- 实际进行了多少次调用；
- 延迟为何突然增加；
- 是否重复计费；
- 写工具将来是否产生重复副作用。

第 3 周会在理解错误分类后重新加入明确、可记录的重试策略。

### 8.3 为什么流式方法暂时不统计 Usage

不同 OpenAI-compatible 供应商对流式 Usage 的支持可能不同。本章先保证安全地拼接文本；后续会增加 Provider Capability 与统一 Usage Event。

不要为了让第一版“看起来完整”而伪造 Token 为准确值。

## 9. CLI 入口

创建 `src/agent_service/main.py`：

```python
from agent_service.config import LLMSettings
from agent_service.gateway import OpenAICompatibleGateway


def run_non_stream() -> None:
    settings = LLMSettings.from_env()
    gateway = OpenAICompatibleGateway(settings)

    result = gateway.chat("设备温度升高通常需要先收集哪些信息？")

    print(result.text)
    print("\n--- usage ---")
    print(f"provider={result.provider}")
    print(f"model={result.model}")
    print(f"input_tokens={result.input_tokens}")
    print(f"output_tokens={result.output_tokens}")
    print(f"request_id={result.request_id}")


def run_stream() -> None:
    settings = LLMSettings.from_env()
    gateway = OpenAICompatibleGateway(settings)

    for text_delta in gateway.stream_chat(
        "请用三点说明设备异常排查时为什么必须保留原始告警。"
    ):
        print(text_delta, end="", flush=True)
    print()


if __name__ == "__main__":
    run_non_stream()
```

运行：

```bash
uv run python -m agent_service.main
```

第一次成功后，把入口临时改为 `run_stream()`，再运行一次。不要在循环中反复在线测试。

## 11. 第一天就要建立的费用意识

### 11.1 本章建议调用矩阵

- 千问非流式与流式均完成 Smoke Test；
- DeepSeek 完成连通性与错误契约测试；
- 排错时允许按需调用，不设金额或次数上限；
- 普通自动化测试仍使用 Fake/回放，以保证结果确定且执行快速。

### 11.2 费用计算

通用估算公式：

```text
本次费用
= 输入 Token ÷ 1,000,000 × 输入单价
+ 输出 Token ÷ 1,000,000 × 输出单价
```

具体单价从供应商当前官方价格页读取，不写死在课程里。

后续系统会增加：

- 按模型、任务和环境统计 Usage 与费用；
- 费用异常增长告警，但不设置教程金额上限；
- 单次最大 Token；
- 单任务最大步骤；
- 模型分级路由；
- Fake Model 和录制回放。

## 12. 常见错误与诊断顺序

### 12.1 缺少环境变量

现象：程序在发请求前抛出 `缺少必要环境变量`。

这是好错误，因为没有浪费 API 费用，也没有把问题推迟到远端。

诊断：

```bash
python3 -c "import os; print(bool(os.getenv('LLM_API_KEY')))"
```

### 12.2 401 / Authentication Error

按顺序检查：

1. Key 是否复制完整；
2. Key 是否被禁用或过期；
3. 千问 Key 与地域 Base URL 是否一致；
4. Base URL 是否包含官方要求的路径；
5. 是否错误地把千问 Key 配给 DeepSeek Base URL；
6. 环境变量中是否带多余引号或空格。

不要把 Key 打印出来排查。

### 12.3 404 / Model Not Found

检查：

- 模型名称是否来自当前控制台；
- 当前地域是否提供该模型；
- 模型服务是否已经开通；
- Base URL 是否正确；
- 示例中的旧模型名是否已经变化。

### 12.4 429 / Rate Limit

429 不只是“请求太快”，也可能是额度或账户限制。第一周不要立即写无限重试：

1. 读取错误信息；
2. 检查额度与控制台；
3. 等待合理时间；
4. 只手动重试一次；
5. 记录问题。

### 12.5 Timeout

检查：

- 网络是否可访问供应商；
- Base URL 是否正确；
- 模型是否处于高延迟模式；
- 是否请求了过长输出；
- 超时发生在连接、读取还是总请求。

本章不把超时从 30 秒直接改成 10 分钟。长超时会把错误隐藏成“程序很慢”。

### 12.6 流式输出为空

检查：

- 是否真的设置 `stream=True`；
- 是否读取 `delta.content`；
- 某个 Chunk 是否只包含角色或结束原因；
- 供应商是否使用不同的流式扩展；
- 最终是否有异常被吞掉。

## 13. 练习题与答案

### 练习 1：配置职责

问题：以下四个配置分别解决什么问题？

```text
LLM_PROVIDER
LLM_API_KEY
LLM_BASE_URL
LLM_MODEL
```

答案：

- `LLM_PROVIDER` 是内部标识，用于日志、路由和选择 Provider 特有逻辑；
- `LLM_API_KEY` 负责远端认证与计费；
- `LLM_BASE_URL` 决定请求发送到哪个供应商/地域/业务空间；
- `LLM_MODEL` 选择供应商内部模型。

只改 `LLM_PROVIDER` 不会自动把请求发到另一个供应商，真正的网络目的地由 Base URL 决定。

### 练习 2：为什么不能只使用一个 `MODEL_NAME`

答案：模型名通常只在某个供应商和接口中有意义。没有 Base URL 和认证信息，`qwen-...` 或 `deepseek-...` 无法决定完整调用位置。企业系统还需要知道供应商以应用不同的能力和错误处理。

### 练习 3：给配置加载写测试思路

问题：不调用真实 API，怎样验证缺少环境变量时能一次性报告？

答案思路：

1. 使用 pytest 的 `monkeypatch.delenv` 删除四个变量；
2. 调用 `LLMSettings.from_env()`；
3. 断言抛出 `RuntimeError`；
4. 断言消息同时包含四个变量名；
5. 测试结束后由 `monkeypatch` 自动恢复环境。

参考代码将在测试章节正式实现：

```python
import pytest

from agent_service.config import LLMSettings


def test_settings_reports_all_missing_names(monkeypatch: pytest.MonkeyPatch) -> None:
    names = ("LLM_PROVIDER", "LLM_API_KEY", "LLM_BASE_URL", "LLM_MODEL")
    for name in names:
        monkeypatch.delenv(name, raising=False)

    with pytest.raises(RuntimeError) as captured:
        LLMSettings.from_env()

    for name in names:
        assert name in str(captured.value)
```

### 练习 4：为什么关闭自动重试

答案：第一周需要观察真实错误和真实调用次数。自动重试可能增加延迟、费用，并在未来对写工具产生重复副作用。关闭不是永久决策，而是为了先建立可解释 Baseline，再在第 3 周加入有分类、有上限、有记录的重试。

### 练习 5：接口兼容是否等于模型行为一致

答案：不等于。接口兼容只说明请求与响应的大体格式可复用。模型的指令遵循、Tool Calling、结构化输出、Reasoning、上下文和安全行为都可能不同，仍需针对真实评测集验证。

### 练习 6：无金额上限时还要记录费用吗

问题：既然教程不设置 API 金额上限，为什么仍要记录每次调用费用？

答案：费用是系统行为指标。它可以暴露死循环、重复上下文、多层重试和模型路由异常，也能支持企业容量规划。记录费用不代表必须设置消费上限。

## 14. 工程挑战

在不增加真实 API 调用的前提下完成：

1. 为 `LLMSettings` 增加 `max_output_tokens`；
2. 从环境变量读取，并验证必须是正整数；
3. 将其传给模型请求；
4. 写出三个测试用例：合法数字、零、非数字；
5. 确保错误在发起网络请求前发生。

参考答案方向：

- 字符串转整数放在配置边界；
- 捕获 `ValueError` 并抛出包含变量名的配置错误；
- `<= 0` 明确拒绝；
- Gateway 只接收已经验证的整数；
- 测试只验证配置，不创建真实 Client。

本题不提供整段复制代码，因为目标是第一次独立修改；完成后再与上述设计点逐一核对。

## 15. 面试追问

### 15.1 为什么要做模型网关？

回答框架：

1. 隔离供应商 SDK 与业务代码；
2. 统一输入输出、错误、Usage 和 Trace；
3. 支持模型路由、降级和成本控制；
4. 集中处理安全与重试；
5. 通过契约测试验证兼容性。

不要只回答“方便切换模型”，那只是结果之一。

### 15.2 Chat Completions 与 Responses API 怎么选？

回答框架：

- 先看目标供应商当前兼容范围；
- 本教程第一版用 Chat Completions 获得千问/DeepSeek 的共同基础；
- 高级工具、状态或供应商特有能力可能需要 Responses API；
- 业务层不直接绑定某一种远端协议；
- 通过评测和能力需求决定，不因“新”就盲目迁移。

### 15.3 为什么 API Key 不能放前端？

前端代码和网络请求都可被用户观察，Key 会被复制滥用，导致数据与费用风险。前端只能调用自己的后端，后端再代表受认证用户调用模型，并执行限流、审计和权限控制。
