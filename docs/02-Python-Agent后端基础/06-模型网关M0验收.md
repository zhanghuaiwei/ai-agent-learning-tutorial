# 模型网关 M0 验收

> 第 4 周里程碑｜目标：建立后续所有章节复用的可靠底座，并用证据证明它。

## 1. 里程碑定位

M0 不是"做完了"，而是"可以证明做对了"。第 1～5 章建成的底座将承载后续全部阶段：

| 构件 | 所在文件 | 建立章节 |
| --- | --- | --- |
| 配置与 `.env` | `config.py` | 第 1、5 章 |
| 数据契约 | `schemas.py` | 第 2 章 |
| 双风格异步网关 + Protocol | `gateway.py` | 第 1～3 章 |
| 错误分类与三级错误体系 | `errors.py` | 第 3、5 章 |
| 可靠执行器（超时/重试/并发/取消） | `executor.py` | 第 3 章 |
| REST + SSE API、运行登记 | `api.py`、`service.py`、`runs.py` | 第 4 章 |
| 测试替身 | `fakes.py`、`tools.py` | 第 2、3 章 |
| 结构化日志 | `logging_setup.py` | 第 5 章 |

验收要回答的问题只有一个：**这套底座是否值得被后面 18 周的代码依赖？**不值得就现在修，越晚越贵。

## 2. 必交功能清单

逐项核对，每项都应能指向代码位置或测试名称：

- [ ] 统一 `ModelGateway` 接口（Protocol），千问与 DeepSeek 差异只存在于网关实现与 `_build_client`；
- [ ] 普通（`POST /v1/chat`）与 SSE（`POST /v1/chat/stream`）API 可用，`run_id` 贯穿响应、日志、状态查询；
- [ ] 超时、最多两次重试、指数退避加抖动、并发信号量、取消传播、耗时统计（`ReliableInvoker` + `InvokeStats`）；
- [ ] 错误分级与稳定错误码，供应商原始错误不出边界（`errors.py` + 全局异常处理器）；
- [ ] Fake 网关与故障注入（`FakeGateway` / `FlakyGateway`），断网可跑全部测试；
- [ ] `.env.example` 齐全，配置覆盖顺序"默认值 < `.env` < 环境变量"有验证记录；
- [ ] JSON 结构化日志含 `run_id`、耗时、attempts、结果码，无 Prompt 原文、无 Key。

## 3. 验收场景

每个场景都要有可复现的验证方式（测试名或手工操作步骤）：

| 场景 | 预期 | 验证方式 |
| --- | --- | --- |
| 正常问答 | 返回文本、模型、Token、attempts、elapsed_ms | `test_chat_success` + 在线 Smoke |
| 首次 429 后成功 | 仅重试一次，attempts=2，日志有记录 | `test_retry_then_success` |
| 持续 429 | 3 次尝试后放弃，HTTP 429 + `GW_RATE_LIMITED` | `test_upstream_failure_maps_to_503` 同构 |
| 永久 400/401 | 不重试，attempts=1，错误体脱敏 | `test_permanent_error_no_retry` |
| 总超时 | 预算内结束，无遗留任务 | `test_total_deadline_enforced` |
| 客户端断开 | 上游调用被取消，run 状态 `cancelled` | `test_cancellation_propagates` + 手工 curl 实验 |
| 并发上限 | 峰值并发不超过信号量上限 | `test_concurrency_cap` |
| 流中途失败 | 收到 `run.failed` 事件而非半个回答 | `test_stream_event_order` 的失败注入变体 |
| 费用异常增长 | 通过台账与 `chat.completed` 日志定位（重试风暴、循环） | §6 费用观测 |

## 4. 环境重建

证明底座可复现，而不是"只在我的机器上能跑"：

```bash
git clone <你的仓库地址> agent-service-fresh
cd agent-service-fresh
uv sync                     # 从 uv.lock 精确还原依赖
cp .env.example .env        # 填入真实配置
uv run pytest               # 必须全绿且零真实调用
```

重建失败的常见原因：`.env.example` 缺字段、`uv.lock` 没提交、测试隐式依赖了本机环境变量、`tests/` 目录没有提交全。**在 fresh clone 里验收，不要在开发目录里自我安慰。**

## 5. 在线 Smoke Test

离线测试证明逻辑正确，Smoke Test 证明"真实集成是通的"。预算：**不超过 5 次真实调用**（第 1 章的约定在本里程碑最后一次执行）：

| # | 调用 | 验证点 |
| --- | --- | --- |
| 1 | 千问 Chat Completions 非流式 | 200，Token 数合理，request_id 有值 |
| 2 | 千问流式 | 事件顺序正确，中文正常 |
| 3 | 千问 Responses 风格 | 同一 `.env` 只改 `LLM_API_STYLE` 即切换 |
| 4 | DeepSeek 连通性 | 切换供应商只动配置 |
| 5 | 错误契约（可选） | 故意填错 Key 一次，确认 401 → 不重试 → 脱敏错误体 |

每次调用后立即把 Token 数与估算费用记入台账。5 次之后，之后的回归全部离线——需要真实模型行为时，那是评测（第 7 阶段）的工作。

## 6. 费用观测

- [ ] 用[API 费用台账模板](../99-附录/06-API费用台账模板.md)记录 M0 全部真实调用；
- [ ] 台账能回答：总费用、每个供应商的 Token 分布、单次最贵调用及其 `run_id`；
- [ ] `chat.completed` 日志与台账数字能对上（差一条就是漏记）。

费用异常增长（如某次调试反复重试导致 attempts 持续为 3）要能从日志定位到具体 `run_id`——这是"费用作为系统行为指标"的第一次实战。

## 7. 通过标准

同时满足才算通过 M0：

1. **测试不少于 20 个**（unit + integration + e2e 合计，按测试函数数）；
2. **连续 30 次 Fake 请求无泄漏**：循环执行离线冒烟 30 次，无失败、无告警、无凭据出现在日志（写个 10 行的循环脚本即可验证）；
3. **真实调用费用可查**：台账覆盖全部 Smoke 调用；
4. **能脱稿解释**：异步事件循环为什么适合模型网关、重试为什么必须分类且有上限、取消为什么不能吞、Fake 为什么放在 `src`；
5. **环境重建**通过（§4）。

任何一条不满足：先补底座，不进入下一阶段。下一阶段的 Function Calling、RAG、LangGraph 全部压在这套网关、契约和测试上——底座的裂缝会被成倍放大。

## 8. 练习与答案

### 练习 1：为何不直接到处调用供应商 SDK？

**答案：**网关集中隔离供应商差异，统一处理超时、重试、并发、费用观测和错误脱敏；业务代码依赖 `ModelGateway` 协议，因此可测试（Fake 注入）、可替换（改配置切供应商）、可演进（加风格不动业务）。代价是只抽象"实际共同的能力"——过度抽象的网关比没有网关更难维护。

### 练习 2：怎样证明切 Provider 没破坏业务？

**答案：**三层证据：契约测试全绿（结构行为不变）、固定评测集对比（质量指标不回退——评测在第 7 阶段补上后回填）、少量影子流量（真实分布下的成功率、延迟、成本、安全指标）。只有 Smoke Test 通过不算证明。

### 练习 3：M0 的"通过"依赖测试数量吗？

**答案：**20 是底线不是目标。数量的价值在于场景覆盖度——9 个验收场景各有测试对应，比 100 个重复断言更有意义。如果 9 个场景都覆盖了，20 自然超过。

## 10. 通过之后

进入下一阶段：LLM 应用与原生 Agent（G1 门槛）。第一个真正的 Agent 能力是 Structured Output——让模型按我们的 Schema 输出 JSON。第 2 章的 Pydantic 契约、本章的稳定错误码会在那里直接复用；`FakeGateway` 将升级为能返回"合法/非法结构化输出"的替身，用于离线验证解析与修复逻辑。

在那之前，不要碰框架。底座未稳就上框架，是把 LangChain 的默认行为当成自己的架构。
