# 测试、日志、配置与错误体系

> 所属阶段：第 4 周  
> 预计用时：6～7 小时  
> 项目产出：没有真实模型也能稳定回归的服务骨架  
> 资料验证日期：2026-09-02

## 1. 本章从哪里开始

第 4 章结束时，服务已经有六个端点、SSE 事件协议和内存运行登记表。但三个地基是空的：

- **测试不成体系**：现有测试覆盖了 Schema 和执行器，API 层只有零星几个；lifespan、错误映射、断开取消都没有回归保护；
- **日志裸奔**：`InvokeStats` 的重试次数和耗时只存在于返回值里，打印几行就丢了。出了问题，无法回答“那次 429 重试了吗、哪次调用最慢”；
- **配置手写**：`LLMSettings.from_env()` 是第 1 周的最小实现——缺 `.env` 支持、缺覆盖顺序、缺结构化报错。

本章把这三块补齐，并统一错误体系。这是 M0 验收前的最后一章。完成后你应该能回答：

1. “代码是否按约定运行”（测试）和“系统是否足够好”（评测）为什么是两个问题？
2. 一条结构化日志应该包含哪些字段，又不应该包含什么？
3. 配置的覆盖顺序是什么，为什么启动时校验？
4. 异常分类为什么必须分级，全局处理器解决什么？

## 2. 本章完成标准

必须同时满足：

- `tests/` 分为 `unit` / `integration` / `e2e` 三层，各自职责明确；
- 第 1 章练习 3 承诺的配置测试正式落地（`monkeypatch` 删环境变量，断言一次性报错）；
- 全局异常处理器统一错误体格式，422/500 也含稳定 `code`；
- JSON 结构化日志包含 `run_id`/`request_id`、耗时、结果码，且**不含** Prompt 原文与 API Key；
- 配置迁移到 `pydantic-settings`，支持 `.env`，覆盖顺序为“默认值 < `.env` < 环境变量”；
- 断网状态下 `uv run pytest` 全绿。

## 3. 测试分层

| 层 | 测什么 | 依赖 | 速度 |
| --- | --- | --- | --- |
| 单元（unit） | 确定性函数：Schema 校验、成本计算、错误分类、退避时长 | 无外部依赖 | 毫秒级 |
| 集成（integration） | 组装后的行为：API 路由 + 错误映射 + 事件顺序 | Fake 网关，无网络 | 秒级 |
| 端到端（e2e） | 从入口到替身的完整链路：lifespan 启动 → 请求 → 断言 | Fake，无网络 | 秒级 |
| Agent 评测 | 回答质量、轨迹、检索质量 | 真实模型，受控执行 | 分钟级 |

一个容易混淆的边界：**普通测试回答“代码是否按约定运行”，评测回答“概率系统是否足够好”**。测试断言“重试后 `attempts == 2`”，评测度量“回答引用准确率 87%”。前者必须确定性全绿，后者允许统计波动。两者不能互相替代——测试再全也无法证明模型回答得好，评测分数再高也拦不住下一行代码把重试逻辑写错。评测体系在第 7 阶段展开，本章只做前三层。

```python
import pytest

from agent_service.config import LLMSettings


def test_settings_reports_all_missing_names(monkeypatch: pytest.MonkeyPatch) -> None:
    names = ("LLM_PROVIDER", "LLM_API_KEY", "LLM_BASE_URL", "LLM_MODEL")
    for name in names:
        monkeypatch.delenv(name, raising=False)

    with pytest.raises(RuntimeError) as captured:
        LLMSettings.from_env()

    for name in names:
        assert name in str(captured.value)


def test_settings_rejects_unknown_api_style(monkeypatch: pytest.MonkeyPatch) -> None:
    monkeypatch.setenv("LLM_PROVIDER", "qwen")
    monkeypatch.setenv("LLM_API_KEY", "test-key")
    monkeypatch.setenv("LLM_BASE_URL", "https://example.test")
    monkeypatch.setenv("LLM_MODEL", "test-model")
    monkeypatch.setenv("LLM_API_STYLE", "grpc")

    with pytest.raises(RuntimeError, match="LLM_API_STYLE"):
        LLMSettings.from_env()
```

`monkeypatch` 的价值：测试结束自动恢复环境，测试之间不互相污染。注意断言的是“报错信息里包含全部缺失变量名”——一次性报完，而不是报一个改一个。

### 4.4 CI 禁止真实调用的守卫

测试不允许产生真实 API 费用，靠纪律不够，靠机制。`conftest.py` 加守卫：

```python
@pytest.fixture(autouse=True)
def forbid_real_network(monkeypatch: pytest.MonkeyPatch) -> None:
    """任何测试试图访问真实供应商域名时立刻失败。"""
    forbidden = ("dashscope.aliyuncs.com", "api.deepseek.com")

    original_getenv = __import__("os").getenv

    def guarded_getenv(name: str, *args, **kwargs):
        value = original_getenv(name, *args, **kwargs)
        if name == "LLM_BASE_URL" and value and any(d in value for d in forbidden):
            raise AssertionError("测试不得使用真实供应商 Base URL")
        return value

    monkeypatch.setattr("os.getenv", guarded_getenv)
```

更彻底的做法（把 httpx 传输层换成断言失败的 transport）在 CI 章节实现；当前守卫已经能拦住“误配真实环境变量跑测试”这种最常见的失误。

## 5. 错误体系

### 5.1 分级

第 3 章的 `GatewayError` 只覆盖了“外部依赖错误”这一类。完整的分类是三级：

| 级别 | 例子 | 对外语义 | 典型 HTTP 码 |
| --- | --- | --- | --- |
| 领域错误 | 幂等冲突、找不到运行记录、非法参数 | 用户可以理解并处理 | 400 / 404 / 409 |
| 外部依赖错误 | 供应商 429/5xx/超时、工具失败 | 不是用户的错，稍后可试 | 429 / 503 |
| 系统错误 | 代码 bug、配置错误 | 服务端问题，别暴露细节 | 500 |

`errors.py` 扩展：

```python
class AppError(Exception):
    """所有对外错误的基类：带稳定机器码。"""

    def __init__(self, *, code: str, message: str) -> None:
        super().__init__(message)
        self.code = code
        self.message = message


class DomainError(AppError):
    """领域错误：调用方的输入或状态问题。"""


class GatewayError(AppError):
    """外部依赖错误（第 3 章定义，现在纳入统一层级）。"""

    def __init__(self, *, code, message, retryable, status_code=None) -> None:
        super().__init__(code=code, message=message)
        self.retryable = retryable
        self.status_code = status_code


class SystemError(AppError):
    """系统错误：内部缺陷，细节不出边界。"""
```

错误码命名规范（和 `ToolResult.code` 一脉相承）：

```text
GW_*   网关/供应商
E_*    领域错误
SYS_*  系统错误
```

### 5.2 全局异常处理器

`api.py` 注册，把“到处 try/except”变成“一处翻译”：

```python
from fastapi.responses import JSONResponse


def _register_exception_handlers(app: FastAPI) -> None:
    @app.exception_handler(AppError)
    async def handle_app_error(request: Request, exc: AppError) -> JSONResponse:
        if isinstance(exc, DomainError):
            status = _domain_status(exc.code)
        elif isinstance(exc, GatewayError) and exc.status_code:
            status = 429 if exc.status_code == 429 else 503
        else:
            status = 500
        return JSONResponse(
            status_code=status,
            content={"code": exc.code, "message": exc.message},
        )

    @app.exception_handler(Exception)
    async def handle_unexpected(request: Request, exc: Exception) -> JSONResponse:
        # 未分类异常：只回稳定文案，细节进日志（带 run_id 可查）
        return JSONResponse(
            status_code=500,
            content={"code": "SYS_INTERNAL", "message": "服务内部错误"},
        )
```

两个纪律：**未分类异常的原始信息（类型、堆栈）绝不进响应**——那是最常见的泄漏通道（路径、密钥片段、上游地址）；响应里只有稳定码，细节全在日志里用 `run_id` 关联。422 的错误体本章先保持 FastAPI 原生格式（够用），需要统一成自有格式时在 `_register_exception_handlers` 里加 `RequestValidationError` 的处理器即可——工程挑战之一。

## 6. 结构化日志

### 6.1 为什么不用 print 和裸 logging.info

第 1～4 章的 `print` 是 CLI 时代的选择。服务化之后，日志的第一消费者是**机器**（grep、聚合、告警）而不是人眼。结构化日志 = 每行一个 JSON 对象，字段可查询。

### 6.2 字段约定

`logging_setup.py`：

```python
from __future__ import annotations

import json
import logging
import sys
from datetime import datetime, timezone


class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        payload = {
            "ts": datetime.now(timezone.utc).isoformat(),
            "level": record.levelname,
            "service": "agent-service",
            "event": record.getMessage(),
        }
        # run_id / request_id 等上下文字段通过 extra 注入
        for key in ("run_id", "request_id", "conversation_id", "duration_ms",
                    "result_code", "attempts", "provider", "model"):
            value = record.__dict__.get(key)
            if value is not None:
                payload[key] = value
        return json.dumps(payload, ensure_ascii=False)


def setup_logging(level: int = logging.INFO) -> None:
    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(JsonFormatter())
    root = logging.getLogger()
    root.handlers = [handler]
    root.setLevel(level)
```

调用侧（以第 4 章 `chat` 端点为例的改造方向）：

### 6.3 不记录什么

| 禁止入日志 | 原因 |
| --- | --- |
| Prompt / 回答原文 | 隐私 + 企业文档泄漏风险；体积爆炸 |
| API Key、完整 Base URL | 安全事故的标配 |
| 工具返回的文档正文 | 同 Prompt |
| 完整堆栈（对外） | 内部路径泄漏；堆栈只进服务端日志 |

原则：**日志记录“发生了什么”（事件、标识、指标），不记录“内容本身”**。需要内容级追踪时，那是 LangSmith Trace 的职责（第 7 阶段），且同样要做脱敏。

### 6.4 费用观测的最小闭环

`chat.completed` 事件里的 `provider`、`model`、`input_tokens`（在 `ChatResponse` 里有，一并入日志）配合附录的[API 费用台账模板](../99-附录/06-API费用台账模板.md)，就构成第 1 章 §11 承诺的费用观测闭环：每次调用的 Token 可查、异常增长可发现。费用是系统行为指标——暴露死循环、重复重试、路由异常——而不是需要设置消费开关的东西。

## 7. 配置迁移到 pydantic-settings

### 7.1 为什么迁移

手写 `from_env()` 在第 1 周是合适的：逻辑透明。但它已经落后于需求：没有 `.env` 支持（每次开终端重新 export）、类型转换全手工、报错格式不统一。`pydantic-settings` 一次解决三件事。

```bash
uv add pydantic-settings
```

### 7.2 迁移后的 config.py

```python
from __future__ import annotations

from typing import Literal

from pydantic_settings import BaseSettings, SettingsConfigDict


class LLMSettings(BaseSettings):
    """模型网关配置：默认值 < .env < 环境变量。"""

    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        env_prefix="LLM_",
        extra="ignore",
    )

    provider: str
    api_key: str
    base_url: str
    model: str
    api_style: Literal["chat_completions", "responses"] = "chat_completions"
    timeout_seconds: float = 30.0
```

对照旧版逐项看收益：

| 旧 `from_env()` | 新 `BaseSettings` |
| --- | --- |
| 手工 `os.getenv` 循环 | 字段即声明，自动读取 `LLM_*` |
| 缺失变量手拼报错 | `ValidationError` 列出全部缺失字段 |
| `api_style` 手写校验 | `Literal` 直接约束，非法值报“允许取值清单” |
| 类型全靠自觉 | `timeout_seconds: float` 自动转换与校验 |
| 无 `.env` | 内置支持，且环境变量优先于 `.env` |

覆盖顺序（优先级从低到高）：**字段默认值 → `.env` 文件 → 进程环境变量**。容器编排注入的环境变量永远能覆盖本地 `.env`，这是部署阶段依赖的性质。

### 7.3 .env.example 与兼容

`.env.example` 提交进 Git（真实 `.env` 在 `.gitignore` 里，第 1 章已配置）：

```text
LLM_PROVIDER=qwen
LLM_API_KEY=replace-me
LLM_BASE_URL=replace-me
LLM_MODEL=replace-me
LLM_API_STYLE=chat_completions
```

`from_env()` 类方法保留为兼容别名，但注意异常类型要转换——`BaseSettings` 抛的是 `ValidationError`，而既有调用方（第 1 章代码与 4.1 的测试）约定的是 `RuntimeError`：

```python
from pydantic import ValidationError


class LLMSettings(BaseSettings):
    ...

    @classmethod
    def from_env(cls) -> "LLMSettings":
        """兼容别名：保持第 1 周的构造契约与异常类型。"""
        try:
            return cls()
        except ValidationError as exc:
            raise RuntimeError(f"缺少必要环境变量或配置非法: {exc}") from exc
```

既有测试与调用点零修改——第 2 章契约演进规则的又一次应用：实现换了，构造契约（`LLMSettings.from_env() -> LLMSettings`，失败抛 `RuntimeError`）不变。4.1 的两个配置测试此时应该**原样通过**，迁移没有破坏行为，测试就是证据。

注意 `.env` 的边界：它解决“本地开发 convenience”，不是 secret 管理。真实部署用编排系统的 secret 机制，第 8 阶段部署设计时展开。

5. 配置迁移到 `pydantic-settings`，补 `.env.example`，验证覆盖顺序（改 `.env` 重启生效、环境变量覆盖 `.env`）。

## 9. 常见错误与诊断顺序

### 9.1 monkeypatch 后测试互相污染

确认使用 `pytest.MonkeyPatch` 参数或 `monkeypatch` fixture（自动恢复）；手写 `os.environ[...] = ...` 且不清理是污染根源。

### 9.2 测试随机失败（时好时坏）

按顺序排查：测试之间是否共享了可变替身（`FlakyGateway` 的行为脚本是按调用次数消耗的）；异步测试是否依赖真实时间（退避基线没压到 0.01）；`asyncio_mode = "auto"` 是否配置。

### 9.3 .env 不生效

确认工作目录（`env_file` 相对启动目录解析）；确认没有同名进程环境变量优先覆盖；确认 `.env` 没被意外提交（`git check-ignore .env`）。

### 9.4 日志里看不到 extra 字段

`JsonFormatter` 只挑白名单字段——新字段要加进白名单；用 `record.__dict__` 调试看实际有哪些 key。

### 9.5 异常处理器没接住异常

FastAPI 的 exception handler 匹配的是**精确类型或其子类**的注册顺序；确认异常确实从路由里抛出（`StreamingResponse` 生成器里的异常发生在响应开始后，处理器管不到——那是事件通道的事，第 4 章已定）。

## 10. 练习题与答案

### 练习 1：为什么 CI 不调用真实模型？

**答案：**三个理由：费用（每次回归都是真金白银）、稳定性（网络与模型输出的随机性让测试闪烁）、速度（秒级 vs 毫秒级）。真实调用属于受控评测和 Smoke Test，有独立预算和触发条件。Fake 保证的是“代码逻辑正确”，真实调用回答的是“集成真的通”。

### 练习 2：日志记录完整 Prompt 有何风险？

**答案：**隐私（用户输入可能含个人信息）、合规（企业文档进入日志系统后脱离原权限边界）、安全（系统提示、工具结果可能被用于注入攻击分析）、成本（日志体积膨胀）。原则是事件与指标入日志、内容入 Trace 且脱敏、原文不出必要边界。

### 练习 3：Fake 和 Mock 的分界？

**答案：**Fake 是“能工作的简化实现”（FakeGateway 真的返回结构合法的结果），绑定契约；Mock 是“调用断言装置”，绑定实现细节。优先 Fake：契约稳定时 Fake 几乎不用改，Mock 随每次重构一起碎。

### 练习 4：为什么环境变量要覆盖 `.env` 而不是反过来？

**答案：**编排系统（容器、CI）注入环境变量是最后一公里，必须最优先；`.env` 只是本地开发便利。反过来会导致“CI 想覆盖配置却覆盖不动”，排障成本极高。

### 练习 5：什么时候测试该删？

**答案：**测试对应的契约被删除时（不是“跑不过就删”）。测试是契约的执行形式：契约在，测试在；契约废弃，测试随契约一起退出并记录原因。

## 12. 面试追问

### 12.1 你的测试策略是什么？

回答框架：分层（单元/集成/e2e/评测）+ 每层回答不同问题；替身用 Fake 绑契约而非 Mock 绑实现；CI 零真实依赖（费用、稳定性、速度）；真实调用进受控评测与 Smoke。加分项：说出“测试和评测不可互替”及理由。

### 12.2 结构化日志的设计原则？

回答框架：机器第一消费者，一行一 JSON；字段分上下文（`run_id`/`request_id`）、指标（`duration_ms`/`attempts`）、结果（`result_code`）；内容不入日志（Prompt、Key、堆栈对外）；日志与 Trace 分工。能给出“grep + jq 两分钟回答某次重试”的例子最有力。

### 12.3 异常体系怎么设计？

回答框架：三级分类（领域/外部依赖/系统）→ 每类有稳定机器码 → 一处集中翻译成 HTTP 响应 → 细节只进日志并用 `run_id` 关联。反模式主动列举：到处 `except Exception`、堆栈直接返回给客户端、错误文案里夹带上游原始信息。
