# 最终课程架构

## 1. 架构结论

本教程采用以下总体架构：

```text
岗位能力模型
    ↓
Agent 核心知识主线 ────────┐
Python 工程主线 ──────────┤
企业项目演进主线 ─────────┼── 每周验收门
评测与安全主线 ───────────┤
计算机基础补给线 ─────────┤
面试表达与证据主线 ────────┘
```

教程不是把 LangChain、LangGraph、LangSmith 分别翻译一遍，也不是按 API 罗列功能，而是让六条主线在同一个企业项目中汇合。

课程总计 24 个核心周，每周 15 小时，约 360 小时。2027 年 2 月 14 日前必须完成可投递版本，后续两周用于岗位适配和模拟面试。

## 2. 为什么选择工业运维协同方向

### 2.1 西安产业适配性

西安的《十五五规划纲要》把人工智能与制造业融合、工业互联网、行业大模型、航空航天、低空产业、智能终端和时空信息列为重要发展方向。[西安市十五五规划](https://www.xa.gov.cn/gk/zcfg/xaszfwj/2044274527574188033.html)

西安市 2026 年发展计划进一步提出推进“算力 + 高质量数据集 + 大模型 + AI 应用”，同时推动商业航天、无人机、机器人、汽车和传统产业智能化。[西安市 2026 年国民经济和社会发展计划](https://xadrc.xa.gov.cn/xxgk/ghjh/ndjh/2033388629116690433.html)

因此，项目选择：

**智维 Agent——工业设备维护知识与工单协同平台**

它并不把求职范围锁死在工业企业，而是提供可迁移的企业能力：

- 企业知识库与文档检索；
- 复杂任务的信息收集与规划；
- 业务系统工具调用；
- 状态管理与人工审批；
- 多租户、权限和审计；
- 质量评测、成本和稳定性；
- Java 存量系统与 Python AI 服务集成。

这些能力也能迁移到政企软件、云服务、研发效能、智能客服、能源、汽车、航空航天供应链和企业办公自动化。

### 2.2 为什么不选普通企业知识库

普通知识库容易只覆盖“上传文件—向量检索—生成回答”，难以自然体现 Tool Calling、状态机、审批、事务边界和业务闭环。

工业运维协同场景天然包含：设备、手册、告警、历史案例、工单、人员、审批和风险等级，能合理承载 Agent 的主要能力，但又不需要让模型直接控制设备。

### 2.3 安全边界

项目是辅助决策系统，不是假装具备工业控制资质：

- Agent 可以检索、归纳、建议和创建工单草稿；
- Agent 不得直接控制设备；
- Agent 不得绕过业务服务写数据库；
- 关闭设备、修改高风险工单、指派人员等操作必须人工确认；
- 所有工具调用保留输入、结果、调用者、时间和审批记录；
- 无证据时必须拒绝给出确定性故障结论。

## 3. 岗位能力分层

### 3.1 P0：面试前必须形成的能力

1. **Python Agent 后端**：类型、异步、异常、测试、FastAPI、Pydantic、日志和配置。
2. **模型应用基础**：Message、Token、Context、Prompt、Structured Output、Tool Calling、流式输出。
3. **Agent 原理**：循环、停止条件、工具选择、任务规划、记忆和失败模式。
4. **LangChain**：模型抽象、工具、Agent、中间件、结构化输出和回调。
5. **RAG**：摄取、切分、Embedding、检索、过滤、重排、引用、拒答和评测。
6. **LangGraph**：State、Node、Edge、Reducer、Checkpoint、Interrupt、恢复和子图。
7. **LangSmith**：Trace、Dataset、Experiment、离线与在线评测概念。
8. **可靠性**：超时、重试、幂等、并发、缓存、限流、循环上限、降级和预算。
9. **安全**：Prompt Injection、越权、工具污染、敏感信息、高风险审批和审计。
10. **数据与异步作业**：SQL、事务、索引、Redis、任务队列、重复投递与后台 Worker。
11. **模型边界**：Transformer、自回归生成、KV Cache、RAG/微调/推理服务选型。
12. **工程交付**：API、数据库、Linux 排障、版本管理、CI、部署、发布回滚、README 和架构决策。
13. **面试表达**：能说明业务价值、架构边界、指标、失败案例和权衡。

### 3.2 P1：项目按期时加入的增强能力

- Java Spring Boot 业务服务集成；
- MCP Server 与 Client；
- 混合检索和重排；
- 多 Agent 的 Supervisor/Router 模式；
- PostgreSQL/pgvector 或远程向量库部署配置；
- OpenTelemetry、指标和告警概念；
- 浏览器、代码执行等高风险工具的安全设计。
- Dify 工作流与 LangGraph 的对照选型；
- Docker/Kubernetes 应用侧配置与 vLLM OpenAI-compatible Serving 边界；
- 多模态/OCR 的受控输入流程；
- 一次可验证的开源 Issue、文档 PR 或 Bug 复现。

### 3.3 P2：理解边界即可

- Transformer 数学推导与训练细节；
- SFT、LoRA、RLHF/RFT 的完整训练流程；
- vLLM、CUDA 和 GPU 推理优化；
- Kubernetes 深度运维；
- GraphRAG、大规模知识图谱；
- 所有 Agent 框架的 API 对比。

P2 会提供面试级解释和进一步资料，但不会挤占项目主线。

### 3.4 岗位族与投递边界

主投“AI 应用开发 / Agent 应用开发 / 大模型应用研发”岗位；具备平台化要求时可投 Agent 平台应用侧岗位。明确要求预训练、CUDA、分布式训练或推理引擎内核的算法/Infra 岗不属于本课程的默认目标。

判断依据和 2026-08 西安岗位样本见[面向 2027 招聘的岗位能力再审计](08-面向2027招聘的岗位能力再审计.md)。岗位变化快，2026-11、2027-01 和正式投递周都要重新采样。

## 4. 六条并行学习线

### 4.1 Agent 核心知识线

```text
原生模型 API
  → Structured Output
  → Tool Calling
  → 手写 Agent Loop
  → LangChain Agent
  → RAG
  → LangGraph
  → Memory / Human-in-the-loop
  → MCP / Multi-Agent
```

框架出现之前必须先手写最小实现。这样才能回答：框架解决了什么问题、隐藏了什么状态、失败时从哪里排查。

### 4.2 Python 工程线

```text
类型与数据模型
  → 异步与并发
  → FastAPI / SSE
  → 测试与依赖注入
  → 数据访问
  → 后台任务
  → 稳定性与可观测性
```

Python 不只是模型调用脚本，而是最终应聘的核心工程语言。

新增的 `Redis/Queue/Worker` 不是为了堆中间件：文档摄取、长任务评测和外部同步天然跨越一次 HTTP 请求，必须能处理重复投递、取消、积压和 Worker 崩溃。

### 4.3 企业项目线

每个阶段都修改同一个代码库：

```text
M0 模型网关
M1 设备问答 API
M2 设备工具助手
M3 有引用的维护知识库
M4 可恢复的故障处理工作流
M5 带审批的工单协同 Agent
M6 Java 业务服务与 MCP 集成
M7 可评测、可审计、可交付版本
```

### 4.4 评测与安全线

评测不会等到课程末尾：

- 模型网关阶段：Schema 合规率、错误率、延迟和费用；
- Tool Calling 阶段：工具选择与参数正确率；
- RAG 阶段：检索命中、引用正确性、忠实度和拒答；
- LangGraph 阶段：路径、恢复、重复执行和审批正确性；
- 最终阶段：端到端任务成功率、安全测试和回归结果。

OpenAI 官方文档也把评测、工具边界、批准边界、成本与重试停止条件视为生产 Agent 的重要组成部分。[OpenAI model guidance](https://developers.openai.com/api/docs/guides/latest-model)

### 4.5 计算机基础补给线

每周固定 2 小时，内容与项目同步：

| 项目正在学习 | 同期补给内容 |
| --- | --- |
| HTTP API | TCP/HTTP、状态码、超时、SSE |
| 异步工具调用 | 进程、线程、协程、并发与并行 |
| RAG 数据 | 索引、B+Tree、事务、SQL、向量检索 |
| LangGraph 状态 | 状态机、图、队列、幂等 |
| 缓存与限流 | Redis 思想、TTL、令牌桶 |
| 文档摄取与长任务 | Queue、ACK、至少一次投递、DLQ、Outbox |
| 微服务集成 | REST、鉴权、重试风暴、最终一致性 |
| 稳定性 | 日志、指标、Trace、SLO |
| 部署排障 | Linux 进程、FD、信号、反向代理、容器 Probe |

算法训练以能通过常见工程岗位基础面试为目标，不采用竞赛路线；必须完成 list/dict/set/deque/heap/graph、12 道关联题、10 条主项目 SQL 和两次 EXPLAIN 证据。

### 4.6 面试证据线

每周必须保留一种证据：

- 可运行提交；
- 测试或评测报告；
- 架构决策记录；
- Bug/事故复盘；
- 性能或成本对比；
- 口述题录音提纲；
- 项目演示片段。

最终简历写的是已经证明的结果，而不是“熟悉 LangGraph”。

证据按“已证明/已实践/已理解/未掌握”分级。四年前端经历只证明软件交付与协作，不自动等同于 Python 后端年限；Python、SQL、Queue 和 Agent 能力必须由新项目单独证明。

## 5. Python 与 Java 的边界设计

### 5.1 推荐结论

使用双栈，但不同时起步：

- **Python 是必须完成的 Agent 主线。**
- **Java 是第 21 周加入的企业系统集成增强线。**
- Java 只复用已有 Spring Boot CRUD 能力，不额外展开一套 Java 后端课程。

### 5.2 服务职责

| Python Agent Service | Java Business Service |
| --- | --- |
| 模型网关与供应商切换 | 用户、角色和权限 |
| Prompt / Context | 设备与资产台账 |
| RAG 与向量检索 | 告警与工单 |
| LangChain / LangGraph | 工单状态机与事务 |
| Agent 状态与 Memory | 审批结果与业务规则 |
| Tool 编排与参数验证 | 幂等写入与审计数据 |
| Agent Trace 与 Eval | 对外 REST API |

关键原则：Agent 可以决定“建议调用哪个工具”，但 Java 服务决定“这个业务操作是否合法、是否允许执行、如何保证事务”。

### 5.3 为什么不从第一天使用双栈

如果同时学习 Python、Spring Boot、Agent、RAG 和微服务，最容易出现的问题是每层都能运行，但任何一层都无法深入排障。

前 18 周先让 Python 独立完成闭环；后期再把本地 Python 业务工具替换成远程 Java API。这样能直接比较：

- 本地函数工具与远程 API 工具的区别；
- 网络超时、重试和幂等问题；
- Agent 权限与业务权限的区别；
- 跨服务 Trace 和错误传播；
- AI 服务与存量业务系统如何解耦。

### 5.4 Java 增强线的退出条件

若第 18 周时以下任一项目未达标，暂缓 Java：

- RAG 引用与拒答评测尚未通过；
- LangGraph 中断恢复仍不能独立完成；
- Python API 没有稳定测试；
- API 调用缺少 Usage、成本或异常增长监控；
- 主项目无法端到端演示。

暂缓 Java 不代表项目失败；相同接口先由 Python Adapter 实现，核心能力完成后再替换。

## 6. 模型与费用治理架构

### 6.1 供应商策略

- 千问：日常默认、Embedding 与主要 Tool Calling 实验；
- DeepSeek：复杂任务对照、推理行为比较与少量基准测试；
- 模型名称通过配置注入，不写死在业务代码；
- 业务层只依赖内部 `ModelGateway` 接口。

千问官方提供 OpenAI-compatible API 与 Function Calling；DeepSeek 官方也提供兼容调用方式和 Tool Calls。这使统一网关成为可行方案。[千问 Function Calling](https://help.aliyun.com/zh/model-studio/qwen-function-calling)、[DeepSeek API](https://api-docs.deepseek.com/)、[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)

### 6.2 调用与成本治理

每次执行都生成 Usage Record：

```text
request_id
provider
model
input_tokens
output_tokens
latency_ms
estimated_cost
tool_steps
retry_count
success
```

治理策略：

1. 不设置月度金额硬上限；按模型、任务、环境记录并分析 Usage 与实际/估算费用。
2. 模型选择以质量、延迟和单位任务成本对照实验为依据，不因教程预算排除强模型。
3. 单次 Agent 最大步骤默认 6，超限返回结构化失败，防止失控循环。
4. RAG 摄取与检索测试独立于生成模型，便于分层定位质量。
5. 普通 CI 使用 Fake、Stub、Golden File 和录制回放，以保证确定性；真实模型在评测工作流中充分运行。
6. 规则评测、人工评测和 LLM-as-a-Judge 分工使用，避免单一评测器偏差。

模型价格会变化，因此教程讲 Usage、单位任务成本和异常增长分析，不长期写死单价，也不以累计金额限制学习范围。

## 7. 无 Docker 的双配置策略

### 7.1 本地学习配置

- Python：`uv` + `.venv`；
- 业务数据：SQLite；
- 向量数据：轻量嵌入式向量库；
- Java：H2；
- 模型：远程 API；
- 缓存：进程内 TTL Cache；
- Trace：LangSmith + 本地 JSON 备份；
- 启动：命令行脚本，不依赖容器。

### 7.2 企业部署配置

- PostgreSQL/MySQL；
- pgvector 或独立向量服务；
- Redis；
- Secret Manager/KMS 概念；
- 容器镜像、健康检查和滚动升级配置；
- 集中日志、Trace、指标和告警。

企业配置会提供设计和配置样例，但不要求在低配置电脑上完整运行。Dockerfile 由 CI 构建验证，不把“本地没有 Docker”误解为“不学容器化”。

## 8. 教程文章模板

每篇长教程固定包含：

1. 与岗位和企业项目的关系；
2. 学习目标、预计时间与完成标准；
3. 问题场景；
4. 核心原理与必要底层知识；
5. 从最小实现到工程实现；
6. 代码结构与关键代码解析；
7. 正常路径、异常路径和攻击路径；
8. 测试、评测、成本与日志；
9. 常见错误和调试顺序；
10. 项目增量任务；
11. 练习题；
12. 紧随题目的答案与解释；
13. 面试追问和参考回答框架；

答案紧随练习，但建议先折叠或滚动到不可见位置独立完成，再对照答案。

## 9. 阶段验收门

| 阶段 | 进入下一阶段前必须通过 |
| --- | --- |
| Python | 能独立写异步 API、错误处理和测试 |
| LLM 基础 | 能手写 Tool Calling Loop，并验证参数 |
| LangChain | 能解释框架状态、工具与中间件，不依赖复制代码 |
| RAG | 有检索与生成分层评测，有引用和拒答 |
| LangGraph | 能暂停、恢复、重放并避免重复副作用 |
| Eval/Safety | 有固定数据集、回归结果和攻击样例 |
| Java/MCP | 跨服务工具调用具备鉴权、超时、幂等和审批 |
| 最终项目 | 可从空环境启动、可演示、可测试、可说明指标与权衡 |

未通过验收门时，允许延后增强项，不允许用增加新框架掩盖基础缺口。

## 10. 课程成功标准

2027 年 2 月 14 日时，至少应具备：

- 一个可运行的企业级 Agent 项目；
- 30 个以上核心单元/集成测试；
- 一套至少 30 条的 Agent/RAG 评测数据；
- 一份包含质量、延迟、成本和安全结果的评测报告；
- 5 份以上重要架构决策记录；
- 3 份真实失败复盘；
- 一份完整 README 和部署说明；
- 一段 5～8 分钟项目演示；
- 一套可口述的项目深挖与 Agent 系统设计答案。

这些是初始下限，会根据实际项目推进调整，但不会以文件数量代替真正的工程质量。
