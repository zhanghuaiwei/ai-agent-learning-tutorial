# 超时、重试、限流、熔断、缓存与降级

> 预计 8 小时｜产出：依赖故障时仍有确定行为的 Resilience 层。

> **阅读前置**：本阶段第 2～3 章。前置要求：第 4 阶段的执行边界（步数/Token/Deadline/循环检测）与 SSE 终态、第 6 章的六类 Runbook、第 5 阶段的 `E_*` 错误码。本章把这些机制收口为一张可测试的依赖策略表。

## 1. 本章从哪里开始

Agent 与普通接口最大的不同是：一次运行会同时依赖模型、检索、业务工具、数据库。任何一个慢，都可能让整条链路级联超时。第 3 章的 DoS 红队用例已经暴露了问题——循环调用与重试风暴会让防护形同虚设。本章用六个机制（超时、重试、限流、熔断、缓存、降级）保证：**依赖故障时，系统仍有确定行为，且不会把故障放大**。

## 2. 本章完成标准（通过门槛）

- 有一张依赖策略表：每个依赖的超时、可重试码、重试次数、熔断阈值、缓存 TTL、降级结果；
- 重试有单一所有者，网关/Graph/SDK 不各自重试三次，总尝试次数可统计；
- 熔断半开探测可恢复，限流按租户/用户/Tool/Provider 分维度；
- 缓存 Key 包含租户、权限与数据版本，降级不改变安全语义；
- 用 Fake Clock 和故障注入测试，不靠真实等待。

## 3. 时间预算

从用户总 SLO 反推：例如总时限 20 秒，模型 10 秒、检索 3 秒、业务工具 3 秒、编排与输出留余量。嵌套调用的子超时总和不能无限超过父期限，**传递绝对 Deadline 比层层固定超时更可靠**：

```python
from __future__ import annotations
from dataclasses import dataclass
from datetime import datetime, timedelta

@dataclass(frozen=True)
class Deadline:
    at: datetime

    def remaining(self) -> float:
        return max(0.0, (self.at - datetime.now()).total_seconds())

    def child(self, budget_seconds: float) -> "Deadline":
        return Deadline(at=min(self.at, datetime.now() + timedelta(seconds=budget_seconds)))
```

一次 Agent 运行在入口建立 Deadline，往下游传播的是绝对时刻，而不是「再给 3 秒」的相对值——后者会在多层嵌套里被叠加放大。

## 4. 五类机制

| 机制 | 原则 | 反面例子 |
| --- | --- | --- |
| 重试 | 只对瞬时、可重放失败；指数退避 + 抖动 + 上限 | 对写操作盲目重试造成重复工单 |
| 限流 | 按租户、用户、Tool、Provider 控制速率和并发 | 一个长 Agent 吃掉全局配额 |
| 熔断 | 连续失败快速失败，半开探测恢复 | 把熔断当重试替代品 |
| 缓存 | 只缓存允许、稳定、带版本和权限作用域的数据 | 缓存跨租户最终答案 |
| 降级 | 失败退混合检索；模型失败返回证据/草稿 | 业务写失败伪装成功 |

### 4.1 重试与退避

```python
import asyncio, random

async def call_with_retry(fn, *, retryable, max_attempts=3, base=0.2):
    attempt = 0
    while True:
        attempt += 1
        try:
            return await fn()
        except AppError as e:
            if e.code not in retryable or attempt >= max_attempts:
                raise
            delay = base * (2 ** (attempt - 1)) + random.uniform(0, 0.1)
            await asyncio.sleep(delay)
```

只对 `E_UPSTREAM_TIMEOUT` 这类瞬时、可重放错误重试；`E_FORBIDDEN`、`E_INVALID_ARGUMENT` 重试没有意义，还会放大安全拒绝。

### 4.2 熔断与半开

连续失败超过阈值 → 熔断打开，快速失败；经过冷却期后进入半开，允许少量探测；成功则关闭，失败则重新打开。熔断解决的是「别再给坏掉的依赖加压」，不是重试的替代品。

### 4.3 缓存的安全 Key

缓存 RAG 最终答案风险高；更安全的起点是缓存 Embedding 或公开只读查询。任何缓存 Key 都要纳入租户与权限：

```python
cache_key = f"{tenant_id}:{scope_hash}:{data_version}:{normalized_query_hash}"
```

缺任何一个维度都可能在多租户间串数据。

### 4.4 降级的语义

降级必须可见且不改变安全语义：检索失败退混合检索；模型失败返回证据或草稿并标注「非实时」；业务写失败**不可伪装成功**。

## 5. 防止重试风暴

网关、Graph、SDK 若各自重试三次，最坏会放大到 27 次。必须建立**单一重试所有者**并统计总尝试次数：

```text
重试所有者：网关层（唯一）
Graph/SDK：不重试，只上抛
每次调用记录 attempt + retry_count
总尝试次数有上限并进入 Trace
```

重试所有权是面试高频点，也是线上最容易被忽略的级联放大来源。

## 8. 常见错误与诊断顺序

### 8.1 层层固定超时叠加

症状：嵌套调用总时长远超用户 SLO。诊断顺序：确认是否传递绝对 Deadline，而不是每层各自加固定超时。

### 8.2 对写操作盲目重试

症状：上游成功但响应丢失，重试导致重复工单。诊断顺序：确认写操作是否走幂等键 + 结果查询，重试只对可重放读操作。

### 8.3 熔断后返回旧告警未标注

症状：用户拿到过期数据却不自知。诊断顺序：确认降级结果是否明确标注数据时间与「非实时」，高风险判断是否拒答或转人工。

## 9. 练习题与答案

### 练习 1：缓存 RAG 最终答案安全吗？

**答案：**需把租户、权限、文档/Prompt/模型版本纳入 Key，并考虑敏感性与过期；更安全的起点是缓存 Embedding 或公开只读查询。

### 练习 2：熔断打开后返回旧告警可以吗？

**答案：**只有业务允许且明确标注数据时间与「非实时」；高风险判断应拒答或转人工。

### 练习 3：为什么写操作不能简单重试？

**答案：**上游可能已提交但响应丢失，重试会造成重复工单。写操作靠幂等键 + 结果查询恢复，而非盲目再次创建。

## 11. 面试追问

### 11.1 网关、Graph、SDK 各自重试会怎样？

回答框架：重试次数成倍放大，最坏形成重试风暴拖垮下游。必须建立单一重试所有者，SDK/Graph 只上抛，总尝试次数进 Trace 并设上限。

### 11.2 熔断和重试的区别？

回答框架：重试针对瞬时故障，用退避换取成功；熔断针对持续故障，快速失败避免继续加压。熔断打开后靠半开探测恢复，不是重试的替代品。
