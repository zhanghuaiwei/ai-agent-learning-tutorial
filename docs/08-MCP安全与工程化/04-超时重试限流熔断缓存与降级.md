# 超时、重试、限流、熔断、缓存与降级

> 预计 8 小时｜产出：依赖故障时仍有确定行为的 Resilience 层。

## 1. 时间预算

从用户总 SLO 反推：例如总时限 20 秒，模型 10 秒、检索 3 秒、业务工具 3 秒、编排与输出留余量。嵌套调用的子超时总和不能无限超过父期限，传递绝对 Deadline 比层层固定超时更可靠。

## 2. 五类机制

- 重试：只对瞬时、可重放失败，指数退避 + 抖动 + 上限。
- 限流：按租户、用户、Tool、Provider 控制速率和并发。
- 熔断：连续失败时快速失败，半开探测恢复；不是重试替代品。
- 缓存：只缓存允许、稳定、带版本和权限作用域的数据。
- 降级：重排失败退混合检索；模型失败返回证据/草稿；业务写失败不可伪装成功。

防止重试风暴：网关、Graph、SDK 不能各自重试三次。建立单一重试所有者并统计总尝试次数。

## 3. 项目任务

定义依赖策略表：超时、可重试码、次数、熔断阈值、缓存 TTL、降级结果。用 Fake Clock 和故障注入测试，禁止靠真实等待。

## 4. 练习与答案

### 练习 1：缓存 RAG 最终答案安全吗？

**答案：**需把租户、权限、文档/Prompt/模型版本纳入 Key，并考虑敏感性与过期；更安全的起点是缓存 Embedding 或公开只读查询。

### 练习 2：熔断打开后返回旧告警可以吗？

**答案：**只有业务允许且明确标注数据时间与“非实时”；高风险判断应拒答或转人工。

## 5. 验收与资料

故障无级联放大，降级可见且不改变安全语义。参考 [AWS Retry with backoff](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/retry-backoff.html)、[Microsoft Circuit Breaker](https://learn.microsoft.com/azure/architecture/patterns/circuit-breaker)。
