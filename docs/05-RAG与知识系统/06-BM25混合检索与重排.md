# BM25、混合检索与重排

> 预计 7 小时｜产出：能同时找准故障码与自然语言语义的检索管道。

> **阅读前置**：承接第 5 章的单路向量检索，本章引入 BM25 关键词检索、RRF 融合与重排。前置要求：第 5 章的 `RetrievalResult` 与硬过滤管线；第 4 章的向量索引抽象；M3 验收给出的 `reciprocal_rank_fusion` 实现（本章直接复用其口径）。需要能跑出纯向量与纯 BM25 两个候选列表，重排器可用规则或本地 Cross-Encoder 模拟。

## 1. 本章从哪里开始

第 5 章的单路向量检索对自然语言问句有效，但对精确符号无能为力：用户问“故障码 E_OVERHEAT_7 怎么处理”，向量检索可能召回一堆“过热”相关但无关型号的段落，而漏掉包含精确故障码的那段。反过来，纯关键词/BM25 擅长精确型号、错误码、零件号，却不懂“泵体抖得厉害”和“振动超限”是同一件事。

本章偿还的债是：**把向量和关键词两条召回路融合起来，让精确符号与语义近似同时被命中，并在融合后用重排把有限的高质量候选送进 Context**。这是第 5 章管线从“单路”到“多路”的自然升级，也是 M3 验收“关键词 + 向量 + RRF，可选重排与降级”的核心实现章。

## 2. 本章完成标准（通过门槛）

必须同时满足：

- 实现关键词/BM25 与向量两路召回，理解二者分数尺度不同、不可直接相加；
- 实现 RRF 融合（`1 / (k + rank)`，`k` 建议 60），按排名而非原始分数融合；
- 实现可选重排：Cross-Encoder 或 LLM Reranker 只处理融合后有限候选（如 Top 20），再取前 4～8 条；
- 实现去重与多样性：按内容 Hash 去重、限制单文档候选数，重排前不丢 ACL 元数据；
- 比较纯 BM25、纯 Dense、RRF、RRF + Reranker 四组 Baseline 的 `Recall@5`、MRR、P95 与费用；
- 重排失败可降级到融合排序，并记录降级。

## 3. 为什么混合，以及为什么不能直接相加

向量检索与 BM25 的分数量纲、分布完全不同：余弦相似度通常落在 `[-1, 1]`（归一化后 `[0, 1]`），BM25 分数可以无上界且随文档长度、词频剧烈变化。直接相加会被任意缩放主导，结果不稳定。

**Reciprocal Rank Fusion（RRF）** 只依赖排名，不依赖分数大小：

```python
from collections import defaultdict


def reciprocal_rank_fusion(
    ranked_lists: list[list[str]],
    *,
    rank_constant: int = 60,
) -> list[tuple[str, float]]:
    scores: dict[str, float] = defaultdict(float)
    for ranked_ids in ranked_lists:
        for rank, chunk_id in enumerate(ranked_ids, start=1):
            scores[chunk_id] += 1 / (rank_constant + rank)
    return sorted(scores.items(), key=lambda item: item[1], reverse=True)
```

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

`rank_constant` 通常取 60（与 M3 验收一致）。RRF 的优点：无需调参融合权重、对不同分数尺度鲁棒；代价：放弃了原始分数里的“置信度”信息，排名越靠前优势被压缩。工程上先用 RRF 建基线，确有需要再在验证集上学习加权融合。

## 4. 两路召回与融合

两路并行召回，各自带硬过滤，再融合：

```python
async def hybrid_retrieve(query: RetrievalQuery, principal: Principal) -> RetrievalResult:
    filt = build_filter(query, principal)
    dense_ids = await vector_store.query_ids(query.text, top_k=query.top_k, filter=filt)
    bm25_ids = await bm25_index.query_ids(query.normalized, top_k=query.top_k, filter=filt)
    fused = reciprocal_rank_fusion([dense_ids, bm25_ids])
    # 去重 + 单文档候选数限制 + 保留 ACL 元数据
    candidates = dedupe_and_diversify(fused, max_per_doc=2)
    return RetrievalResult(
        evidences=[to_evidence(c) for c in candidates[: query.top_k]],
        index_version=..., query_version=...,
    )
```

`bm25_index` 与向量索引共享同一批 Chunk（`chunk_id` 相同），因此融合按 `chunk_id` 对齐。注意：**BM25 索引也需要 `tenant_id + allowed_doc_ids` 过滤**，不能只给向量路加过滤——否则关键词路会把越权 Chunk 带进融合。

## 5. 重排：只处理有限候选

RRF 融合后的 Top 20 进入重排，再取 Top 4～8 进 Context。重排器两类：

| 类型 | 实现 | 特点 |
| --- | --- | --- |
| Cross-Encoder | 双塔之外的交叉编码器，同时输入 query + doc 打分 | 精度高，需逐对推理，成本随候选数线性增长 |
| LLM Reranker | 用 LLM 对候选打分/排序 | 更灵活，可读理由，成本更高、延迟更大 |

重排的代价约束：

1. **只处理有限候选**（Top 20），不对全库重排；
2. **缓存 + 超时降级**：重排器失败时回退到 RRF 融合排序，记录降级原因；
3. 重排前**不丢 ACL 元数据**——`tenant_id/acl` 随候选一路保留，重排只是换排序，不改变权限边界。

## 6. 去重与多样性

同一文档的相邻 Chunk 常霸榜（第 3 章 overlap 的副作用）。去重与多样性策略：

```text
1. 按 content_hash 去重（完全相同的 Chunk 只保留一条）
2. 限制单文档候选数（如 max_per_doc=2），防止一本文档垄断 Top-K
3. 保留覆盖多个故障假设的证据，避免只留同义重复
```

多样性不是越多越好：过度分散会稀释最相关证据。用证据集上的 Recall 与回答忠实度来校准 `max_per_doc`。

## 7. 四组 Baseline 对照

本章项目任务必须出四组对照，而不是只交“混合+重排”一个数字：

| Baseline | 构成 | 回答的问题 |
| --- | --- | --- |
| BM25 | 纯关键词 | 精确符号的召回上限 |
| Dense | 纯向量 | 语义近似的召回上限 |
| RRF | BM25 + Dense 融合 | 融合是否优于单路 |
| RRF + Reranker | 融合 + 重排 | 重排是否有稳定收益 |

指标用 `Recall@5`、MRR、P95 延迟、费用四维。M3 验收的判断标准很明确：**若重排没有稳定改善 Recall/MRR/引用或业务成功率，就不保留额外复杂度**。混合检索的价值要由数据证明，而不是“上了就高级”。

## 9. 常见错误与诊断顺序

### 9.1 直接相加 BM25 与余弦分数

现象：融合结果被某一路的分数尺度主导。先确认融合是否用 RRF 排名而非原始分数相加。**不要**手工拍一个“0.7 * 向量 + 0.3 * BM25”的权重就上线——那是把任意缩放引入了结果。

### 9.2 重排器失败导致整次问答失败

现象：重排超时，整个请求报错。先查是否有降级到 RRF 融合的路径、是否记录了降级。**不要**把重排做成单点故障。

### 9.3 BM25 路漏过滤导致越权

现象：越权 Chunk 通过关键词路进入候选。先查 BM25 索引是否与向量路共享同一套 `tenant_id + allowed_doc_ids` 过滤。**不要**只给向量路加过滤。

### 9.4 重排前丢了 ACL 元数据

现象：重排结果里混入无权 Chunk。先查候选在融合/重排过程中是否保留了 `tenant_id/acl` 元数据，再查重排器是否只返回 ID 而丢了元数据。

## 10. 练习题与答案

### 练习 1：为何不能直接相加 BM25 分数和余弦分数？

**答案：**量纲与分布不同，结果受任意缩放影响；RRF 用排名融合更稳健，或在验证集上学习归一化。

### 练习 2：重排器失败是否整次问答失败？

**答案：**通常可降级到融合排序，但必须记录降级，并对高风险问题更保守地拒答。重排不应成为单点故障。

### 练习 3：BM25 索引为什么也要做租户/ACL 过滤？

**答案：**两路召回共享同一批 Chunk，若关键词路不过滤，越权 Chunk 会被带进融合与重排，扩大泄漏面。每条召回路都要注入可信身份过滤。

### 练习 4：重排有必要对全库做吗？

**答案：**不必。只对融合后有限候选（Top 20）重排，再取前 4～8 条。对全库重排成本与延迟不可控。
