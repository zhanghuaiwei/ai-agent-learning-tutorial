# RAG 系统全景与失败分类

> 预计 5 小时｜目标：把 RAG 视为可分层评测的数据系统，而不是“向量库 + Prompt”。

> **阅读前置**：本章是第 5 阶段（RAG 与知识系统）的入口章。前置要求：M2 已通过（第 4 阶段第 7 章），即 `search_manual` 已经只返回精简片段 + `evidence_ids`，不再把整本手册塞进 Prompt；Pydantic 契约已在 `schemas.py` 固定（`ToolResult`、`AgentAnswer`、`CitationSource`）。若 `search_manual` 仍在返回上万字正文，请先回补 M2 关键闸门，再进入本章。

## 1. 本章从哪里开始

第 4 阶段结束时，智维 Agent 已经能选择工具、按角色暴露工具、把结构化输出收敛成 `AgentAnswer(status, answer, evidence_ids)`。但它留下一个被 M2 验收刻意点名的债：**`search_manual` 的“知识”仍是硬编码的内存假数据，或整段手册文本**。一旦手册变成 300 页、跨多个设备型号、多个租户，这种“把全文塞给模型”的做法会立刻崩掉——Token 爆炸、答错找不到根因、无法证明答案来自哪里。

本章进入第 5 阶段，要建立的第一件事不是写向量库，而是建立一套**分层视角**：RAG 是一条从“文档接入”到“引用可核验回答”的流水线，每一层都可能失败，且每一层都要能独立评测。没有这套视角，后面 7 章的调参都是盲人摸象。

## 2. 本章完成标准（通过门槛）

必须同时满足：

- 能画出 RAG 全链路数据流，并为每一层标注“谁拥有这份数据、谁可以读”；
- 能独立说出七类失败（接入 / 索引 / 召回 / 排序 / 组装 / 生成 / 产品）各对应哪一层，并给出定位顺序；
- 能说清 2-step RAG、Agentic RAG、Hybrid 三者的差异与取舍；
- 准备 20～30 份可公开使用的维护文档，建立 50 条问题及标准证据 ID 的数据集雏形；
- 能把 M2 的 `search_manual` 与 M3 的 `Retriever` 契约对应起来，明确二者演进关系。

## 3. 全链路：一条流水线，七个可失败层

把 RAG 拆成两端：**离线摄取端**（写入知识）和**在线查询端**（消费知识）。两端共享同一套 Chunk / 元数据 / 向量存储。

```text
离线摄取端（写）                        在线查询端（读）
文档接入 → 解析/清洗 → 切分           用户问题 → 查询理解 → 召回
  → 元数据/权限 → Embedding/索引          → 过滤/融合 → 重排 → Context 组装
                                          → 模型回答 → 引用校验 → 拒答/输出
                                              ↘ 反馈与评测 ← 两端都要记录版本
```

离线端和在线端不是两套代码，而是**同一条流水线的两个方向**：离线端产出的 Chunk 元数据（`tenant_id`、ACL、`fault_codes`、`heading_path`）直接决定在线端能否正确过滤和引用。很多“检索质量差”的根因在离线端——切分把警告和操作割裂、元数据漏了权限字段——却常常被误判为“向量模型不行”。

## 4. 三种架构：先定检索的“自由度”

| 架构 | 检索方式 | 延迟特征 | 适用场景 | 主要风险 |
| --- | --- | --- | --- | --- |
| 2-step RAG | 固定先检索、后生成，检索一次 | 可预测、低 | 知识问答路径固定，重延迟 | 复杂多跳问题召回不足 |
| Agentic RAG | 由 Agent 决定是否/何时/如何检索，可多次 | 波动大、高 | 需要动态多次检索或调用工具 | 循环、成本、根因难定位 |
| Hybrid | 查询改写与检索编排确定化，少量动态工具 | 中等、较可预测 | 大多数生产系统 | 编排复杂度上升 |

本教程主线（智维 Agent）先做 **2-step RAG**：检索层确定性返回 `RetrievalResult`，生成层确定性输出 `RagAnswer`，中间不引入自由循环。原因在 M3 验收写得很直白：**RAG 本身不稳定时，多节点只会让根因更难定位**。等第 6 阶段进入 LangGraph，再把检索子图挂进图工作流，那时“是否多检索一次”才由状态机而非模型临时起意决定。

## 5. 七类失败与定位顺序

失败分类是本章的核心产出。先把现象归到正确的一层，再谈调参：

| 失败类别 | 对应层 | 典型现象 | 先检查 |
| --- | --- | --- | --- |
| 接入失败 | 解析/清洗 | 扫描 PDF 文字缺失、表格错位、页眉混入 | 解析器、原文件、金样对照 |
| 索引失败 | 切分/元数据 | 切分丢语义、权限串租户、版本错 | Chunk 元数据、稳定 ID、ACL |
| 召回失败 | 向量/关键词召回 | 正确片段根本没进候选集 | Query、Chunk、Embedding、BM25 |
| 排序失败 | 融合/重排 | 召回了但排不到前面 | 融合算法、重排器、分数尺度 |
| 组装失败 | Context 组装 | 重复、超长、来源不清、预算挤掉关键证据 | 去重、Token 分配、证据预算 |
| 生成失败 | 生成层 | 证据足够却答错、伪造引用 | Prompt、Structured Output、引用校验 |
| 产品失败 | 拒答/产品策略 | 问题超出知识范围却不拒答 | 证据门槛、拒答码、评测集 |

定位顺序用一条铁律兜底：**从上游往下游查，不要一上来换大模型**。标准证据不存在 → 查接入/版本/ACL；证据存在但未召回 → 查 Query/Chunk/Embedding/BM25；已召回未进 Context → 查去重/重排/Token 分配；Context 正确但答错 → 查 Prompt/引用校验。这条顺序会在第 8 章评测中变成可脚本化的断言。

## 6. 数据所有权：为什么“向量库”不是全部

RAG 不是“把文档向量化存进库里”就结束了。真正要回答的是**每一份数据由谁拥有、谁能读、删除时怎么溯源**：

| 数据 | 拥有者 | 谁能读 | 删除方式 |
| --- | --- | --- | --- |
| 原文件 | 租户（上传方） | 该租户 + 运维 | 对象存储删除 + 索引同步 |
| 解析正文 | 接入管道 | 该租户 | 随文档版本删除 |
| Chunk | 索引 | 该租户（按 ACL） | 向量 + BM25 一起删 |
| Embedding | 索引版本 | 不单独暴露 | 随索引版本切换/删除 |
| 查询日志 | 平台 | 脱敏后分析 | 保留期 + 访问控制 |

“幽灵知识”是所有权设计失败的典型：原文档删了，但 Chunk、向量、缓存里的旧知识仍能被检索到。数据所有权的边界不清，权限与删除就无法闭环。这也是第 2 章“增量与删除”、第 8 章“文档注入收口”都要回到的主线问题。

## 7. 与主线契约的映射

M2 的 `search_manual` 返回 `ManualSnippet`（精简片段），M3 的 `Retriever` 返回 `RetrievalResult`（含 `Evidence` 列表）。二者是同一条知识线的两次抽象：

```python
# M3 契约（第 5 阶段第 9 章验收定义，这里只预告骨架）
class RetrievalQuery(BaseModel):
    text: str
    tenant_id: str
    allowed_doc_ids: frozenset[str]
    top_k: int = Field(default=20, ge=1, le=50)

class Evidence(BaseModel):
    chunk_id: str
    document_id: str
    document_version: str
    title: str
    locator: str
    text: str
    score: float

class Retriever(Protocol):
    async def search(self, query: RetrievalQuery) -> RetrievalResult: ...
```

注意两点：`tenant_id` / `allowed_doc_ids` 来自可信 Principal 和 ACL 服务，**不从用户 Prompt 抽取**；`Evidence.chunk_id` 是稳定 ID，为后续“引用可核验、评测可对齐”服务。本章先把这个方向定下来，后续章节逐层填实现。

## 9. 常见错误与诊断顺序

### 9.1 把“向量库 + Prompt”当 RAG 全部

只搭一个向量库 + 把 Top-K 拼进 Prompt，是 Demo 不是系统。缺了切分元数据、权限过滤、引用校验、评测，一旦答错你无法定位是召回了错片段还是模型幻觉。诊断顺序：先确认是否有一条完整流水线和分层指标，再谈优化。

### 9.2 回答错误就换 Embedding 模型

这是最常见的错误归因。回答错可能出在解析、切分、权限过滤、重排、Context 或生成任何一层。先按 §5 定位到层，再决定是否动模型。

### 9.3 一上来就上 Agentic RAG

Agentic RAG 带来灵活性的同时也带来循环、延迟和成本不可控。先用 2-step 建立可评测基线，确有“需要多次检索/调用工具”的证据再升级。

### 9.4 数据集只有“成功样本”

如果 50 条问题全是“能答对的”，评测就没有区分度。无答案、冲突版本、跨租户、注入这些负向样本必须从一开始就进数据集，否则后面 7 章无法验证安全边界。

## 10. 练习题与答案

### 练习 1：回答错误就说明 Embedding 不好吗？

**答案：**不一定。可能是解析、切分、权限过滤、重排、Context 或生成问题。必须按失败分类定位到层，看每层指标和 Trace，而不是直接归因于向量模型。

### 练习 2：何时优先 2-step RAG，何时引入 Agentic RAG？

**答案：**知识问答路径固定、重视延迟和可预测性时用 2-step；只有确需动态多次检索或调用其他工具，且能承受循环与成本风险时才引入 Agentic RAG。多数生产系统用 Hybrid（确定化编排 + 少量动态工具）折中。

### 练习 3：`tenant_id` 应该从用户 Prompt 里抽取吗？

**答案：**不能。租户与 ACL 来自可信 Principal 和 ACL 服务，由代码注入，模型提供的 `tenant_id` 一律视为不可信数据。否则一个“我是 tenant-b”的注入就能跨租户读知识。

### 练习 4：删除原始文档后，为什么仍可能检索到旧知识？

**答案：**因为 Chunk、向量、BM25 索引、缓存里还留着派生数据。删除必须沿着数据血缘同步清理所有派生对象，这正是数据所有权要预先定义的原因。
