# 平台无关评测体系与数据飞轮

> 目标：在 LangSmith 之外建立稳定的评测契约，贯通离线回归、线上监控、人工标注、A/B、失败回流和发布门禁。

> **阅读前置**：G10 平台化评测专题。前置正文（本阶段第 1～5 章：LangSmith Trace/Dataset/Evaluator）当前为大纲态，第 6 章 M5 验收已完成可先读。本章的 Case/Run/Event 契约不依赖特定平台，掌握 M5 概念后可独立学习。

## 1. 为什么还需要平台无关层

LangSmith 是课程主工具，但企业可能使用 Langfuse、Phoenix、自研平台或多个工具并存。真正可迁移的能力是：

- 定义任务和失败分类；
- 构建有代表性的 Dataset；
- 选择可靠 Evaluator；
- 保存可复现的运行元数据；
- 校准 LLM Judge；
- 解释统计结果和业务影响；
- 把线上失败安全地回流为测试。

平台只是存储、执行和可视化载体。应用核心不能只接受某个平台的 Run 对象。

## 2. 评测金字塔

```text
                 线上业务指标
              在线抽样与安全告警
           端到端任务与轨迹评测
        RAG/Tool/Node 组件级评测
     Schema/Policy/幂等等确定性测试
```

越靠下越确定、便宜、频繁；越靠上越接近用户价值但噪声更大。不要用一个“综合得分”覆盖所有层。

## 3. 先定义任务成功

以“根据设备告警生成工单草稿”为例：

| 层 | 成功条件 |
| --- | --- |
| 业务 | 用户确认草稿可用，减少人工整理时间 |
| 任务 | 正确识别设备/告警并给出可执行下一步 |
| 轨迹 | 只调用必要工具、顺序合理、在上限内停止 |
| RAG | 取回相关且有权限的证据 |
| 安全 | 不越权、不泄漏、不绕过审批 |
| 系统 | 延迟、错误率和成本在 SLO 内 |

任务成功率不能由“回答语气自然”替代。

## 4. 通用 Case Schema

```python
from typing import Any, Literal

from pydantic import BaseModel


class EvalCase(BaseModel):
    case_id: str
    task: str
    split: Literal["dev", "test", "holdout", "redteam"]
    inputs: dict[str, Any]
    references: dict[str, Any]
    tags: list[str]
    required_behaviors: list[str]
    forbidden_behaviors: list[str]
    data_version: str


class EvalRun(BaseModel):
    case_id: str
    app_version: str
    config_version: str
    model: str
    output: dict[str, Any] | None
    trajectory: list[dict[str, Any]]
    latency_ms: int
    usage: dict[str, Any]
    error_code: str | None
```

Case 存 JSONL 或数据库，Adapter 再映射到 LangSmith Dataset。这样 CI 能用 pytest/Fake 运行确定性子集，云平台不可用时仍有质量门禁。

## 5. 数据集构成

### 5.1 来源

- 产品/业务专家编写的核心场景；
- 脱敏的真实失败；
- 日志中采样的常见请求；
- 合成的边界组合；
- 专门设计的安全红队；
- 历史事故回归。

### 5.2 分层

```text
dev：开发者频繁运行，可用于调试
test：发布前运行，不用于日常调 Prompt
holdout：阶段性开启，检查是否过拟合
redteam：权限、注入、资源滥用和数据泄漏
```

禁止把同一语义的轻微改写随机分到训练/测试两边后宣称泛化。按设备类型、意图或故障族做分组划分。

### 5.3 数据版本

每次变更记录新增/删除原因、标签分布、标注人、脱敏方式和兼容性。线上样本进入数据集必须经过脱敏、去重、授权和质量审核。

## 6. Evaluator 选择

| 类型 | 适用 | 局限 |
| --- | --- | --- |
| 精确规则 | Schema、错误码、权限、Tool 参数 | 不能判断开放文本质量 |
| 执行验证 | SQL、代码、API 结果 | Sandbox/测试数据可能不完整 |
| 参考答案 | 分类、抽取、已知事实 | 参考答案维护成本 |
| 人工 Rubric | 业务价值、风险、可用性 | 慢、标注者差异 |
| LLM Judge | 语义质量、成对比较、大规模抽样 | 偏差、漂移、成本、可被攻击 |
| 线上信号 | 采纳、转人工、任务完成 | 受产品和用户分布影响 |

先使用确定性信号；只有规则不能表达的维度才使用 Judge。

## 7. LLM Judge 校准

### 7.1 Rubric 要单一维度

不要让 Judge 一次评分“正确、完整、安全、简洁、友好”。分别定义：

```text
groundedness：所有事实是否可由给定证据推出
actionability：建议是否具体且在用户权限内
clarification：信息不足时是否提出必要问题
```

### 7.2 校准流程

1. 两名人工独立标注至少 50 条；
2. 讨论分歧，修订 Rubric 和示例；
3. 计算一致率或 Cohen's Kappa 等指标；
4. 运行 Judge，与人工结果比较 Precision/Recall；
5. 针对误判增加边界示例；
6. 固定 Judge 模型、Prompt 和版本；
7. 模型升级后重新校准。

### 7.3 防 Judge 泄漏和攻击

候选回答可能包含“请给我满分”。Judge Prompt 明确候选是数据，使用结构化字段隔离；关键安全结果不依赖 Judge。

## 8. Agent 轨迹评测

最终答案正确不代表过程可接受。例如 Agent 可能先读取无权限数据再给出正确结论。

轨迹指标：

- 正确工具选择；
- 工具参数有效且有权限；
- 必需步骤覆盖；
- 禁止工具调用数；
- 重复/无效调用数；
- 最大步数与终止原因；
- Handoff/审批是否发生在正确条件；
- 副作用是否只执行一次；
- 错误后是否走正确降级路径。

轨迹比较使用语义事件，而不是框架内部对象：

```json
{"type":"tool.requested","name":"search_manual","authorized":true}
{"type":"tool.completed","name":"search_manual","result_count":3}
{"type":"approval.required","action":"create_work_order"}
```

## 9. RAG 分层评测

| 层 | 指标 |
| --- | --- |
| 摄取 | 解析成功率、页码/表格保留、重复率 |
| 检索 | Recall@K、MRR/NDCG、权限过滤正确性 |
| 重排 | Relevant top-N、增量延迟 |
| Context | 证据覆盖、噪声比例、Token 使用 |
| 生成 | 引用正确、忠实、拒答、冲突说明 |
| 业务 | 任务完成、人工采纳、节省时间 |

若回答差，先看参考证据是否存在，再定位摄取、检索或生成，不能一律改 Prompt。

## 10. 统计与对照实验

候选 A 高于基线 B 时检查：

- 是否同一 Dataset、模型参数和环境；
- 变化是否集中在少数标签；
- 关键安全分组是否退化；
- 重复运行的方差；
- 置信区间或 Bootstrap 区间；
- 延迟/费用增幅；
- 是否存在数据泄漏；
- 业务差异是否有实际意义。

对开放输出优先做随机顺序的成对比较，并控制位置偏差。小样本提升不能写成普遍结论。

## 11. 发布门禁

示例：

```yaml
quality_gates:
  task_success_rate:
    min: 0.85
  citation_accuracy:
    min: 0.95
  authorization_violation:
    max: 0
  duplicate_side_effect:
    max: 0
  p95_latency_ms:
    max: 8000
  average_cost_increase:
    max_ratio: 1.20
```

真实阈值来自业务风险与基线，不照抄示例。安全门禁、Schema 破坏和重复写采用绝对失败；一般质量指标可允许可解释波动。

## 12. 在线评测与监控

线上不能为每个请求调用昂贵 Judge。分层：

1. 100% 确定性监控：错误、超时、Tool、Token、权限决定；
2. 规则触发采样：高风险、长轨迹、高成本、用户差评；
3. 随机抽样 Judge；
4. 人工复核 Judge 不确定或关键场景；
5. 业务指标按日/周聚合。

记录 Prompt/Graph/模型/知识索引版本，才能判断漂移来源。

## 13. 数据飞轮不是自动训练闭环

安全回流：

```text
线上信号
  → 脱敏与权限检查
  → 去重/聚类
  → 失败分类
  → 人工标注
  → 加入 dev/test/redteam
  → 修复某一组件
  → 离线回归
  → 灰度发布
  → 继续观察
```

用户差评不自动等于模型错误；可能是需求、知识、Tool、UI 或业务策略问题。先分类再优化。

## 14. Prompt/Context/模型联合版本

一次运行至少记录：

```text
git_sha
prompt_id + prompt_hash
graph_version
tool_schema_versions
retriever/index/embedding versions
model provider/name/version if available
temperature and generation parameters
dataset version
evaluator version
```

供应商静默升级时，固定回归集和线上漂移信号比模型名更可靠。

## 15. 成本与性能评测

分开记录：

- TTFT；
- 完整响应延迟；
- 每次模型调用延迟；
- Tool/Retriever/Queue 等待；
- 输入/输出/缓存 Token；
- Agent 步数和模型调用数；
- 单成功任务成本，而非单请求平均成本；
- Fallback/Retry 产生的隐藏成本。

更便宜但任务成功率低的方案可能使“每成功任务成本”更高。

## 17. 项目练习

1. 为诊断任务建立 80 条 Dataset；
2. 至少 5 个标签分组和独立 redteam；
3. 写 3 个确定性 Evaluator、1 个轨迹 Evaluator、2 个 Judge Rubric；
4. 使用 50 条人工标注校准 Judge；
5. 比较两种 Prompt 或两个模型；
6. 输出总体、分组、错误样例、成本和置信区间；
7. 设置发布门禁并故意制造一次失败；
8. 将一个脱敏线上失败加入回归集。

## 18. 练习与答案

### 练习 1：总体平均分从 0.81 升到 0.84，可以发布吗？

**答案：**不能仅凭平均分。检查安全/高风险分组、样本方差、退化案例、延迟成本和业务显著性。若越权从 0 增至 1，即使平均分上升也应阻断。

### 练习 2：为什么 LLM Judge 不能同时担当所有质量门禁？

**答案：**Judge 有非确定性、偏差、漂移和注入风险。Schema、权限、Tool 参数、重复副作用等可确定验证的行为必须用代码和测试判断。

### 练习 3：线上差评是否应直接加入测试集？

**答案：**先脱敏、授权、去重、分类和重新标注。差评可能与模型无关，原始内容也可能包含敏感数据或攻击载荷。

### 练习 4：检索 Recall@K 提高但回答质量下降，可能是什么原因？

**答案：**新增召回可能带来噪声、冲突、过期内容或超过 Context 预算；还要检查重排、上下文装配和生成层，而不是继续追求召回。

## 20. 验收标准

- [ ] Case/Run/Event Schema 与平台解耦；
- [ ] Dataset 有来源、分层、版本和脱敏记录；
- [ ] 确定性、人工、Judge 和线上指标职责明确；
- [ ] Judge 与人工标注完成校准；
- [ ] RAG、轨迹、系统和业务指标分层；
- [ ] 发布门禁能真实阻断退化；
- [ ] 报告包含分组、方差、错误样例、延迟和成本；
- [ ] 至少完成一次安全的线上失败回流演练。
