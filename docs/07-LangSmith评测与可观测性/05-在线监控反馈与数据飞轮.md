# 在线监控、反馈与数据飞轮

> 预计 6 小时｜产出：从线上信号安全地产生下一轮评测样本。
> 所属阶段：第 7 阶段（LangSmith 评测与可观测性），第 5 章。

> **阅读前置**：本章从哪里开始——第 4 章（Agent 轨迹与 RAG 分层评测）已经把离线评测打通，但离线只能回答「这个版本好不好」。第 7 章《平台无关评测体系与数据飞轮》§12～§13 给出在线评测与数据飞轮的权威契约，本章把它落到「线上监控 → 人工反馈回流 → 数据集 → 回归」的闭环，并守住采样与隐私边界。

## 1. 本章从哪里开始

第 4 章结束时，你有一个「能定位到组件层」的离线评测体系。但离线评测有一个根本盲区：**数据集是过去的问题，线上是未来的问题**。真实用户会问出数据集里没有的故障码、会触发没预料到的越权尝试、会点「踩」然后离开——这些信号如果不接回来，你的评测集就会越来越旧，质量门禁也越来越「测不出真正的退化」。

所以本章要回答两个问题：

1. **在线监控**：线上不能为每个请求调用昂贵 Judge，如何分层采样、设 SLO、让告警可行动；
2. **数据飞轮**：如何把线上失败**安全地**回流成下一轮评测样本——经脱敏、权限审查、去重、人工标注后进入回归集，而不是自动训练或自动改 Prompt。

这套闭环对应第 7 章 §13 的「数据飞轮不是自动训练闭环」：用户差评不自动等于模型错误，先分类再优化。

## 2. 本章完成标准（通过门槛）

必须同时满足：

- 在线指标分三类（系统 / Agent / 成本 + 安全），每条有负责人与处置动作；
- 三条告警可行动（如「5 分钟内提交 Tool 失败率 >5% 且请求数 >20」），而非单次异常就叫醒人；
- 设置 SLO：核心只读任务可用性、P95、工单重复创建为 0；
- 反馈闭环走完：弱信号收集 → 失败分类 → 脱敏/权限审查/去重/标注 → 人工批准 → 加入回归集；
- 线上数据**不直接自动训练或改变 Prompt**；
- 监控模型/Prompt/数据版本分布，发布用灰度或特性开关，异常可快速回滚；
- 至少把 5 个失败 Trace 转为合格数据集样本。

## 3. 在线指标：三类 + 安全

第 7 章 §12 的在线分层，落到智维 Agent 的指标：

| 类别 | 指标 | 用途 |
| --- | --- | --- |
| 系统 | 请求量、成功/超时/429、P50/P95/P99、队列、依赖错误 | SLO 与容量 |
| Agent | 任务完成、平均步数、Tool 错误、循环、审批转化、拒答 | 质量趋势 |
| 成本 | 每任务 Token/费用、缓存命中、模型分布 | Usage 观测与异常告警 |
| 安全 | 越权拦截、注入检测、敏感输出事件 | 硬门禁 |

成本指标的口径延续全程契约：**只观测 Usage + 异常增长告警，不设固定金额上限**。例如「单任务平均 Token 环比增长 50%」触发告警，但不存在一个「累计多少钱就停」的上限——企业里真正的决策信号是「每成功任务成本」，而不是「花了多少钱」。

## 4. 告警必须可行动

「告警响了但不知道干什么」等于没告警。告警要绑定**条件 + 阈值 + 处置动作**：

```yaml
alerts:
  - name: submit_tool_failure_spike
    condition: "5 分钟内 create_work_order_draft 失败率 > 5% 且请求数 > 20"
    action: "检查上游工单服务、幂等键冲突、审批流状态；必要时回滚灰度"
  - name: upstream_429_surge
    condition: "5 分钟内 get_alarm 返回 E_UPSTREAM_TIMEOUT 或 429 > 3%"
    action: "熔断告警读取、按读/写与幂等决定有限重试"
  - name: duplicate_work_order
    condition: "同一幂等键成功提交次数 > 1"
    action: "立即阻断并排查，重复工单为硬门禁 0"
```

单次异常不叫醒人——加「且请求数 > 20」这样的量级门槛，避免噪声淹没真实信号。

## 5. SLO 与安全硬门禁

SLO 设置（示例，真实阈值来自业务基线）：

| 对象 | 目标 |
| --- | --- |
| 核心只读任务可用性 | ≥ 99.5% |
| P95 延迟 | ≤ 8000ms |
| 工单重复创建 | = 0（硬门禁） |
| 越权拦截 | = 0 泄漏（硬门禁） |

安全指标不做「百分比 SLO」，而是**事件计数为 0**：越权、密钥泄漏、未审批写、重复工单，出现 1 次即告警并触发处置，不参与平均。

## 6. 在线采样：不能每个请求都跑 Judge

线上不能为每个请求调用昂贵 Judge（第 7 章 §12），分层采样：

1. **100% 确定性监控**：错误、超时、Tool、Token、权限决定；
2. **规则触发采样**：高风险、长轨迹、高成本、用户差评；
3. **随机抽样 Judge**：按比例抽少量请求跑 Judge；
4. **人工复核**：Judge 不确定或关键场景；
5. **业务指标按日/周聚合**。

记录 Prompt/Graph/模型/知识索引版本，才能判断漂移来源（第 7 章 §12、§14）。

## 7. 反馈闭环：弱信号 → 强样本

点赞/点踩只是弱信号（第 7 章 §13）。完整闭环：

```text
线上信号（点踩 / 失败 / 转人工 / 放弃）
  → 脱敏与权限检查
  → 去重 / 聚类
  → 失败分类（需求 / 知识 / Tool / UI / 业务策略）
  → 人工标注（重写期望输出、判定是否模型错误）
  → 加入 dev / test / redteam
  → 修复某一组件
  → 离线回归
  → 灰度发布
  → 继续观察
```

关键约束：**用户差评不自动等于模型错误**，可能是需求、知识、Tool、UI 或业务策略问题，先分类再优化。线上数据也不能直接自动训练或改变 Prompt。

## 8. 失败 Trace 转数据集样本

把失败 Trace 转成合格样本，是一个有审核的转换，不是复制粘贴：

```python
# scripts/feedback_to_dataset.py
from observability.redact import redact, fingerprint


def trace_to_case(trace: dict, reviewer: str, decision: str) -> dict:
    # 1. 脱敏：正文键替换，保留业务 ID 与版本
    safe_inputs = redact(trace["inputs"])

    # 2. 去重指纹：同一类问题是否已存在
    dedup_key = fingerprint(trace["inputs"]["question"])

    # 3. 人工标注字段：由 reviewer 判定并填写
    return {
        "inputs": safe_inputs,
        "outputs": {
            "expected_status": decision,          # 人工判定，不是模型自动给
            "required_evidence_ids": trace.get("gold_evidence_ids", []),
            "forbidden_tools": trace.get("forbidden_tools", []),
        },
        "metadata": {
            "category": trace.get("category"),
            "source": "online_replay",
            "reviewer": reviewer,
            "dedup_key": dedup_key,
            "data_version": trace["data_version"],
        },
    }
```

要点：`expected_status` 由人工判定，`required_evidence_ids` 是人工给定的金标证据，`reviewer` 记录审核人，`dedup_key` 防止同类问题重复入库。**没有 `reviewer` 字段的样本不进入回归集**——这是「人工批准后才加入」的落点。

## 9. 发布与回滚

监控模型/Prompt/数据版本分布，发布使用灰度或特性开关，异常可快速回滚：

```text
灰度发布：新 Prompt/Graph 先给 5% 流量
  → 观察安全硬门禁、P95、任务成功率、Usage
  → 无异常扩大灰度
  → 异常一键回滚到上一版本
```

版本分布监控能回答「线上现在跑的是哪一版 Prompt/索引」——这是漂移判断的前提（第 7 章 §14）。

## 11. 常见错误与诊断顺序

### 11.1 把点踩直接当模型错误

点踩可能是需求、知识、Tool、UI 或业务策略问题。诊断顺序：先分类（看是模型错还是外部因素）→ 再决定是否回流 → 不自动训练或改 Prompt。

### 11.2 把用户输入自动加入数据集

可能含隐私、错误标注、攻击文本与数据授权问题。诊断顺序：先脱敏 → 权限审查 → 去重 → 人工标注 → 审核，才能进入回归集。

### 11.3 单次异常就叫醒人

噪声会淹没真实信号。诊断顺序：加量级门槛（如「且请求数 > 20」）→ 绑定处置动作 → 聚合观察，而非单点告警。

### 11.4 线上跑昂贵 Judge 全量

成本与延迟不可接受。诊断顺序：确定性信号 100% 监控 → 高风险/差评/长轨迹触发采样 → 随机抽样 Judge → 人工复核关键场景。

## 12. 练习题与答案

### 练习 1：点赞率下降能证明模型退化吗？

**答案：**不能单独证明，可能是用户分布、界面、延迟或样本偏差。应结合任务完成、组件指标和版本分布分析，先分类再下结论。

### 练习 2：为何不自动把用户输入加入数据集？

**答案：**可能含隐私、错误标注、攻击文本与数据授权问题，必须脱敏、权限审查、去重、人工标注、审核后才能使用。

### 练习 3：为什么数据飞轮不是自动训练闭环？

**答案：**用户差评不等于模型错误，可能是需求/知识/Tool/UI/业务策略问题；线上数据也不能直接自动训练或改 Prompt。正确闭环是「分类 → 标注 → 审核 → 加入回归集 → 修复组件 → 回归 → 灰度」。

### 练习 4：在线采样为什么分层？

**答案：**线上不能为每个请求跑昂贵 Judge。确定性信号 100% 监控，高风险触发采样，随机抽样 Judge，关键场景人工复核，业务指标按日/周聚合，兼顾成本与覆盖。

## 13. 工程挑战

1. 写一个「采样器」：按确定性 / 规则触发 / 随机三类规则决定一个请求是否进 Judge，写测试证明高风险请求 100% 被采样；
2. 给 `trace_to_case` 写拒绝测试：缺少 `reviewer` 字段、正文未脱敏、`dedup_key` 重复的样本不得入库；
3. 模拟一次灰度发布：新 Prompt 在 5% 流量下出现越权泄漏，验证「安全硬门禁 + 一键回滚」能触发；
4. 设计告警的「最小可行动」校验：任何告警若没有处置动作字段，脚本报错拒绝上线。

参考方向：采样器复用第 7 章 §12 的分层规则；拒绝测试复用 `redact` 与 `fingerprint`；灰度回滚复用特性开关（第 4 阶段 Middleware 的 flag 思路）。

## 14. 面试追问

### 14.1 「你们怎么从线上产生下一轮评测样本？」

回答框架：弱信号（点踩/失败/转人工）→ 脱敏与权限检查 → 去重聚类 → 失败分类 → 人工标注金标 → 审核（reviewer 字段）→ 加入 dev/test/redteam → 修复 → 回归 → 灰度。线上数据不自动训练或改 Prompt。

### 14.2 「点赞率下降，你们会立刻优化模型吗？」

回答框架：不会。先分类判断是模型、知识、Tool、UI 还是业务策略问题，结合任务完成与版本分布分析，再决定动作。点踩是弱信号，不能单独证明模型退化。

### 14.3 「为什么安全指标不做百分比 SLO？」

回答框架：安全违规是低频高危事件，99 正常 + 1 越权不是 99% 可发布。越权、重复工单按事件计数为 0，出现即告警并触发处置，不参与平均稀释。
