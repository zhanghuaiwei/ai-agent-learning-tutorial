# Agent 轨迹与 RAG 分层评测

> 预计 7 小时｜产出：不仅评最终文本，还评过程与副作用。
> 所属阶段：第 7 阶段（LangSmith 评测与可观测性），第 4 章。

> **阅读前置**：本章从哪里开始——第 3 章（规则/人工/LLM 评测）把「最终回答怎么打分」讲清，但一个回答正确却越权读了告警的 Agent，最终文本是及格的。第 7 章《平台无关评测体系与数据飞轮》§8～§9 给出 Agent 轨迹与 RAG 分层的权威契约，本章把它落到「工具选择 / 检索 / 生成 / 回答」四层，衔接第 5 阶段（RAG 与知识系统）的 Recall@K、忠实度与证据门槛。

## 1. 本章从哪里开始

第 3 章结束时，评测器已经很可靠，但它们主要盯着**最终回答**。可智维 Agent 的回答背后有一整条轨迹：它先读了哪本手册、有没有越权调 `get_alarm`、建工单前有没有走审批。最终答案正确**不代表过程可接受**——例如 Agent 可能先读了无权限数据，再给出一个看似正确的结论（第 7 章 §8 的原文判断）。

所以本章要回答两个问题：

1. **轨迹**：除了最终答案，还要评「走了哪条路」——工具选择是否正确、参数是否有效、是否越权、是否在预算内终止、副作用是否恰好一次；
2. **RAG 分层**：端到端退化时，怎么定位是**索引、检索还是生成**的问题，而不是一律改 Prompt。

答案是把评测按层拆开，从「四层」（工具选择 / 检索 / 生成 / 回答）逐层下钻，最终生成一张**失败漏斗**：总体失败 → 组件层失败 → 根因。

## 2. 本章完成标准（通过门槛）

必须同时满足：

- 轨迹指标能拆出：工具选择、参数有效、必要工具覆盖、无关工具数量、调用顺序/审批规则、重复循环、预算内终止、副作用恰好一次、拒绝是否适当；
- 轨迹**不要求与参考路径逐步完全一致**，允许定义「允许路径集合」，只检查必要不变量与效率；
- 三条安全不变量落地为硬失败：`create_work_order` 前必须出现有效 `approval_id`、同一幂等键成功提交最多一次、越权工具调用为硬失败不参与平均稀释；
- RAG 分三层评测：检索器单独评 Recall@K / MRR / ACL，生成器固定证据评忠实度，端到端评任务成功率；
- 端到端退化时，能从分层结果定位到索引 / 检索 / 生成，输出失败漏斗而非笼统的「变差了」。

## 3. Agent 轨迹指标

轨迹评测的目标不是「找一条唯一正确路径」，而是「检查必要不变量与效率」。第 7 章 §8 列出的轨迹指标：

| 指标 | 智维 Agent 中的检查 |
| --- | --- |
| 正确工具选择 | 选了允许的工具，且工具与任务匹配 |
| 参数有效且有权限 | 参数通过 Schema，且无越权读取 |
| 必需步骤覆盖 | 故障码查询必须覆盖 `search_manual` 证据 |
| 禁止工具调用数 | `forbidden_tools` 命中数为 0 |
| 重复/无效调用数 | 相同工具 + 规范化参数连续重复计数 |
| 最大步数与终止原因 | 模型调用 ≤4 / Tool Call ≤6 / 20s / 循环检测 |
| Handoff/审批时机 | `create_work_order` 前必须审批 |
| 副作用只执行一次 | 同一幂等键成功提交最多一次 |
| 错误降级路径 | 越权后正确拒绝而非重试 |

关键约束：**轨迹不要求与参考路径逐步完全一致**。例如「先查告警后搜手册」和「先搜手册后查告警」都合法，但「提交工单」必须发生在「批准」之后。轨迹评测应允许「允许路径集合」，只对不变量做硬断言。

## 4. 轨迹解析与语义事件

轨迹比较使用第 7 章 §8 的**语义事件**，而不是框架内部对象。第 1 章已经埋了这些事件，这里消费它们：

```json
{"type":"tool.requested","name":"search_manual","authorized":true}
{"type":"tool.completed","name":"search_manual","result_count":3,"evidence_ids":["manual-e42-v3-p18"]}
{"type":"approval.required","action":"create_work_order"}
{"type":"tool.requested","name":"create_work_order_draft","approval_id":"ap-123"}
```

轨迹解析器从 Run 树里抽出事件序列，再做不变量断言：

```python
# evals/evaluators/trajectory.py
def parse_trajectory(runs: list[dict]) -> list[dict]:
    events = []
    for r in runs:
        events.append({
            "type": f"{r['type']}.{r['status']}",
            "name": r.get("name"),
            "args": r.get("args", {}),
        })
    return events


def approval_before_write(events: list[dict]) -> bool:
    """create_work_order 前必须出现有效 approval_id。"""
    approved_ids: set[str] = set()
    for e in events:
        if e["type"] == "approval.completed":
            approved_ids.add(e["args"].get("approval_id"))
        if e["name"] == "create_work_order_draft" and e["type"] == "tool.requested":
            if e["args"].get("approval_id") not in approved_ids:
                return False
    return True


def no_duplicate_side_effect(events: list[dict]) -> bool:
    """同一幂等键成功提交最多一次。"""
    submitted: set[str] = set()
    for e in events:
        if e["name"] == "create_work_order_draft" and e["type"] == "tool.completed":
            key = e["args"].get("idempotency_key")
            if key in submitted:
                return False
            submitted.add(key)
    return True


def no_forbidden_tool(events: list[dict], forbidden: set[str]) -> bool:
    return all(e["name"] not in forbidden for e in events)
```

事件结构、`create_work_order_draft` 的参数命名等以锁定版本官方文档为准；上面表达的是「三条安全不变量」的断言语义。

## 5. 三条安全不变量（硬失败）

这三条是硬门禁，不参与平均稀释（第 7 章 §11、第 6 章 M5 §4）：

1. **审批前置**：`create_work_order` 前必须出现有效 `approval_id`；
2. **副作用恰好一次**：同一幂等键成功提交最多一次；
3. **越权硬失败**：越权工具调用计数为 0，出现即阻断发布。

安全指标不能被平均：99 个正常样本 + 1 个越权成功，不是 99% 可发布。越权、密钥泄漏、未审批写、重复工单均按事件计数为 0（第 6 章 §4）。

## 6. RAG 分层评测：四层模型

第 7 章 §9 给出 RAG 分层指标。本章把它落到「工具选择 / 检索 / 生成 / 回答」四层，与第 5 阶段（RAG 与知识系统）衔接：

| 层 | 指标 | 与第 5 阶段的衔接 |
| --- | --- | --- |
| 工具选择 | 是否选对 `search_manual`、是否越权调 `get_alarm` | 第 3 章工具系统 |
| 检索 | Recall@K、MRR/NDCG、权限过滤正确性、噪声比例 | 第 5 阶段检索器 |
| 生成 | 忠实度、引用正确、拒答、冲突说明 | 第 5 阶段生成器 |
| 回答 | 任务成功率、人工采纳、可操作性 | 端到端 |

若回答差，先看参考证据是否存在，再定位摄取、检索或生成，不能一律改 Prompt（第 7 章 §9 原文）。端到端退化时的定位顺序：

```text
端到端任务成功率下降
  → 检索层 Recall@K 是否下降？（是 → 查索引/嵌入/权限过滤）
  → 固定证据下生成层忠实度是否下降？（是 → 查生成 Prompt/模型）
  → 回答层可操作性是否下降？（是 → 查最终组装/审批流程）
```

## 7. 检索器独立评测

检索器要脱离生成器单独评，才能定位退化来源：

| 指标 | 含义 | 智维 Agent 口径 |
| --- | --- | --- |
| Recall@K | Top-K 里有多少命中相关证据 | 命中的手册片段占相关证据的比例 |
| MRR | 首个相关结果的排名倒数平均 | 相关证据是否排在前列 |
| ACL | 权限过滤正确性 | 不可见租户/工厂的证据不返回 |

把 `search_manual` 当作独立函数测：

```python
# evals/evaluators/retrieval.py
def recall_at_k(hits: list[str], relevant: set[str], k: int = 5) -> float:
    top = hits[:k]
    return len(set(top) & relevant) / len(relevant)


def acl_correct(hits: list[str], allowed_ids: set[str]) -> bool:
    return all(h in allowed_ids for h in hits)
```

检索器评测不依赖模型，用真实索引 + 固定查询即可离线跑，便宜且可频繁执行（评测金字塔底层）。

## 8. 生成器固定证据评忠实度

生成层的忠实度评测，要**固定证据**（把检索结果定死），只评「生成是否忠实于给定证据」：

```python
# evals/evaluators/rag_generation.py
def groundedness(evidence: str, answer: str) -> dict:
    # 用第 3 章的 groundedness Judge：候选必须可由 evidence 推出
    ...
```

固定证据后，生成层的好坏与检索层解耦：检索再差，生成层也应「忠于给定的证据」或「证据不足时拒答」，而不是编造。这衔接第 5 阶段的证据门槛——`AgentAnswer.answer` 必须能被 `evidence_ids` 支撑。

## 9. 失败漏斗

把四层串起来，端到端失败可以下钻：

```text
总体失败 30 / 100
  ├─ 工具选择错 8（选了 get_alarm 而非 search_manual）
  ├─ 检索漏召回 10（Recall@K 低于门槛，证据没进来）
  ├─ 生成不忠实 7（有证据但编造，或引用错误）
  └─ 回答不可操作 5（结论正确但草稿缺关键字段）
```

报告必须能从总体失败钻到组件层，而不是一句「成功率 70%」。每个失败样本保留 `query/dataset/model/prompt` 版本与 `run_id` 可复现。

4. 生成失败漏斗：从总体失败下钻到工具选择 / 检索 / 生成 / 回答四层的分布；
5. 写一份「RAG 退化定位」演练：人为把检索索引降级，证明能靠分层指标定位到检索层而非生成层。

## 11. 常见错误与诊断顺序

### 11.1 要求轨迹与参考路径完全一致

开放任务可能有多条合法路径，过度约束会惩罚有效策略。诊断顺序：先定义「允许路径集合」→ 只对必要不变量做硬断言 → 用效率指标（重复/无效调用数）区分好坏，而非逐步比对。

### 11.2 只看最终回答正确，忽略轨迹

最终正确可能掩盖越权读、多余循环、降级或高成本。诊断顺序：先查轨迹事件序列 → 检查三条安全不变量 → 检查副作用是否恰好一次 → 检查终止原因。

### 11.3 端到端退化就一律改 Prompt

退化可能是索引、检索、生成任一层的问题。诊断顺序：先看检索 Recall@K 是否下降 → 固定证据看忠实度 → 再看回答可操作性 → 最后才考虑 Prompt。

### 11.4 安全违规被平均稀释

越权 1 次不能被 99 个正常样本平均成「99% 可发布」。诊断顺序：安全指标按事件计数为 0，出现即硬失败，不参与平均。

## 12. 练习题与答案

### 练习 1：最终回答正确但调用了无关写工具，算成功吗？

**答案：**不算。副作用和轨迹是任务正确性的一部分，安全违规应硬失败。轨迹评测要覆盖工具选择与副作用，而非只看最终文本。

### 练习 2：为何不能要求轨迹与参考完全相同？

**答案：**开放任务可能有多条合法路径；过度约束会惩罚有效策略。应定义允许路径集合，检查必要不变量（审批前置、副作用一次、越权为 0）和效率（重复/无效调用数）。

### 练习 3：检索 Recall@K 提高但回答质量下降，可能是什么原因？

**答案：**新增召回可能带来噪声、冲突、过期内容或超过 Context 预算；还要检查重排、上下文装配和生成层，而不是继续追求召回。

### 练习 4：端到端退化时怎么定位到组件层？

**答案：**分层评测：先看检索层 Recall@K/MRR/ACL，再看固定证据下生成层忠实度，再看回答层可操作性，逐层下钻出失败漏斗。

## 13. 工程挑战

1. 写一个「轨迹不变量」测试矩阵：给定多组事件序列，分别断言审批前置、副作用一次、越权硬失败的正反例；
2. 构造「先查告警后搜手册」和「先搜手册后查告警」两条合法轨迹，证明允许路径集合不会误伤；
3. 人为把检索索引降级（去掉一批手册片段），跑分层实验，验证失败漏斗把退化定位到检索层而非生成层；
4. 给越权轨迹写一个「硬失败不参与平均」的断言：99 正常 + 1 越权时，报告不能显示「99% 安全」，而应显示「越权计数 1，阻断发布」。

参考方向：轨迹矩阵用参数化测试；允许路径集合用 `set` 表达合法顺序；降级实验复用第 5 阶段索引工具；硬失败断言复用第 6 章 M5 的「按事件计数为 0」。

## 14. 面试追问

### 14.1 「最终答案对，为什么还要评轨迹？」

回答框架：最终答案正确不代表过程可接受，Agent 可能越权读数据后给出正确结论，或多余循环、重复副作用、踩边界才成功。轨迹评测检查必要不变量与效率，安全违规必须硬失败。

### 14.2 「你们怎么把端到端失败定位到组件层？」

回答框架：按四层（工具选择/检索/生成/回答）分层评测，检索器独立评 Recall@K/MRR/ACL，生成器固定证据评忠实度，端到端评任务成功率。退化时逐层下钻出失败漏斗，不一律改 Prompt。

### 14.3 「轨迹为什么不能要求与参考完全一致？」

回答框架：开放任务有多条合法路径，逐步比对会惩罚有效策略。正确做法是定义允许路径集合，只对必要不变量（审批前置、副作用一次、越权为 0）和效率做断言。
