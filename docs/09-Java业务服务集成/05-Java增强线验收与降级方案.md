# Java 增强线验收与降级方案

> 所属阶段：第 9 阶段（Java 业务服务集成增强线），第 21 周验收
> 预计 4 小时｜目标：证明能与企业既有 Java 业务系统集成，而非展示 CRUD 数量；给出可执行的双栈决策。

## 1. 本章从哪里开始

前四章依次交付了：边界（第 1 章）、受控 API（第 2 章）、Tool Adapter（第 3 章）、幂等与跨服务失败（第 4 章）。现在要把它们放在一起验收，并回答一个必须直面、不能和稀泥的问题：**这个"Python 主线 + Java 业务服务"的双栈，到底值不值得保留？**

很多增强线工程死在"验收时只数接口数量"，而本阶段的价值恰恰不在 CRUD 数量，在**业务边界与跨服务可靠性**。所以本章的验收标准不数"写了几十个 Controller"，而数"跨服务一次正常提交 + 一次成功后超时恢复，能否演示清楚"。

完成后你应该能回答：

1. Java 线完成了很多 CRUD 但无幂等，算通过吗？
2. 什么情况下保留双栈、什么情况下降级为纯 Python、什么情况升级为纯 Java？
3. 面试时该把自己定位成"Java Agent 工程师"吗？

## 2. 本章完成标准（通过门槛）

必须同时满足：

- 完整验收清单逐项有代码落点与测试（见第 3 节）；
- 能现场演示一次跨服务正常提交 + 一次成功后超时恢复；
- 架构图能说清数据所有权、身份、事务和失败语义；
- 双栈决策给出**明确结论**，不写"看情况"；
- 未完成 Java 实现时，Mock/契约与设计必须可运行、可评审。

达不到"说清失败语义"，说明第 4 章没过关，先回补幂等与调和再谈验收。

## 3. 完整验收清单

逐项核对，每一项都能指到代码与测试：

| 验收项 | 落点 | 判定 |
| --- | --- | --- |
| Java 拥有设备/告警/工单/审批，Python 不直连业务库 | 第 1 章边界 + 第 2 章 API | 无 Python 直连 MySQL 路径 |
| JWT/Mock Auth 下资源级租户隔离 | 第 2 章 §5 | 越权 403、JSON 指定租户不生效 |
| OpenAPI 契约、请求/响应校验、稳定错误码 | 第 2 章 §3/§6 | `code/message/request_id/details` |
| 工单幂等、事务、乐观锁、成功后超时调和 | 第 4 章 | 并发下只有一张工单 |
| Python Fake/REST Adapter 契约一致 | 第 3 章 | 同一组契约测试通过 |
| 端到端 Trace 可串联 | 第 3 章 §7 | `traceparent`/`request_id` 贯通 |
| 费用仅观测 + 异常增长告警 | 主线观测 | 只观测 Usage，不设固定金额上限 |

## 4. 双栈决策：明确结论

不写"看情况"，直接给结论：

**默认保留双栈（Python 主线 + Java 最小业务服务）。** 理由：企业现状就是"AI 编排在 Python、业务真相在 Java"，这个组合正是你要展示的核心能力——不是"会用 Java"，而是"能安全集成既有 Java 业务系统"。

在这个默认结论下，两条降级/升级路径是例外，各有明确触发条件：

| 结论 | 触发条件 | 代价 |
| --- | --- | --- |
| 降级为纯 Python | 目标岗位明确纯 Python；或时间严重不足；或没有可展示的业务边界 | 失去"集成既有 Java"的证据 |
| 升级为纯 Java（Spring AI） | JD 明确 Java AI 生态且连续出现；公司统一 Java 栈 | 稀释 Agent 深度，需重补 RAG/评测 |

判定口诀：**默认双栈；JD 是纯 Python 就砍 Java；JD 明确 Java AI 生态才升级，且要单独补 Spring AI，而不是临时改主线。**

## 5. 时间不足时的降级优先级

第 20 周主项目仍不稳时，按优先级砍，先保住可评审的契约：

```text
优先级从高到低：
1. OpenAPI 与数据所有权        ← 必须留，是边界证据
2. Mock Server                 ← 可运行、可评审
3. Python Adapter 契约测试      ← 证明 Fake/HTTP 一致
4. Java 最小提交 API            ← 业务真相的最小载体
5. 完整鉴权 / Outbox            ← 可后补
```

若只完成前三项，必须在架构文档说明生产实现（鉴权、幂等、Outbox 怎么做）；**不要挪用最终三周的评测和面试时间**。

## 6. 演示脚本

按此顺序演示，每条都要有"预期可观察行为 + 判据"：

1. **跨服务正常提交**：Python 建草稿 → 提交 → 查状态 `SUBMITTED`，展示 `request_id` 贯通 Python 与 Java 日志；
2. **成功后超时恢复**：Java 提交成功后延迟响应 → Python 落 `UNKNOWN` → 调和器按幂等 Key 查到 `COMPLETED` → 置 `SUBMITTED`，展示全程只有一张工单；
3. **越权 403**：租户 A 查租户 B 设备，展示资源级隔离，不泄露存在性；
4. **架构图讲解**：一张图说清数据所有权、身份、事务、失败语义四处。

## 8. 常见错误与诊断顺序

### 8.1 用 CRUD 数量代替验收质量

现象：验收时数"实现了 20 个 Controller"。**先查**：有没有幂等、越权、超时调和的证据？**不要先做**：堆更多 CRUD——课程价值是业务边界与跨服务可靠性，CRUD 只是载体。

### 8.2 双栈结论写"看情况"

现象：决策文档写"视团队而定，两种都可以"。**先查**：默认结论是什么？降级/升级的触发条件是否可执行？**不要先做**：和稀泥——面试官要的是明确判断。

### 8.3 只演示成功路径，不演示超时恢复

现象：只跑通正常提交，跳过超时场景。**先查**：有没有"成功后超时"的集成测试与演示？**不要先做**：回避失败语义——那恰恰是本阶段的核心价值。

### 8.4 时间不够就挪用评测时间补 Java

现象：主项目还不稳，却花大量时间补 Java 鉴权。**先查**：是否只完成前三个优先级、其余写架构文档？**不要先做**：牺牲最终三周的评测和面试时间。

## 9. 练习题与答案

### 练习 1：Java 线完成很多 CRUD 但无幂等，算通过吗？

**答案：**不算。课程价值是业务边界与跨服务可靠性，CRUD 只是载体。没有幂等、越权、超时调和的证据，CRUD 数量再多也不算通过。

### 练习 2：面试时应把自己定位成 Java Agent 工程师吗？

**答案：**定位为 Python Agent 应用工程师，能与 Java 企业业务后端集成；如 JD 明确 Java AI 生态，再单独补 Spring AI，而非临时改主线。

### 练习 3：什么情况下把双栈降级为纯 Python？

**答案：**目标岗位明确纯 Python、时间严重不足、或没有可展示的业务边界时；但仍应在架构文档说明如何集成现有 Java 系统，而不是假装它不存在。

### 练习 4：什么时候才升级为纯 Java？

**答案：**JD 明确 Java AI 生态且连续出现、公司统一 Java 技术栈时；升级要单独补 Spring AI 的 RAG/评测/Agent 深度，不能只把现有 Python 逻辑机械翻译成 Java。

## 11. 面试追问

### 11.1 "你们做 Java 增强线，价值是什么？"

回答框架：不是 CRUD 数量，是证明能安全集成既有 Java 业务系统——数据所有权唯一、资源级租户隔离、幂等与超时调和、端到端 Trace 串联。

### 11.2 "为什么不全用 Java 写 Agent？"

回答框架：主线目标是 Agent 深度，Python 生态的 LangChain/LangGraph 资料与评测更成熟；双栈默认保留是因为企业业务真相本就在 Java。除非 JD 明确 Java AI 生态，才单独补 Spring AI。

### 11.3 "这套集成在什么情况下会失败？"

回答框架：在"超时被当失败盲目重试"时重复建单，在"模型可指定租户"时越权，在"CRUD 数量当验收"时失去可靠性证据。这些都是本阶段第 2/3/4 章专门消灭的反模式。
