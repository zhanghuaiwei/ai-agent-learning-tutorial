# AI 服务与业务服务边界

> 所属阶段：第 9 阶段（Java 业务服务集成增强线），第 21 周
> 预计 4 小时｜目标：明确「AI 编排」与「业务真相」的边界，产出可执行的数据所有权表与集成决策表。
> 结论：保留 Python 主线，Java 只承担值得保留的业务边界。

## 1. 本章从哪里开始

到本阶段为止，Python 主线（M0～M5）已经交付了一个能查手册、查告警、建工单草稿的「智维 Agent」：LangChain `create_agent` 装配、`AgentContext` 冻结 dataclass 身份注入、`search_manual`/`get_alarm`/`create_work_order_draft` 三个工具、`E_*` 错误契约、SSE 12 事件、只观测 Usage + 异常增长告警的费用策略。

但主线里有一个刻意留出的空洞：**工单草稿、告警状态、设备台账这些"业务真相"，主线一直用内存 Fake 或简单占位实现，没有真正的确定性业务规则与事务。** 第 9 阶段要补的就是这一块——用最小 Spring Boot 业务服务承载确定性规则，让 Python Agent 通过 REST Tool Adapter 调用它。

本章是第 9 阶段的开篇，不写代码，先回答一个最容易答错的问题：**AI 到底该拥有什么、不该拥有什么。**

完成后你应该能回答：

1. 为什么「模型生成工单文本」不等于「模型拥有工单真相」？
2. 什么数据只能有一个权威写入方？Python 和 Java 各自保存什么？
3. 判断"这件事该放 Python 还是 Java"时，按什么规则而不是凭感觉？

## 2. 本章完成标准（通过门槛）

必须同时满足：

- 产出一张**服务责任表**：设备、告警、工单、审批、文档索引、Agent State 六类数据，逐项标出权威写入方与可保存方；
- 产出一张**时序图**（或等价文字版）：一次「查告警 → 建工单草稿」的完整链路，能标出每一跳的调用方、身份来源、鉴权边界；
- 任何"核心事实"都**只有一个权威写入方**，不存在 Python 与 Java 同时写同一张业务表的路径；
- 能凭一张决策表回答"这个字段/这条规则放哪边"，而不是给出"看情况"的和稀泥结论；
- 费用口径正确：只观测 Usage + 异常增长告警，不设固定金额上限。

达不到前三条，不要进入第 2 章写 API——边界没想清楚，接口写得越多越乱。

## 3. 为什么不是全 Java

一个很自然的诱惑是：公司后端全是 Java，为什么不干脆用 Spring AI 把 Agent 也写成 Java？

答案不是"Java 不好"，而是**投入产出与学习目标不匹配**：

- LangChain/LangGraph/LangSmith 的优质资料、示例、评测工具以 Python 为主，Agent 编排、RAG、结构化输出、流式的成熟案例集中在 Python 生态；
- 你的目标岗位是 **AI Agent 应用开发**，每周学习时间有限，把主线换成 Java 会稀释 Agent 深度，把时间花在 JVM、依赖注入、ORM 的边角上；
- 主线前 8 个阶段已经沉淀了 `create_agent`、`ToolStrategy`、SSE 12 事件、`E_*` 契约、评测脚本，这些资产是 Python 的。

所以结论很硬：**Python 必须是 Agent 后端主线。** 这一条不是偏好，是边界的第一刀。

## 4. 为什么仍保留 Java

但"Python 主线"不等于"Java 没价值"。企业里设备台账、告警流转、工单审批往往已经在 Java 系统里，而且这些系统的价值恰恰在于**确定性**：

- 设备编号唯一、告警状态机、工单审批流的规则是业务规则，不该由模型"发挥"；
- 转账/出库/审批这类操作需要事务、乐观锁、审计，模型只负责理解意图，不负责保证一致性。

用一个最小 Java 业务服务，能证明你理解一条关键命题：**AI 编排不能拥有一切。** 于是分工变成：

- **Java 拥有**：设备、告警、工单、审批、事务和最终业务规则；
- **Python 拥有**：模型网关、RAG、Graph、Prompt、评测和 Agent Tool Adapter；
- 两者通过**版本化 REST 契约**集成，**不共享数据库表**。

若时间不足，Java 线可降级为 OpenAPI + Mock Server 设计，不影响 Python 主项目完成；但不得为了"全栈"牺牲 M4～M6 的可靠性证据（越权拦截、终态、评测）。

## 5. 核心命题：模型不拥有业务真相

这是本章的题眼。看一个反例：

```
用户：现在 A 工厂有几条未关闭告警？
模型：有 3 条。（——如果这个数字来自模型"编"出来的，就错了）
```

模型的职责是**理解意图 → 选择工具 → 组织语言**，而"几条告警"这个事实必须来自 `get_alarm` 查询的确定性结果。模型输出的工单标题、故障描述可以靠生成能力，但：

| 事实 | 模型能生成吗 | 谁拥有真相 |
| --- | --- | --- |
| 告警条数 | 不能编，必须查 | Java 业务服务 |
| 设备是否在保 | 不能编，必须查 | Java 业务服务 |
| 工单状态 | 不能编，必须查 | Java 业务服务 |
| 工单标题/摘要 | 可以生成 | Python 生成后写入 Java 草稿 |
| 故障分析建议 | 可以生成 | Python，作为工单正文的一部分 |

一句话：**模型负责"说"，业务服务负责"是"。** 能生成的内容（摘要、建议）可以放进工单草稿，但草稿本身、草稿的提交与审批状态，必须是 Java 侧受控的确定性状态。

## 6. 数据所有权

在上一节的命题下，六类数据的权威归属如下：

| 数据 | 权威方 | Python 可保存 |
| --- | --- | --- |
| 设备/告警 | Java | 只保存带时间的查询快照或引用，不回写 |
| 工单/审批 | Java | `work_order_id/approval_id` 与运行映射，不建第二份状态 |
| 文档索引 | Python 知识服务 | Chunk、向量、版本、ACL |
| Agent State | Python/LangGraph | 执行状态，不替代业务事实 |
| 模型调用观测 | Python | Usage、延迟、工具调用记录，仅观测 + 告警 |
| 审计/事务日志 | Java | 业务写操作的权威审计 |

注意"Python 可保存"一列的含义：**Python 可以缓存、可以存引用，但绝不成为第二个权威写入方。** 例如 Python 存了"某设备上一次查询有 3 条告警"的快照，这不等于 Python 拥有告警真相；下次要回答，仍要重新查 Java。

## 7. 边界判定规则：一张可执行的决策表

"放哪边"不能凭感觉，按以下规则顺序判定：

| 判定维度 | Python（Agent 侧） | Java（业务侧） |
| --- | --- | --- |
| 数据是否模型可生成 | 生成类：摘要、建议、闲聊 | 事实类：台账、状态、审批结论 |
| 是否需要事务/一致写 | 否 | 是 |
| 是否可逆写 | 草稿（可撤回/覆盖）可放 Python 调 Java 写 | 提交/审批这类不可逆动作必须 Java 受控 |
| 是否跨请求共享真相 | 运行内上下文 | 跨会话、跨服务的事实 |
| 是否有审计合规要求 | 不需要强审计 | 需要 |
| 调用方向 | 总是主动调 Java | 被调，暴露受控 API |

判定口诀：**能生成的放 Python，必须是真的放 Java；可逆写可以借 Java 的 API 做，不可逆写必须 Java 的事务做。**

## 8. 集成契约概览：给后四章铺路

本章的边界最终会落成第 2～4 章的接口。这里先定契约骨架，后四章只是把它坐实：

```text
Python Agent
  ├─ search_manual        → 知识服务（Python 自持，不经过 Java）
  ├─ get_alarm            → GET  /api/v1/equipments/{id}/alarms   （Java）
  └─ create_work_order_draft → POST /api/v1/work-order-drafts      （Java）
        └─ 提交/审批        → POST /api/v1/work-orders             （Java）
```

跨服务统一约定：

- **鉴权**：Java 用 Resource Server 校验 JWT（`iss/exp/aud`）；服务身份或受控 Token Exchange 获得，用户 `X-User-Id` 与 `tenant_id` 来自可信 Claim，**不由模型或请求 JSON 任意指定**；
- **Trace 透传**：`traceparent`（W3C Trace Context）与 `request_id` 从 Python 透传到 Java，贯通端到端 Trace；
- **幂等**：写请求带幂等键（`Idempotency-Key`），Java 用幂等表 + 业务唯一键双保险；
- **错误契约**：Java 错误统一 `code/message/request_id/details`，映射为 Python 侧的 `E_*`（`E_NOT_FOUND`/`E_CONFLICT`/`E_FORBIDDEN`/`E_UPSTREAM_TIMEOUT` 等）。

这些细节分别在后面四章展开，本章只需要你记住：**边界是接口的因，接口是边界的果。**

## 10. 常见错误与诊断顺序

### 10.1 把"模型生成了工单文本"当成"模型拥有工单"

现象：演示时模型输出了一段漂亮工单，就以为工单功能做完了。**先查**：这段文本写入到哪了？有没有真实存在的 `work_order_id`？提交后状态是否在 Java 侧可查、可审计？**不要先做**：在 Python 里自己建一张 `work_orders` 表存模型输出。

### 10.2 共享数据库"图省事"

现象：Python 直接连 Java 的 MySQL，少一次 HTTP 调用。**先查**：这绕过了多少 Java 业务规则和事务？会不会出现 Python 和 Java 同时改同一行？**不要先做**：为了省一次 HTTP 而引入共享数据库耦合——这正是第 8 章要消灭的反模式。

### 10.3 "两边都写"导致真相分裂

现象：告警状态 Python 存一份、Java 存一份，两边对不上。**先查**：谁是权威方？能不能把非权威方改成只读快照或引用？**不要先做**：写同步任务去"对齐"两份真相——对齐是治标，单一权威才是治本。

## 11. 练习题与答案

### 练习 1：Python 能否直接连 Java 的 MySQL 以省一次 HTTP？

**答案：**不建议。会绕过 Java 业务规则和事务，形成共享数据库耦合，让"权威写入方唯一"失效。应通过受控 API 访问，Python 只保存快照或引用。

### 练习 2：何时可以完全去掉 Java？

**答案：**目标岗位明确纯 Python、时间不足，或没有可展示的业务边界时。仍应在架构文档说明如何集成现有 Java 系统，而不是假装 Java 不存在。

### 练习 3：模型输出的故障建议该由谁"拥有"？

**答案：**建议文本本身由 Python 生成、可以作为工单草稿正文的一部分；但草稿一旦提交，其状态、审批流转的真相归 Java。可生成内容与可提交状态是两个所有权层级。

### 练习 4："告警条数"和"告警分析"哪个能由模型编？

**答案：**条数是事实，必须查询 Java，不能编；分析是生成，可以编，但必须标注它是"建议"而非"事实"，且最终写入仍走 Java 草稿接口。

## 13. 面试追问

### 13.1 "你们的 AI 服务里，模型直接写数据库吗？"

回答框架：不写。模型只通过工具表达意图，工具由 Python 侧执行，写操作经 REST 调 Java 业务 API；业务真相在 Java，Python 只保存快照/引用，任何核心事实只有一个权威写入方。

### 13.2 "为什么不全用 Java 写 Agent？"

回答框架：主线目标是 Agent 深度，Python 生态的 LangChain/LangGraph 资料与评测工具更成熟；Java 保留业务真相这一块已足够证明集成能力。除非目标 JD 明确要求 Java AI 生态，才单独补 Spring AI（对应第 6 章）。

### 13.3 "你怎么保证模型不会自己编告警数量？"

回答框架：靠确定性边界——`get_alarm` 只读查询，结果来自 Java；模型无法绕过工具直接获得数据；回答里的事实性数字必须能在工具返回与 Trace 中找到来源，否则视为不可信。
