# 幂等、事务与跨服务失败

> 所属阶段：第 9 阶段（Java 业务服务集成增强线）
> 预计 7 小时｜目标：让 Java 业务服务对跨服务调用做到"恰好一次的业务效果"，超时不再盲目重试。

## 1. 本章从哪里开始

第 3 章把 Java API 包装成了 Tool，但留下一个致命缺口：**Python 调用 Java 是跨网络的，超时、丢包、重试都可能发生。** 如果 Python 提交工单后超时，它无法知道 Java 到底建没建成——盲目重试会重复建单，不重试又可能漏建。

本章解决这个"跨服务恰好一次"问题。答案不是"加个重试"，而是三层机制：**幂等表 + 业务唯一键**挡住重复写，**UNKNOWN 状态 + 调和器**处理超时未知结果，**Transactional Outbox** 保证业务与通知的最终一致。

完成后你应该能回答：

1. 为什么 `@Transactional` 保证不了 Python 和 Java 一起回滚？
2. 收到超时为什么不能断言"失败"，要落到 UNKNOWN 状态？
3. 工单创建成功但通知失败，工单该回滚吗？

## 2. 本章完成标准（通过门槛）

必须同时满足：

- `idempotency_record` 幂等表实现：相同 Key + 相同 Hash 返回原结果，不同 Hash 返回 409；
- 工单表对业务唯一键设约束，形成"幂等表 + 唯一索引"双保险；
- 跨服务状态机含 `UNKNOWN` 与 `RECONCILING`，超时落调和而非断言失败；
- 通知走 Outbox，数据库事务只写业务与事件，事件 ID 去重；
- 并发、超时、重试下**只有一张工单**，可脚本化断言。

达不到"并发下只有一张工单"，说明幂等键没坐实，先修幂等再谈调和。

## 3. 幂等表设计

幂等表是本章的地基：

```sql
CREATE TABLE idempotency_record (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    idem_key      VARCHAR(128) NOT NULL,
    tenant_id     VARCHAR(64)  NOT NULL,
    operation     VARCHAR(64)  NOT NULL,      -- 如 create_work_order
    request_hash  VARCHAR(64)  NOT NULL,      -- 请求体规范化哈希
    status        VARCHAR(16)  NOT NULL,      -- PROCESSING / COMPLETED
    resource_id   VARCHAR(64),                -- 成功后的工单 ID
    response      CLOB,                       -- 成功响应的快照（脱敏后）
    created_at    TIMESTAMP NOT NULL,
    UNIQUE (idem_key, tenant_id, operation)
);
```

关键点：`idem_key` 由 Python 侧 Adapter 生成（写请求带 `Idempotency-Key`），**模型不能设置**；`request_hash` 保证"同一个 Key 但请求内容不同"时能发现冲突。工单表再对业务唯一键（如 `tenant_id + equipment_id + source_ref`）设约束，形成双保险——即使幂等表因某种原因没挡住，数据库唯一索引是最后一道。

## 4. 幂等处理流程

在**同一事务内**完成占用与写入：

```text
1. BEGIN
2. INSERT idempotency_record (status=PROCESSING)  -- 占用 Key
   → 主键/唯一冲突：
       a. 已有记录 COMPLETED 且 request_hash 相同 → 返回原 response（幂等命中）
       b. 已有记录 COMPLETED 且 request_hash 不同 → 409 E_CONFLICT（Key 被复用）
       c. 已有记录 PROCESSING → 按策略 409 或查询（防并发）
3. 执行业务：建工单 + 业务唯一键约束兜底
4. UPDATE idempotency_record SET status=COMPLETED, resource_id=?, response=?
5. COMMIT
```

Java 侧示例：

```java
@Transactional
public WorkOrderDraft createDraft(CreateDraftCommand cmd, Tenant tenant, String idemKey) {
    IdempotencyRecord existing = idempotencyRepo.find(idemKey, tenant, "create_work_order");
    if (existing != null) {
        if (existing.status().equals("COMPLETED")
                && existing.requestHash().equals(hash(cmd))) {
            return fromResponse(existing.response());      // 幂等命中，不重建
        }
        throw new ConflictException("E_CONFLICT", "idempotency key reused with different request");
    }
    idempotencyRepo.insertProcessing(idemKey, tenant, "create_work_order", hash(cmd));
    WorkOrderDraft draft = repository.saveDraft(WorkOrderDraft.create(cmd, tenant, idemKey));
    idempotencyRepo.complete(idemKey, draft.id(), toResponse(draft));
    return draft;
}
```

Python 侧超时后，用**同一个 Key** 重试或查询 `GET /api/v1/idempotency/{key}`，而不是新 Key 再发一次。

## 5. 跨服务状态机

单服务内的状态机，加上"跨服务结果未知"后必须扩展：

```text
DRAFT -> APPROVED -> SUBMITTING -> SUBMITTED
                    -> UNKNOWN -> RECONCILING -> SUBMITTED/FAILED
```

`UNKNOWN` 是本章最重要的状态：**收到超时不能断言失败**，因为请求可能已在 Java 侧成功，只是响应丢了。调和器（Reconciler）按幂等 Key 查询 Java 的真实状态：

```text
Python 提交超时
  → 落 UNKNOWN
  → 调和器按 idem_key 查 GET /api/v1/idempotency/{key}
     → COMPLETED → 置 SUBMITTED（复用 resource_id）
     → 不存在   → 用同 Key 重试提交（幂等表挡住重复）
     → PROCESSING → 稍后再查（防对方仍事务中）
```

## 6. 超时未知结果：补偿/Saga 而非盲目重试

跨服务一致性靠"状态 + 幂等 + 重试 + 补偿"，不靠分布式事务。分级策略：

| 副作用级别 | 失败/超时处理 |
| --- | --- |
| 只读（get_alarm） | 有限重试 + 退避 |
| 可逆写（建草稿） | 幂等键 + 同 Key 重试/查询 |
| 不可逆写（提交工单） | UNKNOWN → 调和 → 必要时补偿（Saga 回滚动作） |

补偿（Saga）的例子：若调和后确认提交已成功，但后续一个依赖步骤失败，需要执行"撤销提交"这类补偿动作；补偿本身也要幂等、可重试、可审计。**核心原则：超时落"补偿/Saga"而非盲目重试。**

## 7. Transactional Outbox

"工单创建成功、通知失败"不该让工单回滚。Outbox 把"业务写"和"事件发布"放进同一本地事务：

```sql
CREATE TABLE outbox_event (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    event_id   VARCHAR(64) NOT NULL UNIQUE,   -- 消费方按此去重
    event_type VARCHAR(64) NOT NULL,
    payload    CLOB NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

```java
@Transactional
public void submitWorkOrder(String idemKey, ...) {
    WorkOrder wo = submit(idemKey);                 // 业务写
    outboxRepo.save(OutboxEvent.create("work_order_submitted", wo.id(), payload)); // 事件写
    // 二者同事务提交，后台异步发布
}
```

消费方即使重复消费，也按 `event_id` 去重。数据库事务只写业务与事件，异步发布；最终仍失败则告警人工处理，而不是让工单回滚。

## 9. 常见错误与诊断顺序

### 9.1 把超时当失败，直接重试出新 Key

现象：超时后换个新 Key 重发，导致重复建单。**先查**：超时是否落 `UNKNOWN` 状态、是否用同 Key 查询/重试？**不要先做**：无脑 `retry()`——要先确认"未知结果"再决定重试还是调和。

### 9.2 以为 `@Transactional` 能跨服务回滚

现象：Java 提交成功、Python 侧出错，以为 Java 会跟着回滚。**先查**：`@Transactional` 只覆盖 Java 管理的事务资源，跨服务一致性靠状态/幂等/重试/补偿。**不要先做**：试图引入分布式事务——这是反模式。

### 9.3 通知失败就回滚工单

现象：通知没发出去，就把已提交的工单回滚了。**先查**：是否用 Outbox 把事件与业务写同事务提交？**不要先做**：让业务动作依赖通知成功——通知是最终一致，不是强一致。

### 9.4 幂等键由模型或客户端随意生成

现象：幂等键不稳定，同一请求两次生成两个 Key。**先查**：Key 由 Adapter 生成且与请求语义绑定，模型不能设置。**不要先做**：信任模型传入的 Key。

## 10. 练习题与答案

### 练习 1：`@Transactional` 能保证 Python 和 Java 一起回滚吗？

**答案：**不能。它只覆盖 Java 管理的事务资源；跨服务通过状态、幂等、重试与补偿实现一致性，不靠分布式事务。

### 练习 2：工单创建成功、通知失败如何处理？

**答案：**工单不应回滚；Outbox 保存待发事件，后台重试，最终仍失败则告警人工处理，而不是让业务动作依赖通知成功。

### 练习 3：收到超时为什么不能断言"失败"？

**答案：**因为请求可能已在 Java 侧成功、只是响应丢失。应落 `UNKNOWN` 状态，由调和器按幂等 Key 查询 Java 真实状态，再决定置 `SUBMITTED` 还是补偿。

### 练习 4：幂等表和业务唯一键为什么都要？

**答案：**幂等表负责"同 Key 同请求"的精确命中与占用；业务唯一键是数据库层最后一道兜底，即使幂等表逻辑有漏洞，唯一索引也能挡住重复业务记录，形成双保险。

## 11. 工程挑战

1. 写并发测试：两个线程同时用相同 Key 提交，断言只有一张工单、另一路命中幂等或 409；
2. 写"成功后超时"集成测试：Java 提交成功后主动延迟响应，验证调和器最终置 `SUBMITTED` 且不重复；
3. 写 Outbox 重试测试：消费方模拟重复消费，断言按 `event_id` 去重、只处理一次。

参考方向：并发测试用两个事务竞争同一 `idem_key`；超时测试用延迟响应制造 `UNKNOWN`；Outbox 测试断言事件处理幂等。

## 12. 面试追问

### 12.1 "你们的工单提交怎么保证不重复？"

回答框架：幂等表 + 业务唯一键双保险；写请求带 `Idempotency-Key`（Adapter 生成，模型不设），同 Key 同 Hash 返回原结果、不同 Hash 409；数据库唯一索引兜底，并发下只有一张工单。

### 12.2 "跨服务怎么保证一致性？"

回答框架：不用分布式事务。只读有限重试、可逆写靠幂等、不可逆写落 `UNKNOWN` + 调和 + 补偿（Saga），通知走 Transactional Outbox 最终一致。

### 12.3 "超时了你们怎么办？"

回答框架：不盲目重试。落 `UNKNOWN` 状态，调和器按幂等 Key 查询 Java 真实状态：`COMPLETED` 复用结果、不存在才用同 Key 重试、`PROCESSING` 稍后再查。
