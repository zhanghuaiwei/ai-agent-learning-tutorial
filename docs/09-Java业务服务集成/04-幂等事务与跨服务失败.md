# 幂等、事务与跨服务失败

> 预计 7 小时｜产出：Java 业务服务的恰好一次“业务效果”。

## 1. 幂等表

`idempotency_record` 保存 Key、tenant、operation、request_hash、status、resource_id、response、created_at。工单表对业务唯一键再设约束，形成双保险。

处理流程：事务内尝试占用 Key → 相同 Hash 且已完成则返回原结果 → 处理中按策略 409/查询 → 不同 Hash 409 → 建工单并保存结果 → 提交。Python 超时后用同 Key 重试或查询。

## 2. 跨服务状态

```text
DRAFT -> APPROVED -> SUBMITTING -> SUBMITTED
                    -> UNKNOWN -> RECONCILING -> SUBMITTED/FAILED
```

`UNKNOWN` 是重要状态：收到超时不能断言失败。调和器按幂等 Key 查询 Java。通知使用 Outbox，数据库事务只写业务与事件，异步发布；即使重复消费也按事件 ID 去重。

## 3. 项目任务

在 Java 提交事务成功后主动延迟响应让 Python 超时；验证调和后只有一张工单。再测试相同 Key 不同请求、并发相同 Key、数据库回滚。

## 4. 练习与答案

### 练习 1：`@Transactional` 能保证 Python 和 Java 一起回滚吗？

**答案：**不能。它只覆盖 Java 管理的事务资源；跨服务通过状态、幂等、重试与补偿实现一致性。

### 练习 2：工单创建成功、通知失败如何处理？

**答案：**工单不应回滚；Outbox 保存待发事件，后台重试，最终仍失败则告警人工处理。

## 5. 验收与资料

并发和超时不重复创建，状态可调和。参考 [Spring Transactions](https://spring.io/guides/gs/managing-transactions/)、[Transactional Outbox](https://microservices.io/patterns/data/transactional-outbox.html)。
