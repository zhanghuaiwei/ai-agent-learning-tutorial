# 西安岗位检索与 JD 能力映射

> 预计 4 小时｜目标：建立「动态收集 JD → 拆解岗位族与能力优先级 → 识别真实缺口 → 映射教程章节」的可复用检索闭环，而不是记下几个职位名。

> **阅读前置**：投递准备专题，属于第 11 阶段（面试准备）。与 08 章《岗位证据矩阵》互为表里——08 章回答"我有什么证据"，本章回答"市场要什么、我还差什么"。建议先读 08 章建立个人证据总表，再回到本章做 JD 采样与能力映射。

## 1. 本章从哪里开始

前端/全栈转 Agent 后端的学习者，最容易犯一个检索错误：**只搜一个职位名**。于是"Agent 工程师"搜不到时，就误以为市场没有岗位。真实情况是——岗位名由 HR 随手写，岗位族才由职责决定。

本章要解决三件事：

1. 一个职位的**标题不能决定它的岗位族**：名为"AI 应用研发"的岗位，职责可能全是 vLLM、GPU 调度和 K8s，那它属于推理 Infra，不是你的主投对象；
2. 一条 JD 的**关键词不能直接等于录用门槛**：P0（必需）和 P1/P2（加分）要拆开看，不能看见"了解 Dify"就立刻推翻主线；
3. 市场高频能力的**真实缺口**要用频率说话：某技能在目标样本中高频出现、且作品无法证明，才进入补缺；低频技术不配打乱主线。

完成后你应该能回答："在西安或全国范围内，我的主投岗位族是哪几类？每类的 P0 能力是什么？我的作品分别能证明哪些、缺口在哪几章？"

## 2. 本章完成标准（通过门槛）

- 至少采样 **20 条 JD 快照**，每条含采样日期与来源链接；
- 每条 JD 完成**岗位族分类**（应用开发 / Agent 平台 / 算法 / 推理 Infra / 解决方案）；
- 输出**能力优先级表**，把高频能力标为 P0/P1/P2；
- 输出**教程章节映射表**，每个高频能力都能指到对应章节的证据或补缺计划；
- 至少识别出 1 个"高频但作品无证据"的真实缺口，并写清补缺决策（补 or 不补，理由）。

## 3. 岗位族先于职位名

职位名是噪声，岗位族才是信号。先按职责把目标样本归入五类，再决定主投/观察/放弃：

| 岗位族 | 典型职责 | 对学习者的定位 |
| --- | --- | --- |
| 应用开发 | 用 LLM 做问答/Agent/知识库/工具调用，交付业务功能 | **主投**：与 M0～M6 主线直接对齐 |
| Agent 平台 | 做编排、Tool/MCP 接入、多租户、评测与治理底座 | 观察：与 M6/系统设计能力部分对齐，需平台化视角 |
| 算法/微调 | 模型训练、微调、蒸馏、数据工程 | 放弃或降权：本教程偏应用，无训练证据 |
| 推理 Infra | vLLM、GPU 调度、K8s、显存与吞吐优化 | 放弃或降权：除非已有真实部署证据 |
| 解决方案 | 需求分析、行业落地、售前、交付 | 部分主投：可复用产品交付经验，但技术主体仍是后端 |

分类不是为了贴标签，而是为了在有限时间里**把简历定制和补缺顺序排出来**。同一个职位可能横跨两类，以"职责动词"和"必需项"为准。

## 4. 搜索词与采样节奏

### 4.1 组合搜索词

单一"Agent 工程师"覆盖不全。用组合词反复采样：

```text
大模型应用开发 / AI 应用工程师 / 智能体 / Agent / RAG / 知识库
LLM 工程师 / AI 平台 / Python 后端含 AI / Java·Python AI 集成 / 解决方案研发
+ 西安（或目标城市）
```

同时观察 Python 后端含 AI、Java/Python AI 集成、解决方案研发岗位——很多 Agent 岗位藏在"后端工程师"标题下。

### 4.2 采样频率

| 阶段 | 频率 | 目的 |
| --- | --- | --- |
| 建立基线 | 每两周采样 10 条 | 摸清岗位族分布与能力词频 |
| 临近投递 | 每周 15 条 | 捕捉最新 JD 变化，校准简历关键词 |

### 4.3 JD 快照字段

每条 JD 至少保留以下字段（过期 JD 保留快照与采样日期，不删）：

```markdown
公司/行业/职级/职责/必需/加分/学历/年限
技术词/业务词/缺口/作品证据/投递状态/日期/链接
```

### 5.2 匹配分只用于排序

```text
硬门槛不满足且不可协商 → 谨慎/不投
P0 已证明：每项 2 分
P0 已实践：每项 1 分
P1 已证明：每项 1 分
有同业务场景：加 2 分
需要伪造经历才能匹配：直接不投
```

分数不是录用概率，只用于决定"这条 JD 值得花多少时间定制简历"。

## 6. 能力映射：市场能力 → 教程证据

截至最近公开样本，西安/全国 Agent 应用岗的高频能力与教程证据对应如下（方向证据，不代表后续岗位数量，投递期必须重新采样）：

| JD 高频能力 | 本课程证据 | 能力优先级 |
| --- | --- | --- |
| Python/FastAPI/异步 | M0 API、超时、取消、测试 | P0 |
| Redis/MQ/后台任务 | 摄取 Job、重复投递、Outbox 与 DLQ | P0 |
| LangChain/Tool | M2 工具助手 | P0 |
| RAG/向量库 | M3 分层评测报告 | P0 |
| LangGraph/Workflow | M4 暂停恢复与幂等 | P0 |
| 评测/优化 | M5 Dataset/Experiment | P0 |
| 工程部署 | M6 CI、故障、成本、安全 | P1 |
| Dify/低代码平台 | 同一流程的 Dify/LangGraph 对照 ADR | P1 |
| 模型原理/微调/推理边界 | 模型选型卡与微调决策 ADR | P2 |
| 企业集成 | Java API/MCP Adapter | P1 |
| 需求到上线 | RFC、Readiness Review、回滚演练与验收纪要 | P0 |

第二轮样本还反复出现 FastAPI、SQL/Redis、分布式任务/MQ、Dify、部署排障、需求分析和技术文档——这些大多已落在上表，未覆盖的进入补缺评估。

## 7. 真实缺口识别与补缺决策

### 7.1 频率阈值

若 30 条目标 JD 中某技能出现 **≥30%** 且作品无法证明，进入补缺；低于阈值的低频技术不追，不因此打乱主线。

### 7.2 补缺三问

每个缺口补之前先问：

1. 它是否出现在**必需项**而非加分项？
2. 它在目标岗位族里是否**稳定高频**（跨多次采样、跨多家公司）？
3. 补它是否会**挤占 Agent 核心**的时间？

三问都满足才补，且补缺产物必须回到项目（代码/测试/ADR），而不是收藏文章。

## 8. 西安与全国样本的方向性结论

政策与产业方向（通用描述，非岗位承诺）：未来政策方向明确提到"算力 + 高质量数据集 + 大模型 + AI 应用"、行业大模型和智能体、AI+制造；同时商业航天、低空、智能制造、文旅等有场景。

对作品选题的启示：选择工业设备维护，既能覆盖通用企业知识/流程，又能映射当地制造和空天产业，但**不把求职限制在单行业**。用"业务问题 → 工程深度"表达项目，而不是"我只懂设备维护"。

> 注意：本教程**不编造具体公司的具体 JD 或薪资数字**，也不把某次公开样本当成长期结论。方向性判断只用于选题和补缺优先级，投递前必须重新采样，以当周真实 JD 为准。

## 项目任务

1. 用组合搜索词在西安/目标城市采样 20 条 JD，每条填完整快照字段并分类岗位族；
2. 建立能力优先级表，把高频能力标为 P0/P1/P2；
3. 对照 08 章个人证据总表，标记每个 P0 能力的证据状态（已证明/已实践/已理解/未掌握）；
4. 找出 1 个"高频但无证据"的缺口，写补缺三问的结论与 48 小时计划；
5. 输出一张"岗位族 → 主投/观察/放弃 → 下一步动作"的决策表。

## 常见错误与诊断顺序

### 9.1 把标题当岗位族

看到"AI 应用研发"就主投，结果职责全是 vLLM/K8s。诊断顺序：先读"职责动词"与"必需项"，再分类岗位族；标题只作为初筛，不作匹配依据。

### 9.2 把加分项当必需项逼自己补

JD 写"加分：了解 Dify"，就立刻改主线去学 Dify。正确做法是看频率和"必需/加分"标注，先补 P0 必需，加分项只在有富余时用对照实验覆盖。

### 9.3 只搜一个职位名

搜不到"Agent 工程师"就下结论没市场。正确做法是组合词 + 拆岗位族，很多 Agent 岗藏在"后端/平台/解决方案"标题下。

### 9.4 把某次公开样本当长期结论

拿着几个月前的 JD 快照决定投递方向。正确做法是保留采样日期，临近投递重新加密采样，以当周真实 JD 校准。

## 练习题与答案

### 练习 1：JD 写 vLLM/K8s，是否立刻改主线？

**答案：**先看目标样本频率和"必需/加分"标注。本课程低配且偏应用，先能解释部署边界即可；若 vLLM/K8s 成为高频**必需**，再安排受控补充，不牺牲 Agent 核心主线。

### 练习 2：已有前端/全栈经验如何定位？

**答案：**作为产品交付、协议、SSE/状态和用户体验优势；简历主叙事仍是"后端 Agent 可靠性"，不把自己写成只会接模型的工程师。

### 练习 3：JD 标题是"AI 应用研发"，职责全是 vLLM、GPU 调度和 K8s，属于主投吗？

**答案：**标题不能决定岗位族。该职责更接近推理 Infra/AI 平台底座，不是默认主投；除非已有真实部署与调优证据，否则降低匹配，而不是在简历堆关键词。

### 练习 4：某技能在 3 条 JD 里都出现，要不要补？

**答案：**看样本量——3 条样本里的"高频"不可靠。至少积累 20～30 条目标样本，某技能出现 ≥30% 且作品无证据，才进入补缺；否则列为观察项。

## 工程挑战

1. 把 20 条 JD 的关键词用脚本统计词频，输出 Top 20 技术词/业务词（区分必需 vs 加分）；
2. 对同一条 JD 做"标题分类"与"职责分类"，记录两者不一致的比例，验证"标题不能决定岗位族"；
3. 写一个 `jd_gap.py` 脚本：输入 JD 能力列表 + 个人证据矩阵（08 章），输出"有证据/无证据/部分证据"三组，并标出 ≥30% 频率的缺口；
4. 为补缺决策写一条 ADR，记录"高频缺口 → 补缺三问 → 结论"，证明你不是靠感觉决定补什么。

## 面试追问

1. 你为什么投西安/这个方向，而不投纯算法或纯后端？
2. 你如何判断一条 JD 值不值得定制简历？
3. 目标岗位族里，哪些能力是 P0、哪些是加分？
4. 你的项目与目标 JD 的差距在哪？怎么补？
5. 如果 JD 要求的技术栈你完全没有，你会怎么写简历？
