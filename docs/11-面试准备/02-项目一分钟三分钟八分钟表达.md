# 项目一分钟、三分钟、八分钟表达

> 预计 6 小时｜目标：把智维 Agent 项目压缩成 1/3/8 分钟三个可脱稿版本，每个技术名都能指到代码/测试/报告证据。

> **阅读前置**：第 11 阶段（面试准备）表达训练。前置依赖：M0～M6 项目证据已可复跑、08 章证据矩阵已填充。本章不教新内容，只教"把已有证据说清楚"——表达本身不是背词，是证据的现场检索。

## 1. 本章从哪里开始

很多人以为"讲项目"就是背一段自我介绍。面试官真正检验的是：**你说的每一句技术断言，能不能被追问到证据**。同样的架构，说"用了 RAG"和说"混合检索 + rerank，Recall@K 见 M3 报告，越权靠服务端 ACL 过滤"是两种可信度。

本章要解决三件事：

1. 把项目压缩成三个时长版本，每个版本都在时限内**有结论地结束**；
2. 建立"表达句 → 证据指针"的映射，让每句话都落得回代码、测试或报告；
3. 用录音回听消灭"然后、就是、调用一下"这类模糊表达，改成能解释**选择代价**的表达。

## 2. 本章完成标准（通过门槛）

- 1/3/8 分钟三个版本均能**脱稿、在时限内结束**；
- 每个技术名（LangChain/LangGraph/RAG/MCP/评测/幂等）都能指到代码、测试或报告；
- 每个版本都按"业务问题 → 约束 → 关键设计 → 量化证据 → 你的贡献 → 局限"的顺序推进；
- 至少**录音两次**并回听，统计模糊词、超时、无证据断言，逐项消除。

## 3. 表达的统一骨架

无论时长多少，都用同一顺序，只是每一段的展开深度不同：

```text
业务问题 → 约束 → 关键设计 → 量化证据 → 你的贡献 → 局限
```

- **业务问题**：维修人员查手册慢、告警与工单割裂、高风险工单需要审批；
- **约束**：企业文档有版本/页码/权限；写操作要有审批和幂等；不能只靠 Prompt 守安全边界；
- **关键设计**：混合 RAG 提供带证据的引用；LangGraph 编排告警查询、诊断、工单草稿、审批与幂等提交；
- **量化证据**：分层评测（Recall@K/忠实度/工具选择准确率/越权拦截率/任务终止率）、P95、费用观测；
- **你的贡献**：独立完成主线，说清"我做了什么决策、为什么"；
- **局限**：这是企业级模拟项目，非生产上线，指标来自冻结评测集，不是真实用户量。

## 4. 每句话都能指到证据（呼应 08 章）

08 章证据矩阵是本章的"弹药库"。表达时任何一句技术断言都必须能立刻指到证据，否则删掉或改口为"实践/了解"：

| 表达句 | 证据指针 | 追问准备 |
| --- | --- | --- |
| 工具按角色动态暴露 | `tool_filter.py` + `required_scope` | 越权为何不靠 Prompt |
| 写工单有审批 + 幂等 | 审批表 + `idempotency_key` + 唯一约束 | 超时未知结果怎么处理 |
| 混合 RAG + 引用 | M3 分层评测报告 | Recall@K 是多少、怎么测 |
| 故障恢复不重复建单 | 故障注入测试 + 调和器 | Java 成功后网络超时场景 |
| SSE 12 事件 | `stream_adapter` + 终态互斥测试 | 断线取消怎么处理 |
| 费用只观测 + 告警 | M6 成本报告 | 异常增长怎么告警 |

面试中若被追问到"证据不足"的一项，诚实说边界，而不是临时编数字。

## 5. 一分钟版本

> 我做的是工业设备维护知识与工单协同 Agent。它不是普通聊天机器人：先用混合 RAG 提供带版本、页码和权限的证据，再用 LangGraph 把告警查询、诊断、工单草稿、人工审批和幂等提交编排成可暂停恢复的流程。我对工具权限、Prompt Injection、跨租户、重复提交做了硬门禁，并用 LangSmith 数据集分别评检索、回答和轨迹。Python 是 Agent 主服务，可选 Spring Boot 服务拥有业务事务。最终指标我会按实际报告填写，不夸大线上规模。

一分钟版本的关键：**一句业务价值 + 两个差异点 + 一个可量化结果 + 一个局限声明**。不要试图塞下所有技术名，留出"邀请对方追问"的钩子。

## 6. 三分钟版本

一分钟基础上，增加三段"选择与证据"：

1. **为什么选 Hybrid RAG 与 Graph，而不是单 Agent**：单 Agent 适合一次工具调用；本项目的工单流程跨请求、含人工审批、需要恢复，因此用 LangGraph 显式 State/Node/Edge，审批用 Interrupt 暂停。这是"业务推出架构"而不是"先选框架"。
2. **最难故障：Java 成功后网络超时**：写操作超时是"结果未知"，不能盲目重试；用幂等键查询业务服务、加唯一约束和调和器，避免重复工单。这条要能对应故障注入测试。
3. **数据与局限**：Recall@K、引用忠实度、越权/重复为零、P95、费用观测，以及已知局限（合成评测集、非生产流量）。

三分钟版本的时间分配建议：业务 30 秒、架构 40 秒、RAG 40 秒、Graph/审批/恢复 50 秒、证据与局限 20 秒。

## 7. 八分钟版本

按最终演示脚本展开，每段预判面试官可能打断的位置：

| 段 | 时长 | 内容 | 可被追问点 |
| --- | ---: | --- | --- |
| 领域与边界 | 1 分钟 | 业务问题、范围、做什么不做什么 | 为什么选设备维护 |
| 架构 | 1 分钟 | API/Agent/RAG/审批/业务服务分层 | 数据所有权 |
| RAG | 1.5 分钟 | 摄取、混合检索、引用、删除 | ACL/版本/删除 |
| Graph/审批/恢复 | 2 分钟 | Checkpoint、Interrupt、幂等、调和 | 崩溃恢复时间线 |
| 评测安全成本 | 1.5 分钟 | 分层指标、红队、费用观测 | Judge 偏差 |
| 故障故事和局限 | 1 分钟 | 一次真实故障 + 已知局限 | 为什么不夸大 |

每段结束都留一个"邀请追问"的落点，而不是一口气说到时间结束。

## 8. 结构卡片方法

不要背词，用结构卡片。每张卡片只写关键词和证据指针，不写完整句子：

```text
卡片1 业务问题：查手册慢 / 告警工单割裂 / 高风险审批
卡片2 约束：版本页码权限 / 审批幂等 / 不用Prompt守安全
卡片3 架构：RAG证据 + Graph编排 + 审批 + 幂等提交
卡片4 证据：分层评测 + P95 + 费用观测（无累计上限）
卡片5 局限：合成评测集 / 非生产流量 / 下一步
```

卡片强迫你"现场组织语言"而不是"复读背稿"，也让不同时长版本能共用同一套卡片。

## 9. 录音回听检查清单

每周录音两次，回听时逐项打勾：

- [ ] 是否出现"然后、就是、调用一下、差不多"等模糊表达；
- [ ] 是否在规定时限内结束（不拖、不赶）；
- [ ] 每个技术名是否都能指到证据；
- [ ] 是否解释了**选择代价**（为什么 Graph 而非单 Agent、为什么不是多 Agent）；
- [ ] 是否如实声明局限（非生产、合成评测集），不夸大用户量/规模。

## 常见错误与诊断顺序

### 10.1 堆技术名但不指证据

说"用了 LangChain、LangGraph、RAG、MCP"却不说明各解决什么问题。诊断顺序：先删掉无法指到证据的技术名，再为每个留下的技术名补一句"它解决什么 + 证据在哪"。

### 10.2 背稿而非结构卡片

背稿遇到打断就断片。诊断顺序：改成结构卡片，每次现场组织语言，练"被打断后从卡片继续"。

### 10.3 夸大线上规模

把个人项目说成"上线了多少用户"。诊断顺序：统一口径为"企业级模拟项目 + 合成评测集 + 非生产流量"，指标只报可复现数字。

### 10.4 只讲 happy path，不讲失败

只讲功能演示，不讲超时、重复、越权、注入。诊断顺序：每个版本至少带一个失败/边界点（如"Java 成功后网络超时"），证明你理解失败路径。

## 练习题与答案

### 练习 1：面试官只有 30 秒怎么办？

**答案：**一句业务价值 + 两个差异点（可恢复工作流、分层评测）+ 一个可量化结果 + 一个局限声明，最后邀请对方选择想深入的部分。

### 练习 2：被问真实用户量怎么办？

**答案：**明确这是企业级作品而非生产上线，给测试规模和方法，不伪造用户；说明上线前还需真实场景验证。指标来自冻结评测集，不冒充生产流量。

### 练习 3：一分钟版本里，哪个技术名可以删掉？

**答案：**凡不能指到证据、也不构成差异点的技术名都可删。一分钟版本只留"业务价值 + 两个差异点 + 一个结果"，其余放进三/八分钟或等待追问。

### 练习 4：被打断"你为什么不用多 Agent"怎么接？

**答案：**回到"职责/权限/上下文是否可隔离且能独立评测"的判据，说明当前单主图 + 子图即可表达，多 Agent 会增加 Prompt、上下文、终止、评测与成本；只有对照评测证明收益才拆分。

## 工程挑战

1. 为每个版本写一份"表达句 → 证据指针"清单，逐句链接到仓库路径或报告，漏一处就补一处；
2. 用结构卡片重新讲三分钟版本三次，记录每次语言差异，证明是"组织"而非"背稿"；
3. 把"Java 成功后网络超时"讲成 40 秒的失败时间线（发起 → 超时 → 查询幂等 → 调和 → 终态），并对应到故障注入测试；
4. 录一段三分钟版本，逐字统计模糊词次数，目标降到 0。

## 官方资料与中文阅读指引

- [Google Technical Writing](https://developers.google.com/tech-writing)：看"先说结论、动词精确、删冗余"的写作原则，迁移到口头表达；
- [GitHub 写作指南](https://docs.github.com/get-started/writing-on-github)：结构化表达与清晰层次，用于脚本与结构卡片；
- [Star Method](https://www.themuse.com/advice/star-interview-method)：STAR 是行为题骨架，本章表达骨架与之同构（业务问题=情境，关键设计=行动，量化证据=结果）。

阅读指引：英文材料只看"结构原则"，不逐字翻译；口头表达的核心证据仍来自你自己的项目（M0～M6 报告、ADR、测试），官方材料只帮你组织，不提供可背的答案。
