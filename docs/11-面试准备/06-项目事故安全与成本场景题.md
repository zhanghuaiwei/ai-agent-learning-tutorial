# 项目事故、安全与成本场景题

> 预计 5 小时｜目标：用 STAR+R 把失败恢复、越权、注入、费用失控四类场景讲成"有证据、可复测"的回答，任何结论都来自真实练习而非背模板。

> **阅读前置**：第 11 阶段（面试准备）压力面训练。前置依赖：M6 的故障注入、安全红队与成本观测报告。使用 STAR+R：Situation、Task、Action、Result、Reflection；结果必须来自真实练习。

## 1. 本章从哪里开始

面试官给一个事故场景，考察的不是"你知道什么"，而是"你按什么顺序想、把风险控制在哪一层、事后怎么证明"。四类高频场景——失败恢复、越权、注入、费用失控——都对应教程里踩过或演练过的真实边界。

本章把每类场景拆成"完整 STAR+R 骨架 + 必答证据清单"。你要做的不是背答案，而是把每个 Action 对应到自己的故障注入测试、安全红队用例和成本观测报告。

## 2. 本章完成标准（通过门槛）

- 四类场景各能**脱稿两分钟**完成 STAR+R；
- 每个回答包含四类证据：用户/业务影响、技术 Trace/指标、数据一致性或安全检查、修复后的自动回归与监控；
- 承认"没有真实生产经历"时，明确说这是**故障注入演练**，不冒充事故；
- 费用失控场景讲清"根因 + 观测告警"，且**不设固定金额上限**。

## 3. 场景一：模型费用失控

### STAR+R

- **S（情境）**：监控发现某个租户/版本的模型调用费用异常增长，比如短时间翻了数倍；
- **T（任务）**：在不中断核心业务的前提下定位根因、止血、回归质量并建立长期观测；
- **A（行动）**：先用 Feature Flag 限制非核心任务；按版本、租户、模型、重试和步骤分解；检查循环、Prompt 变长、缓存失效、流量异常；修复后回归质量；增加步骤/Deadline 边界、调用风暴保护和费用异常告警；
- **R（结果）**：费用回落、质量门禁通过、告警上线；
- **R（反思）**：费用失控的根因往往不是"模型太贵"，而是**循环、无效重试、上下文膨胀或缓存失效**；因此要观测每次调用归因到租户/版本/步骤，并对异常增长告警，而不是事后设一个固定金额上限去卡——因为正常业务量本来就会变化，固定金额上限会误伤增长或漏掉缓慢泄漏。

### 必答证据清单

- 成本按租户/版本/步骤/模型的可观测归因；
- 循环检测与执行边界（最大步数/Deadline/Token）是否真的生效；
- 异常增长告警的阈值如何定义、如何避免误报；
- 修复后的质量回归数据。

## 4. 场景二：RAG 返回其他租户文档（越权）

### STAR+R

- **S**：用户查询时，回答里出现了其他租户的文档片段；
- **T**：按最高等级数据事件处理，隔离相关检索、保全证据、确认影响；
- **A**：修复服务端 ACL 过滤与索引命名空间；清缓存；通知流程按规定执行；加入跨租户硬门禁和持续审计。**不要只加 Prompt**；
- **R**：越权检索被确定性拦截，负向测试通过；
- **R（反思）**：越权拦截必须落在检索前过滤 + 存储层隔离 + 返回前验证，不能先取回跨租户 Chunk 再让模型"忽略"。

### 必答证据清单

- 越权拦截率 100% 的负向测试用例（跨租户/跨工厂/伪造 `tenant_id`）；
- ACL 过滤与索引命名空间的服务端实现路径；
- 缓存清理与审计日志。

## 5. 场景三：工单重复创建（失败恢复）

### STAR+R

- **S**：用户只点了一次，却出现两张相同的工单草稿；
- **T**：停止自动提交，查影响范围并补偿；
- **A**：按幂等键查询影响并补偿；根因通常是**成功响应丢失 + 无唯一约束/多层重试**；修复业务幂等记录、状态 UNKNOWN 和调和器；
- **R**：重复创建归零，故障注入测试通过；
- **R（反思）**：写操作超时是"结果未知"，不能盲目重试；唯一约束是幂等的最后防线之一，业务幂等记录和调和器共同兜底。

### 必答证据清单

- `idempotency_key` + 唯一约束的实现；
- "Java 成功后网络超时"的故障注入测试；
- 调和器如何把 UNKNOWN 状态收敛到终态。

## 6. 场景四：Prompt Injection 触发危险 Tool（注入）

### STAR+R

- **S**：一段不可信文本诱导 Agent 调用写操作或高危工具；
- **T**：禁用 Tool/连接，审计动作，阻断并复盘；
- **A**：权限最小化、文档不可信标记、参数验证、可信审批、输出限制；将载荷加入红队集。承认注入无法只靠识别文本彻底消除；
- **R**：注入用例被拦截，高危动作未发生；
- **R（反思）**：System Prompt 只是软约束，真正的防线是权限最小化、审批和确定性校验。

### 必答证据清单

- 权限最小化（工具 `required_scope`）与审批（`approval.required`）；
- 红队集里的注入载荷与负向测试结果；
- 输出限制与审计。

## 7. 场景五：LLM Judge 指标很好但人工不满意（评测）

### STAR+R

- **S**：自动评测通过，但人工验收觉得答案不行；
- **T**：定位 Judge 与真实满意度的偏差；
- **A**：抽样校准 Judge、检查 Rubric 与数据分布；引入人工金标和规则评测；按分组定位偏差，不直接用更多 Judge 掩盖问题；
- **R**：定位到偏差分组，调整 Rubric 后指标与人工一致；
- **R（反思）**：Judge 是评测工具，不是真理；分层评测（Recall@K/忠实度/工具选择准确率）比单一"准确率"更能定位问题。

### 必答证据清单

- Judge 抽样校准记录；
- 人工金标与规则评测的对照；
- 按分组（租户/任务类型/难度）的偏差定位。

## 项目任务

1. 为四类场景各写一份 STAR+R 脚本，每份至少一处标注"这是故障注入演练，非生产事故"；
2. 每个场景补一份"必答证据清单"，逐项链接到代码/测试/报告路径；
3. 把"费用失控"场景的观测告警阈值设计写进 M6 成本观测，确认**不设固定金额上限**；
4. 每类场景录两分钟口述，回听检查是否四类证据齐全、是否夸大生产经历；

## 常见错误与诊断顺序

### 9.1 把演练说成真实事故

没有生产经历却用"线上炸了"开头。诊断顺序：统一口径"这是故障注入演练/企业级模拟项目"，只报可复现的测试证据。

### 9.2 费用失控只说"加预算"

把费用失控的应对说成"调高金额上限"。诊断顺序：先讲根因（循环/重试/上下文膨胀/缓存失效），再讲观测与异常告警，**不设固定金额上限**。

### 9.3 越权只加 Prompt

说"让模型注意不要跨租户"就完事。诊断顺序：落到服务端 ACL 过滤 + 索引命名空间 + 返回前验证，附越权拦截率 100% 的负向测试。

### 9.4 注入承诺"彻底识别"

说"我们能完全识别注入文本"。诊断顺序：改成"注入无法只靠识别文本彻底消除"，防线是权限最小化 + 审批 + 确定性校验。

## 练习题与答案

### 练习 1：每个场景录制两分钟回答，必须包含哪四类证据？

**答案：**用户/业务影响、技术 Trace/指标、数据一致性或安全检查、修复后的自动回归与监控。没有真实生产经历时明确说是故障注入演练。

### 练习 2：费用突然涨 5 倍，第一步是调高预算吗？

**答案：**不是。先止血（Feature Flag 限非核心任务），再按租户/版本/模型/步骤分解定位根因（循环、重试、上下文膨胀、缓存失效），修复后回归质量，再上异常增长告警；不设固定金额上限去卡。

### 练习 3：越权拦截为什么不能先取回跨租户 Chunk 再让模型忽略？

**答案：**取回本身已是泄露，模型还可能被注入诱导而"忽略"指令。正确做法是检索前过滤 + 存储层隔离 + 返回前验证，让越权数据根本不进入模型上下文。

### 练习 4：写操作超时后，为什么不能直接重试？

**答案：**超时意味着"结果未知"——可能已成功也可能未提交。先按幂等键查询业务服务，确认状态后再决定；配合唯一约束和调和器把 UNKNOWN 收敛到终态，避免重复工单。

## 工程挑战

1. 为"费用失控"写一个可观测脚本，把每次模型调用归因到租户/版本/步骤/模型，输出异常增长告警（不设固定金额上限）；
2. 为"Java 成功后网络超时"写一个故障注入测试，证明同一 `idempotency_key` 不产生重复工单；
3. 为"Prompt Injection 触发危险 Tool"补一个最小权限测试，证明即使模型被诱导调用 `create_work_order_draft`，无审批/无权限时也不会落地；
4. 为 LLM Judge 做一个抽样校准，把 Judge 打分与人工金标对照，定位偏差分组。

## 面试追问

1. 你说费用失控根因是循环，怎么证明是循环而不是流量上涨？
2. 跨租户越权拦截，你在哪一层、用什么机制保证 100%？
3. 重复工单的根因里，"成功响应丢失"和"无唯一约束"谁更致命？
4. 注入载荷绕过了你的文本过滤，怎么办？
5. Judge 指标和人工不一致，你会不会再加一个更强的 Judge？
