# 岗位证据矩阵、简历筛选与投递门槛

> 使用时间：第 1 周建立，第 10/18/23 周更新，投递期每周更新｜目标：把“学过”转换成招聘方可以检查的工程证据。

> **阅读前置**：投递准备专题。第 1 周即建立空矩阵，随 M0～M6 里程碑逐项填充证据（每个里程碑的复盘归档直接对应矩阵的一行）；第 10/18/23 周与投递期更新。

## 1. 三种状态不能混写

每项技能只能标一种：

| 状态 | 定义 | 简历能否写项目能力 |
| --- | --- | --- |
| 已证明 | 有代码、测试、报告、演示且能独立追问 | 可以，写清范围和结果 |
| 已实践 | 完成小实验，尚未进入主项目/生产级验证 | 谨慎写“实践/了解”，面试主动说明边界 |
| 已理解 | 阅读并能解释，但没动手 | 通常不放技能栏，可用于回答选型 |
| 未掌握 | 不能解释或实现 | 不写，建立补缺计划 |

“熟悉、掌握、精通”没有统一标准，优先写动作与证据。


### 3.1 匹配分只用于排序

```text
硬门槛：不满足且不可协商 → 谨慎/不投
P0 已证明：每项 2 分
P0 已实践：每项 1 分
P1 已证明：每项 1 分
有同业务场景：加 2 分
需要伪造经历才能匹配：直接不投
```

分数不是录用概率，只用于有限时间下决定简历定制和补缺顺序。匹配度不是越高越好；岗位描述也可能不完整。

## 4. 已有工作经验如何转换

可以迁移的证据：

- 复杂产品从需求到上线；
- TypeScript 类型与 API Contract；
- SSE/WebSocket、状态、错误与用户反馈；
- 性能、监控、灰度和故障处理；
- 代码评审、CI、跨团队协作；
- 安全呈现：不暴露 Chain-of-Thought/Secret，审批 UX。

不能自动迁移：

- Python 语言深度、asyncio 失败语义；
- 数据库事务与索引；
- Redis/MQ/Worker；
- Agent/RAG/Eval；
- 后端部署和容量。

简历叙事：**软件产品交付经验 + 可验证的 Python Agent 后端项目**，而不是只写“会调 API”。

## 5. 项目简历条目公式

```text
业务问题 + 本人动作 + 关键约束/架构 + 可复现结果 + 证据范围
```

弱表达：

> 使用 LangChain、LangGraph、RAG、MCP 开发智能 Agent。

可追问表达：

> 独立构建设备维护知识与工单协同 Agent：以 LangGraph Checkpoint/Interrupt 管理跨请求审批，业务写入由幂等 API 和资源级授权控制；建立检索、引用、Tool 轨迹与越权分层评测，并用故障注入验证重复恢复不产生重复工单。

加入数值前确认：

- Dataset 数量与来源可解释；
- Baseline 和新版本使用相同数据；
- 指标定义准确；
- 结果可通过命令复现；
- 不把合成负载写成真实生产流量；
- 不把个人项目写成公司上线项目。

## 6. GitHub 项目证据结构

```text
README.md
docs/
  architecture/
  adr/
  api/
  threat-model/
  runbooks/
  career/evidence-matrix.md
reports/
  eval/
  load/
  security/
  incidents/
src/
tests/
scripts/
.github/workflows/
```

README 第一屏回答：问题、角色、主要能力、架构图、演示方式、关键指标、风险边界和证据链接。不要用二十个技术 Badge 代替说明。

### 6.1 开源卫生

- License、贡献指南、Issue/PR 模板；
- `.env.example` 只列变量名和假值；
- 合成数据或明确授权数据；
- CI 不运行付费/敏感生产调用；
- Commit 可读，不一次提交全部代码；
- 已知限制与安全边界公开；
- 第三方文档和素材遵守许可证。

## 7. 投递门槛

### 7.1 可以开始小批量投递

- M0～M4 主链路独立完成；
- README 可从空环境启动 Fake/最小模式；
- LangChain 和 LangGraph 都有代码证据；
- RAG 有引用、拒答和至少 30 条评测；
- 写 Tool 有审批、授权和幂等测试；
- 有一个失败复盘和一个性能/可靠性优化；
- 能完成 3 分钟项目介绍和 30 分钟项目深挖；
- Python/SQL 基础模拟面试无致命错误。

### 7.2 进入目标公司批次

- RC 全部门禁通过；
- 六次模拟面试完成且 P0 错误已复测；
- 使用当周 JD 更新简历关键词，但不堆砌；
- 至少准备应用开发、平台集成两版项目侧重点；
- 投递跟踪表、复盘节奏和可面试时间明确。

不要等到“所有技术学完”才投递；也不要在项目还无法解释失败路径时大量消耗目标公司机会。

## 8. 面试追问树

每个简历条目准备五层：

1. **为什么做**：用户、问题、Baseline；
2. **怎么设计**：边界、数据、流程、选型；
3. **怎么证明**：测试、Dataset、指标、环境；
4. **失败怎么办**：超时、重复、越权、降级、回滚；
5. **还会怎么演进**：容量、团队、业务变化下的下一步。

若第二层后只能背 API，说明证据还不够深。

## 9. 48 小时补缺规则

真实面试暴露缺口后：

```text
0～2 小时：还原题目，确认真正缺口
2～8 小时：读官方资料，写最小复现
8～24 小时：并入项目或补测试/ADR
24～36 小时：口述并录音
36～48 小时：用变体复测，更新证据矩阵
```

一次只修最高收益缺口。不能把“不会 Redis 消息语义”修成收藏十篇文章。

## 10. 练习与答案

### 练习 1：项目评测集 30 条，成功率从 70% 到 90%，简历能否写“提升 20%”？

**答案：**应写“在 30 条冻结评测集上，任务成功率由 70% 提升至 90%（+20 个百分点）”，并说明数据和限制。“提升 20%”会混淆相对增幅与百分点，也容易夸大泛化。

### 练习 2：JD 要求 Dify，你只有 LangGraph 项目，怎么办？

**答案：**如果其他 P0 匹配，完成同一只读流程的 Dify 对照实验，形成 Workflow/DSL、Dataset 和选型 ADR；简历写“Dify 工作流实践”，不写多年经验。若岗位核心是 Dify 平台二开，仍需按真实缺口降低匹配。

### 练习 3：开源仓库是否应该提交真实设备手册展示效果？

**答案：**只有明确拥有公开/再分发授权时可以。默认使用自制合成手册或公开许可数据，记录来源和 License；企业私有资料绝不进入公开仓库。

### 练习 4：面试官问“是否上过生产”，个人项目如何回答？

**答案：**诚实说明是个人企业级模拟项目，已通过 CI、负载、故障注入和部署演练，但没有真实生产用户；再用过去的真实交付经验证明生产协作素养。不要虚构上线。

## 11. 验收标准

- [ ] 所有技能标注“已证明/已实践/已理解/未掌握”；
- [ ] 简历每个技术断言都有证据链接和追问树；
- [ ] 至少保存 20 条 JD 并完成岗位族分类；
- [ ] 完成两版项目侧重点，但事实和指标一致；
- [ ] GitHub 无 Secret、侵权数据和伪造生产指标；
- [ ] 小批量与目标批次投递门槛分别可检查；
- [ ] 面试缺口按 48 小时规则复测并更新矩阵。
