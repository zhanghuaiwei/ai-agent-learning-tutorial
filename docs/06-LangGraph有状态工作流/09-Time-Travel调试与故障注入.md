# Time Travel 调试与故障注入

> 预计 7 小时｜产出：能从历史检查点复现失败并安全分叉实验。

> **阅读前置**：本章是第 6 阶段（LangGraph 有状态工作流）第 9 章，承接第 4 章的 Checkpoint 历史与第 7 章的故障恢复，用检查点回放故障注入并安全分叉实验。前置要求：第 4 章 `aget_state`/`aget_state_history`、第 7 章故障终态表。本章的“只读 Time Travel”是第 10 章 M4 验收“故障注入与只读 Time Travel”的验收项。

## 1. 本章从哪里开始

第 7 章证明了故障能恢复，但“恢复得对不对”还靠人肉观察。真正可复现的调试需要两样东西：

1. **回到过去**：从某个历史检查点看当时的状态、从那里重跑；
2. **主动制造故障**：不等线上出错，而是在最危险路径上注入故障，验证恢复与幂等。

这就是 Time Travel + 故障注入。它们共同回答 M4 验收里的一个问题：**“我觉得稳定”如何变成可测证据**。

## 2. 本章完成标准（通过门槛）

- 能从历史检查点查看某步 State，并从旧状态分叉运行；
- 分叉运行默认使用沙箱/只读工具，禁止再次执行生产副作用；
- 记录 Graph 版本、节点版本、Prompt、模型、工具 Schema 和数据版本，旧 Checkpoint 可被新代码解释；
- 六类故障注入（模型/检索/Checkpoint/审批/业务提交/流）各有预期终态；
- 能从 M4 验收的故障注入里回放并安全分叉。

## 3. Time Travel 是什么、不是什么

Checkpoint 历史（第 4 章 `aget_state_history`）允许你：

```python
snapshot = await graph.aget_state(config)
history = [item async for item in graph.aget_state_history(config)]
# 从某个历史 Checkpoint 分叉
forked = await graph.ainvoke(
    None,   # 或从历史 state 出发
    config={"configurable": {"thread_id": f"{thread_id}-fork", "checkpoint_id": old_checkpoint_id}},
)
```

三个边界必须刻进脑子：

1. **Time Travel 重放执行状态，不回滚外部事实**。已创建的工单不会因为“回到过去”就消失，撤销必须走明确的业务补偿流程（第 7 章）；
2. **分叉是调试与假设验证，不是修改真实业务历史**。默认用只读/Fake Tool，生产副作用 Tool 必须被替换；
3. **旧 Checkpoint 可能无法被新代码解释**。Graph 版本、节点版本、Prompt、模型、工具 Schema、数据版本都要记录，State Schema 变更需要迁移函数（第 4 章 §8）。

## 4. 版本记录：让旧检查点可解释

没有版本记录，旧 Checkpoint 就是一堆无法解释的序列化字节：

| 版本项 | 作用 |
| --- | --- |
| Graph 版本 | 拓扑与路由是否变了 |
| 节点版本 | 节点逻辑是否变了 |
| Prompt 版本 | 提示词是否变了 |
| 模型版本 | 模型能力是否变了 |
| 工具 Schema 版本 | 工具参数契约是否变了 |
| 数据版本 | 检索索引/手册是否变了 |

版本对不上的旧 Checkpoint，要么用迁移函数解释，要么明确拒绝分叉。不能拿新代码去跑旧状态还假装结果可比。

## 5. 安全分叉的规则

分叉用于调试，但分叉也会跑节点。如果分叉跑到了 `submit_work_order`，就会重复副作用。规则：

1. 分叉运行默认**沙箱/只读工具**，把 `submit_work_order`、`create_draft` 换成 Fake；
2. 只读节点（检索、诊断）可以真跑，但写节点必须替换或跳过；
3. 分叉用独立 `thread_id`（或新 Branch），不污染原业务历史。

这对应 M4 练习 4：Time Travel 分叉后不能继续使用真实提交 Tool，外部业务历史不会随 Checkpoint 回滚，真实 Tool 可能重复副作用。

## 6. 故障注入矩阵

| 注入点 | 故障 | 期望 |
| --- | --- | --- |
| 模型 | 超时/非法结构 | 有限重试或降级 |
| 检索 | 空结果/慢 | 拒答或只返回告警 |
| Checkpoint | 写失败 | 不宣称已暂停成功 |
| 审批 | 重复/过期 | 幂等拒绝 |
| 业务提交 | 成功后超时 | 查询幂等结果 |
| 流 | 客户端断开 | 按策略取消/继续 |

每个注入场景保存三样证据：**Trace（调用轨迹）、用户可见结果、恢复证明**。这样“第 7 章的幂等恢复”才有可复现的验证入口。

## 7. 回放 M4 的故障注入

本章要能回放 M4 验收里的故障注入。典型回放流程：

```text
1. 跑一次正常流程，保存 checkpoint 历史
2. 在“业务提交”处注入“成功后超时”
3. 观察 Graph 进入“状态核对中”
4. 恢复后按幂等键查询，得到原工单，不重复 POST
5. 从诊断前 Checkpoint 分叉，替换提交 Tool 为 Fake
6. 对比两个 Prompt 的结果，验证修复
```

关键：**分叉对比实验与故障恢复是两件事**。恢复是在生产 `thread_id` 上安全继续；分叉是在独立线程上用 Fake 工具做假设验证。

## 8. 项目任务

1. 为每个注入场景保存 Trace、用户结果和恢复证明，形成故障注入报告；
2. 从诊断前 Checkpoint 分叉对比两个 Prompt，但提交 Tool 替换为 Fake；
3. 写“分叉不产生副作用”测试：分叉跑完，业务侧工单数不变；
4. 记录版本矩阵（Graph/节点/Prompt/模型/工具 Schema/数据），验证旧 Checkpoint 可解释或明确拒绝。

## 9. 常见错误与诊断顺序

### 9.1 用 Time Travel 撤销已建工单

根因是误以为回退检查点能回滚外部事实。诊断顺序：确认“重放执行状态”与“回滚业务事实”的边界 → 撤销走补偿流程。Time Travel 不撤销工单。

### 9.2 分叉仍用真实提交 Tool

根因是图省事直接复用了生产图。诊断顺序：分叉前把写 Tool 换成 Fake/只读 → 独立 `thread_id` → 断言业务侧工单数不变。真实 Tool 可能重复副作用。

### 9.3 拿新代码跑旧检查点还假装可比

根因是没记录版本。诊断顺序：确认 Graph/节点/Prompt/模型/工具 Schema/数据版本 → 旧 Checkpoint 可迁移或明确拒绝。版本对不上，比较无意义。

### 9.4 故障注入只在“能跑通”的地方注入

根因是挑了安全路径，没碰最危险路径。诊断顺序：按 M4 六类故障逐项注入 → 重点覆盖“提交成功后超时”“Checkpoint 写失败”“审批过期”。只注入容易过的点等于没测。

## 10. 练习题与答案

### 练习 1：能否用 Time Travel 撤销已创建工单？

**答案：**不能。它重放执行状态，不回滚外部事实；撤销必须调用明确的业务补偿流程。

### 练习 2：为什么故障注入优于等线上出错？

**答案：**可重复验证最危险路径，提前发现恢复与幂等缺陷，并形成 Runbook。线上出错的代价不可控且难以复现。

### 练习 3：分叉运行能继续用真实提交 Tool 吗？

**答案：**默认不能。分叉用于调试和实验，应使用只读/Fake Tool；外部业务历史不会随 Checkpoint 回滚，真实 Tool 可能重复副作用。

### 练习 4：为什么旧 Checkpoint 可能无法被新代码解释？

**答案：**Graph/节点/Prompt/模型/工具 Schema/数据都可能变了，旧序列化状态与新逻辑错位；需版本记录 + 迁移函数，或明确拒绝分叉。

## 12. 面试追问

### 12.1 “Time Travel 能回滚生产数据吗？”

回答框架：不能。它重放执行状态，不回滚外部事实。撤销已建工单走补偿流程。分叉用于调试，写 Tool 必须替换为 Fake/只读。

### 12.2 “你们怎么复现线上故障？”

回答框架：故障注入矩阵 + 检查点历史回放。在最危险路径注入故障，保存 Trace、用户结果、恢复证明，形成可复跑的 Runbook，而不是等线上出错。

### 12.3 “旧 Checkpoint 怎么保证还能用？”

回答框架：记录 Graph/节点/Prompt/模型/工具 Schema/数据版本，State Schema 变更配迁移函数，旧快照可解释或明确拒绝。版本对不上就不假装可比。
