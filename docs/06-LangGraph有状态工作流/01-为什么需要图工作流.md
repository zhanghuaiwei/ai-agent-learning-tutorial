# 为什么需要图工作流

> 预计 4 小时｜目标：从“聊天循环”升级到可恢复的企业业务流程。

## 1. 本章从哪里开始

第 4 阶段（LangChain 与单 Agent）交付了一个被验证过的单 Agent：`create_agent` + `AgentContext` + 三个工具（`search_manual`/`get_alarm`/`create_work_order_draft`）+ `E_*` 错误契约 + 自有 SSE 12 事件。它解决的是“一轮对话里，模型安全地选工具、查手册、读告警、建草稿”。

但第 10 章的 M4 验收要的是另一件事：**工单协同**。它不再是一轮对话，而是：

```text
接收请求 → 获取上下文 → 检索 → 诊断 → 风险分级
  → 生成草稿 → 等待人工审批（可能数小时）→ 重新校验 → 提交 → 完成/失败
```

这两者的差异，不是“代码量变多”，而是**运行模型变了**：单 Agent 的一次 `ainvoke` 是有终点的短任务（第 4 阶段用 4 次模型调用、6 次 Tool Call、20 秒 Deadline 来兜底）；工单协同是一次**可能跨进程、跨重启、需要中途暂停等审批**的长期业务流程。本章要回答的核心问题是：为什么这条流程不该再塞进一个 Agent Loop，而该用一张图（Graph）显式表达。

## 2. 本章完成标准（通过门槛）

必须同时满足：

- 能说出单 Agent 循环无法承载“暂停/恢复/跨重启/重试范围/逐状态审计”中的至少三项，并指出根因；
- 能用 State + Node + Edge + Checkpointer 四个词描述 Graph 的职责边界，不把“模型推理”与“流程编排”混为一谈；
- 能把工单协同流程画出拓扑，标出**模型节点、确定性节点、副作用节点、失败终态**四类角色；
- 能举出“不该上 Graph”的反例（简单问答、单轮工具调用），说明图不是为了让流程变复杂；
- 知道图管理的是**执行状态**，业务事实（工单是否真的建了）仍以业务数据库为准。

## 3. 单 Agent 的边界在哪里

第 4 阶段的单 Agent 有几条硬边界（写进 `create_agent` 装配与测试里的）：

| 边界 | 数值 | 语义 |
| --- | --- | --- |
| 最大模型调用 | 4 次 | 防止模型在循环里来回空转 |
| 最大 Tool Call | 6 次 | 防止工具风暴 |
| 总时限 Deadline | 20 秒 | 短任务有界终止 |
| 循环检测 | 相同工具+规范化参数连续 2 次 | 命中即终态 |

这套边界对“查手册→读告警→建草稿”很合适，但对工单协同有四个致命缺口：

1. **时间跨度**：等人工审批可能数小时，20 秒 Deadline 直接判死；
2. **恢复点**：进程在“等待审批”后重启，单 Agent 的消息历史只在本进程内存里，重启即丢；
3. **重试范围**：提交工单超时了，单 Agent 只能把整轮对话重跑，无法只重试“提交”这一步；重跑会把前面所有工具副作用再执行一遍；
4. **审计粒度**：企业要能说清“是谁、在哪一步、基于什么状态、为什么”把工单推下去了，单 Agent 的一串 `tool_calls` 日志不够。

结论不是“单 Agent 错了”，而是**短任务与长流程是两种运行模型**。本章开始引入 LangGraph，正是为长流程提供一个显式的编排骨架。

## 4. 图工作流的四个基本块

LangGraph 把流程表达为一张有向图，四个基本块各司其职：

| 基本块 | 职责 | 对应例子 |
| --- | --- | --- |
| State | 跨节点需要、可序列化的运行状态 | `tenant_id`、`equipment_id`、`draft_id`、`approval_status` |
| Node | 执行一个有限职责（确定性计算或调用模型） | `validate_request`、`diagnose`、`submit_work_order` |
| Edge | 决定下一步（固定连接或条件路由） | `diagnose → create_draft`、`revalidate → submit/failed` |
| Checkpointer | 每个 Super-step 保存 State 快照，支撑恢复 | `InMemorySaver` → 生产持久化后端 |

关键心法：**模型只在局部节点里做语义判断（怎么诊断、要不要改写查询），业务边界由图固定**。校验、权限、状态转移、幂等提交这些确定性逻辑用代码写，不给模型“自由发挥”的空间。这直接延续了第 4 阶段“越权拦截落在确定性代码、不在 Prompt”的结论。

## 5. 何时用、何时不用 LangGraph

| 特征 | 用 LangGraph | 不用（单 Agent 或纯函数即可） |
| --- | --- | --- |
| 时间跨度 | 跨请求、等人工数小时 | 一轮对话内结束 |
| 失败恢复 | 需从中途检查点继续 | 重跑整个输入无副作用 |
| 结构 | 明确并行分支、条件路由、审批点 | 线性、单一路径 |
| 审计 | 需要逐状态转移与重放 | 只需最终答案 |
| 状态 | 有跨步骤的显式状态 | 只有消息历史 |

一条实用的判据：**如果“从失败处继续”和“谁能看到中间状态”是需求，就倾向于图**；如果只是一次问答或单轮工具调用，上 Graph 只会增加样板，不增加价值。图不是为了画得复杂，而是显式管理长期运行与不确定性。

## 6. 图工作流不是什么

容易误读的三个边界：

1. **Graph 不是微服务**。Graph 是一次业务运行的编排模型；节点可以在同一进程内，也可以调用外部 HTTP 服务。服务边界由数据所有权与团队边界决定，不是由图画多大决定。
2. **Graph 不是业务真相**。Checkpoint 里存的是“执行到哪一步了”，工单是否真的建了，仍以业务数据库为准。第 4 章的幂等键、第 7 章的提交幂等，都是为了让 Graph 的执行状态与业务事实对齐。
3. **图不是越复杂越专业**。每个节点/边都要有明确理由；模型能在一个节点里说清的事，不要拆成三个节点加两条边。M4 验收明确要求“子图拆分有明确理由，不以多 Agent 数量为目标”（见第 8 章）。

## 7. 智维 Agent 的图拓扑（目标形态）

本章只画出目标，具体 State/Node/Edge/Reducer 在下一章落地。与第 10 章 M4 验收的组装骨架保持一致：

```text
START
  → validate_request（确定性：校验 tenant/user/equipment）
  → collect_context（并行：告警 + 资产 + 知识）
  → retrieve_knowledge
  → diagnose（模型：诊断 + 风险分级）
      ├─ need_input → request_missing_input → diagnose（有界循环）
      ├─ draft → create_draft → review_draft（interrupt 审批）
      │            → revalidate → submit_work_order → completed → END
      └─ fail → failed → END
```

四类节点角色标注：

| 角色 | 节点 | 为什么 |
| --- | --- | --- |
| 确定性 | `validate_request`、`revalidate`、`failed`、`completed` | 权限、状态转移、终态，无模型 |
| 模型 | `diagnose` | 语义判断，输出结构化诊断 |
| 副作用 | `create_draft`、`submit_work_order` | 调用外部写 API，必须幂等 |
| 暂停 | `review_draft` | `interrupt()` 等人工审批 |

## 8. 与第 4 阶段的继承关系

本阶段不推翻第 4 阶段，而是把已验证的契约**原样迁移**：

- 三个工具与 `schemas.py` 的 Pydantic 契约不变，`create_work_order_draft` 仍带 `idempotency_key`；
- `E_*` 错误码不变，仍区分“模型可修正”与“不可修正”；
- `AgentContext`（冻结 dataclass，身份来自服务端）不变，只是现在由 Runtime 注入 Graph，而不是单 Agent 的 `context_schema`；
- 执行边界的“精神”延续为：Graph 的全局 `recursion_limit` 只做最后保护，每个业务循环（如查询改写）仍要有自己的计数与失败终态。

一句话概括本章升级：**第 4 阶段证明了“一轮对话内安全地选工具”，第 6 阶段要证明“跨重启的流程也能安全地暂停、恢复、无重复副作用地走到终态”。**

## 9. 项目任务

1. 把工单协同流程画成图，标出模型节点、确定性节点、副作用节点、暂停节点、失败终态五类；
2. 指出至少两个“不能由模型决定”的节点，并写一句为什么（对应第 4 阶段“权限在确定性代码”的结论）；
3. 写一个反例用例：说明“查手册→直接回答”为什么不需要上 Graph；
4. 在 `docs/adr/` 写一份简版 ADR《为何把工单协同从单 Agent 迁到 LangGraph》，列出触发条件与不触发条件。

## 10. 常见错误与诊断顺序

### 10.1 把所有节点都塞给模型

高概率根因是误以为“图里的每一步都要 AI 判断”。诊断顺序：先列节点职责 → 区分“确定性”与“语义不确定” → 确定性节点写纯函数 → 只把语义判断交给模型。模型节点越少，可测试性与延迟越可控。

### 10.2 以为上了 Graph 就自动有了恢复

Graph 只是提供了恢复的“可能”，恢复依赖 Checkpointer、稳定 `thread_id` 和幂等副作用。没有这三样，图照样一重启就丢、照样重复建单。诊断顺序：先确认有没有 Checkpointer → 再确认 `thread_id` 是否稳定且绑定用户 → 最后确认写节点是否幂等。

### 10.3 把“画得复杂”当成果

节点和边是为职责与恢复边界服务的，不是越多越好。诊断顺序：问每个节点“它有没有独立的状态、权限或失败边界”，没有就合并；对照第 8 章的“拆分有效理由”清单。

## 11. 练习题与答案

### 练习 1：所有节点都调用 LLM 合理吗？

**答案：**不合理。校验、权限、状态转移、幂等提交等确定性逻辑应用代码实现，模型只处理语义不确定部分。模型节点越多，越难验证、延迟越高、越容易被注入利用。

### 练习 2：Graph 与微服务是一回事吗？

**答案：**不是。Graph 是一次业务运行的编排模型；节点可在同一进程，也可调用外部服务。服务边界由数据所有权和团队边界决定，不能因为图画了条边就把两个服务合并或拆开。

### 练习 3：为什么 20 秒 Deadline 无法直接用于工单审批？

**答案：**工单审批可能等待数小时，短任务 Deadline 会把合法等待判成超时终止。长流程需要“暂停 + 恢复”的模型，而不是把整件事塞进一个短命 Agent Loop 里。

### 练习 4：Checkpoint 里存了“已提交”，能当作“工单已建”吗？

**答案：**不能。Checkpoint 是执行状态快照，业务事实以业务数据库为准。提交成功后网络超时这类场景，必须用幂等键去业务侧核对，而不是信 Checkpoint 里的乐观标记。

## 12. 工程挑战

1. 用伪代码写出“单 Agent 把工单审批塞进一轮对话”会撞上哪几条边界（4 次模型调用 / 6 次 Tool Call / 20s Deadline），逐条说明；
2. 设计一个最小反例：证明“无 Checkpointer 的图”重启后无法从“等待审批”继续，从而反证 Checkpointer 不是装饰；
3. 给第 7 节的拓扑写一个“节点角色”断言：任何写操作节点都必须出现在副作用类里，且必须带幂等键。

参考方向：第 1 题对照第 4 阶段 M2 的执行边界表；第 2 题可先用 `InMemorySaver` 与“无 Saver”各跑一次对比。

## 13. 面试追问

### 13.1 “你们为什么要从单 Agent 迁到 LangGraph？”

回答框架：不是追新，是运行模型变了——工单协同需要跨重启恢复、中途暂停审批、可隔离的重试范围、逐状态审计，单 Agent Loop 的四条硬边界（模型/工具/Deadline/循环）管不住长流程。用 State/Node/Edge/Checkpointer 显式承载这些需求，模型只保留在局部节点。

### 13.2 “Graph 和微服务怎么划界？”

回答框架：Graph 是编排，微服务是部署与数据所有权。节点可以调用服务，但服务边界由团队和数据决定；不能因为图画得动就把跨团队职责揉进一个 Graph 里（对应第 8 章“什么时候用 A2A 而不是子图”）。

### 13.3 “图会不会让系统更难懂？”

回答框架：对短任务会，对长流程反而是把隐式状态显式化——每一步、每一条边、每个终态都可审计可重放。复杂度是需求带来的，图只是让它可见；若需求本身是线性的，就不该上图。

## 16. 下一章入口

本章把“为什么”讲清：工单协同是长流程，需要图来显式管理状态、恢复与审计。下一章落地“是什么”——定义 `WorkOrderState`、Node 的局部更新约定、Edge 与 Reducer 的合并语义，把第 7 节的拓扑变成可编译的图骨架。

**关键闸门**：如果还不能一句话说清“单 Agent 与 Graph 的分界在哪里”，先回到 §3 的边界表和 §5 的判据，不要急着写 State——图的价值来自你清楚它要管理什么不确定性与什么恢复点。
