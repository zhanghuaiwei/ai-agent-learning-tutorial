# 副作用、幂等与故障恢复

> 预计 8 小时｜产出：重复执行仍只创建一张工单的提交节点。

## 1. 至少一次执行现实

网络超时、进程崩溃和恢复会让系统无法确定远端写操作是否成功。可靠系统通常按“可能至少执行一次”设计，通过幂等键把重复请求折叠为同一业务结果。

幂等键可由 `tenant + thread + action_type + action_digest` 生成；业务服务建立唯一约束，并保存请求摘要、状态和结果。相同 Key 不同 Payload 返回 409，而不是悄悄复用。

## 2. 事务边界

本地数据库事务只能保护本服务。跨服务不要幻想一个数据库事务覆盖模型、Python 和 Java；采用明确状态、Outbox/事件、重试与补偿。模型调用不是事务参与者，不应放在持锁事务中。

Node 设计为可重放：确定性计算可重复；外部写通过幂等 API；随机数/当前时间先写入 State；文件和通知用业务 ID 去重。

## 3. 项目任务

在“Java 已创建工单但 Python 收到超时”处注入故障，恢复后查询幂等结果而非再建单。记录状态图与 Runbook。

## 4. 练习与答案

### 练习 1：HTTP POST 一定非幂等吗？

**答案：**协议语义默认不保证，但业务可以通过 Idempotency-Key 和唯一约束实现幂等处理。

### 练习 2：补偿等于数据库回滚吗？

**答案：**不是。补偿是后续业务动作，例如取消草稿或标记作废，可能失败并需审计。

## 5. 验收与资料

重复、超时、崩溃三类注入都不产生重复工单。参考 [Durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution)、[HTTP Idempotency-Key 草案](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)。
