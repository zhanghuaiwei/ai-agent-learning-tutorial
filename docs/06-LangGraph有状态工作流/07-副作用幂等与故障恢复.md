# 副作用、幂等与故障恢复

> 预计 8 小时｜产出：重复执行仍只创建一张工单的提交节点。

> **阅读前置**：本章是第 6 阶段（LangGraph 有状态工作流）第 7 章，承接第 6 章的“恢复会重跑节点”这一伏笔，正面解决副作用幂等与故障恢复。前置要求：第 6 章 Interrupt 前副作用必须幂等的结论、第 2 章 State 里的 `work_order_id`、第 3 阶段已定义的 `idempotency_key`（`create_work_order_draft` 契约，`OK_DUPLICATE` 语义）。本章是 M4 验收“提交幂等、失败恢复”的直接实现。

## 1. 本章从哪里开始

第 6 章把审批串起来了，但留下一个洞：恢复会重跑节点，任何副作用都可能执行两次。更糟的是**网络超时**——提交工单的 HTTP 请求发出去了，远端 Java 服务已经建好了工单，但响应在回来的路上丢了，Python 这边只看到超时。此时你无法确定写操作是否成功。

可靠系统的现实是：**按“可能至少执行一次”设计**，而不是赌“恰好一次”。既然可能重复执行，就用**幂等键**把重复请求折叠成同一个业务结果。第 3 阶段已经埋了 `idempotency_key`（`create_work_order_draft` 带它、命中返回 `OK_DUPLICATE`），本章把这条线从“草稿”延伸到“提交工单”。

## 2. 本章完成标准（通过门槛）

- 提交节点用幂等键折叠重复请求，重复、超时、崩溃三类注入都不产生重复工单；
- 幂等键由 `tenant + thread + action_type + action_digest` 生成，业务服务建立唯一约束并保存请求摘要、状态与结果；
- 相同 Key 不同 Payload 返回 409，不悄悄复用旧结果；
- 节点设计为可重放：确定性计算可重复，外部写走幂等 API，随机数/当前时间先写入 State；
- 提交成功但响应丢失时，用幂等键查询业务结果，不把整个 Graph 从头再跑。

## 3. 至少一次执行现实

三类故障让“是否成功”不可知：

| 故障 | 场景 | 后果 |
| --- | --- | --- |
| 网络超时 | 请求已到远端，响应丢失 | 本地不知道建没建 |
| 进程崩溃 | 节点执行一半挂了 | 恢复时可能重放 |
| 恢复重跑 | Interrupt 恢复、Pending Writes 重放 | 同一节点跑两次 |

处理原则：**用幂等键把“重复执行”变成“同一结果”**。幂等键由调用方（业务层）在任务开始时生成并贯穿，不让模型每次现编——这正是第 3 阶段 M1 红队用例 5 的教训：模型第二次生成的键若不同，幂等就失效了。

```python
idempotency_key = f"{tenant_id}:{thread_id}:{action_type}:{action_digest}"
```

业务服务侧建立唯一约束，并保存请求摘要、状态与结果：

```text
key → { request_digest, status, work_order_id, created_at }
```

- 同 Key 同 Payload：返回已有结果（`OK_DUPLICATE`），不重复建单；
- 同 Key 不同 Payload：返回 409（`E_CONFLICT`），不悄悄复用旧结果——复用会掩盖状态漂移。

## 4. 事务边界

本地数据库事务只能保护本服务。跨服务（模型 + Python + Java）不要幻想一个数据库事务覆盖全部：

1. **模型调用不是事务参与者**，不应放在持锁事务中——它慢、不确定、还贵；
2. 跨服务采用**明确状态 + Outbox/事件 + 重试 + 补偿**，不追求分布式 ACID；
3. 补偿不等于回滚：补偿是后续业务动作（取消草稿、标记作废），可能失败并需审计。

节点设计为**可重放**：

| 内容 | 处理 |
| --- | --- |
| 确定性计算 | 可重复，无副作用 |
| 外部写 | 走幂等 API，带幂等键 |
| 随机数/当前时间 | 先写入 State，重放时保持一致 |
| 文件/通知 | 用业务 ID 去重 |

## 5. 提交节点的幂等实现

```python
async def submit_work_order(state: WorkOrderState) -> dict:
    idem_key = make_idempotency_key(state)   # tenant:thread:submit:action_digest

    result = await business_api.submit(
        draft_id=state["draft_id"],
        idempotency_key=idem_key,
        payload={"action_digest": state["action_digest"]},
    )

    if result.status == "ok":
        return {"work_order_id": result.work_order_id}
    if result.status == "duplicate":
        return {"work_order_id": result.work_order_id}   # 折叠重复
    raise BusinessError(result.error_code)               # 409/其他，走 failed
```

“提交成功但响应丢失”时，恢复后**先查幂等结果，再决定要不要重新 POST**：

```python
async def submit_work_order(state: WorkOrderState) -> dict:
    existing = await business_api.query_by_idempotency_key(state["idem_key"])
    if existing:
        return {"work_order_id": existing.work_order_id}
    return await do_submit(state)   # 确认没建过，才提交
```

绝不把整个 Graph 从头再跑——那会把前面所有副作用再执行一遍。

## 6. 故障终态表

与第 10 章 M4 的故障终态表对齐：

| 故障 | 用户可见结果 | 系统动作 | 可否自动重试 |
| --- | --- | --- | --- |
| 模型临时超时 | 稍后重试/已有证据摘要 | 记录节点失败 | 只读且有限 |
| 检索无证据 | 结构化拒答 | 不创建草稿 | 否 |
| Checkpoint 写失败 | 未可靠暂停 | 不展示“等待审批”成功 | 修复存储后重试 |
| 批准过期 | 要求重新批准 | 作废旧 Approval | 否 |
| 提交成功后超时 | 状态核对中 | 按幂等键查询 | 不重复 POST |
| 业务 409 | 状态已变化 | 重新读取并重规划 | 不盲目重试 |
| 客户端断线 | 按 Run 状态查询 | 取消或后台继续 | 依 Use Case |

## 8. 常见错误与诊断顺序

### 8.1 让模型每次现编幂等键

根因是把幂等键当普通参数交给模型。诊断顺序：确认幂等键是否由业务层在任务开始生成并贯穿 → 用同一键重放测试 → 断言第二次命中 `OK_DUPLICATE`。模型现编的键在重试时不稳定，幂等失效。

### 8.2 同键不同载荷却悄悄复用旧结果

根因是幂等实现只认 Key 不认载荷。诊断顺序：业务侧保存请求摘要 → 同 Key 不同载荷返回 409 → 测试证明不会把“改了内容的提交”复用成旧结果。复用会掩盖状态漂移。

### 8.3 把补偿当回滚

根因是混淆了两者。诊断顺序：确认跨服务没有魔法事务 → 补偿是后续业务动作（作废/取消）→ 补偿可能失败需审计。补偿不等于“撤销到之前状态”。

### 8.4 提交超时后从头重跑整张图

根因是“简单粗暴重跑”。诊断顺序：先按幂等键查询业务结果 → 确认没建过才提交 → 绝不整图重跑。整图重跑会把前面所有副作用再执行一遍。

## 9. 练习题与答案

### 练习 1：HTTP POST 一定非幂等吗？

**答案：**协议语义默认不保证，但业务可以通过 Idempotency-Key 和唯一约束实现幂等处理。幂等是业务层设计，不是 HTTP 动词天然给的。

### 练习 2：补偿等于数据库回滚吗？

**答案：**不是。补偿是后续业务动作，例如取消草稿或标记作废，可能失败并需审计。跨服务没有单一事务可回滚。

### 练习 3：幂等键应该由谁生成？

**答案：**由调用方（业务层）在任务开始时生成并贯穿，不让模型每次现编。第 3 阶段 M1 已证明：模型重试时生成的键不一致，幂等就失效。

### 练习 4：提交成功但响应丢失，恢复时直接重跑图行吗？

**答案：**不行。先按幂等键查询业务结果，确认没建过才提交；整图重跑会把前面所有副作用再执行一遍，可能重复建单。

## 11. 面试追问

### 11.1 “你们怎么保证不重复建单？”

回答框架：幂等键 `tenant:thread:action_type:action_digest` + 业务侧唯一约束。提交前先查、确认没建过才提交；同键同载荷返回已有结果，同键不同载荷 409。重复/超时/崩溃三类注入都验证无重复。

### 11.2 “幂等键放哪、谁生成？”

回答框架：业务层在任务开始生成并贯穿，不让模型现编。键的组成要覆盖租户隔离、会话、动作类型与动作摘要，防止跨租户或动作漂移。

### 11.3 “补偿和回滚区别？”

回答框架：回滚是单数据库事务内的撤销；补偿是跨服务的后续业务动作（作废草稿、取消），可能失败且需审计。跨服务没有单一事务，靠明确状态 + Outbox + 重试 + 补偿。
