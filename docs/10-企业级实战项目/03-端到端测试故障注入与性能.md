# 端到端测试、故障注入与性能

> 预计 10 小时｜目标：产出 Release Candidate 的系统级证据。

## 1. 本章从哪里开始

01 章定义了确定性验收（越权、幂等、状态机），02 章画出了信任边界和故障语义。但架构承诺要落地，必须回答一个尖锐的问题：**整条链路端到端跑起来后，正常路径、异常路径和压力下，系统到底守不守得住承诺？**

单元测试只证明单点正确，证明不了"登录身份上下文 → 提问 → 检索引用 → 工单草稿 → 暂停 → 审批 → 恢复 → Java 提交 → UI 收到完成"这条主链路。本章承接 01/02 章，产出第 10 阶段（企业级实战项目交付）的第三类证据：**E2E 场景、故障矩阵、性能报告**，直接喂给 08 章 RC 验收。

完成后你应该能回答：

1. Fake Model 压测能代表真实模型吞吐吗？为什么还要保留少量真实模型验收？
2. 平均延迟 2 秒为何仍可能体验差？该看哪些指标？
3. 六类故障注入后，凭什么说系统"安全终态"而不是"碰巧没炸"？

## 2. 本章完成标准（通过门槛）

必须同时满足：

- 主链路（登录身份 → 提问 → 检索引用 → 工单草稿 → 暂停 → 审批 → 恢复 → Java 提交 → UI 完成）有 E2E 测试，且用 Fake Model 脚本控制轨迹；
- 覆盖拒绝、无答案、越权、取消、断线恢复、服务重启六类异常场景；
- 故障矩阵至少覆盖模型 429/超时/坏 JSON、向量库慢/空、MCP 断连、Checkpoint 失败、Java 成功后超时、审批重复、SSE 断线七类，每类验证用户结果、业务事实、Graph 终态、Trace、告警五个维度；
- 每个 E2E 场景隔离数据，以 `test_run_id` 清理，不依赖执行顺序；
- 性能报告可复现，分工作负载、分并发、看 P50/P95/P99、首 Token、各依赖、Token/成本、错误与降级率。

## 3. E2E 场景

### 3.1 主链路场景

```text
login_identity_context
  -> ask_question
  -> retrieve_with_citation
  -> create_work_order_draft
  -> pause (interrupt)
  -> approve
  -> resume
  -> submit_to_java
  -> ui_receives_completed
```

每个步骤有可观察断言：`run_id/request_id` 贯穿、引用带 `evidence_id`、草稿状态迁移合法、审批幂等、Java 提交成功后 UI 收到终态。

### 3.2 异常场景

| 场景 | 期望行为 | 对应 01 章故事 |
| --- | --- | --- |
| 拒绝 | 安全拒答，无副作用 | 故事 2/4 |
| 无答案 | 明确"不知道"，不编造 | 故事 4 |
| 越权 | `E_FORBIDDEN`/`refused`，无数据泄露 | 故事 2 |
| 取消 | 终态 `run.cancelled`，只发一次 | 故事 6 |
| 断线恢复 | Checkpoint 恢复继续，不重复执行 | 故事 7 |
| 服务重启 | 幂等，未完成 Job 可重投 | 故事 9 |

### 3.3 Fake Model 的使用

E2E 用 Fake Model 脚本控制轨迹，测试的是**自己的系统**（API、Graph、数据库、流协议、工具），而非模型。只保留少量真实模型验收。每个场景隔离数据，以 `test_run_id` 清理；不要依赖执行顺序——任何两个场景交换执行顺序都该绿。

## 4. 故障矩阵

注入故障，验证五个维度：**用户结果、业务事实、Graph 终态、Trace、告警**。

| 注入故障 | 用户结果 | 业务事实 | Graph 终态 | Trace | 告警 |
| --- | --- | --- | --- | --- | --- |
| 模型 429 | 降级提示/安全失败 | 无变更 | 受控终态 | 有阶段标记 | 供应商 429 |
| 模型超时 | 明确超时错误 | 无变更 | `execution_limit_reached` | 有 Deadline | 上游超时 |
| 模型坏 JSON | `E_MODEL_OUTPUT_INVALID` | 无变更 | 受控终态 | 有校验失败 | 结构化输出失败 |
| 向量库慢 | 降级或等待 | 无变更 | 受控终态 | 有延迟标记 | 检索延迟 |
| 向量库空 | 明确"无证据" | 无变更 | 正常终态 | 有检索记录 | 索引空 |
| MCP 断连 | 设备查询降级 | 无变更 | 受控终态 | 有断连标记 | MCP 不可用 |
| Checkpoint 失败 | 会话不可恢复提示 | 无业务变更 | 失败终态 | 有持久化错误 | Checkpoint 异常 |
| Java 成功后超时 | 提示结果未知，查幂等 | **幂等：无重复工单** | 受控终态 | 有幂等键 | 写结果未知 |
| 审批重复 | 只生效一次 | 单条审批 | 幂等终态 | 有幂等记录 | 重复审批 |
| SSE 断线 | 客户端按 `run_id+seq` 去重 | 无变更 | 服务端终态 | 有 seq | 断线率 |

关键点：Java 成功后超时的场景是"业务写结果未知"——此时**先查询幂等记录，不能盲目重试**，否则会产生重复工单。这是 01 章"同一幂等动作最多一个业务结果"不变量的直接验证。

## 5. 性能方法

### 5.1 工作负载定义

先定义工作负载，再测：

| 负载 | 占比 | 说明 |
| --- | --- | --- |
| 只读问答 | 80% | 单工具检索引用 |
| 多工具诊断 | 15% | 查手册 + 查告警 + 建草稿 |
| 工单流程 | 5% | 含审批暂停/恢复 |

并发从 1/5/10 递增，低配置本机只跑小规模，CI/云临时环境跑目标规模。

### 5.2 指标清单

| 指标 | 说明 |
| --- | --- |
| 端到端 P50/P95/P99 | 分任务类别统计 |
| 首 Token 时间 | 流式体验 |
| 各依赖延迟 | 模型/向量库/Java/MCP |
| Token/成本 | 逐任务记录，异常增长告警（仅观测，不设固定金额上限） |
| 错误率 | 分错误码 |
| 降级率 | 降级路径触发比例 |

### 5.3 优化顺序

Trace 找瓶颈 → 建基线 → 单一改动 → 复测 → 检查质量/费用回归。**不要为了压延迟删除必要安全校验**——越权 scope 检查、引用校验、幂等键这些确定性防护绝不能成为性能优化的牺牲品。

## 6. 项目任务

1. 写主链路 E2E，用 Fake Model 脚本控制轨迹，断言 `run_id` 贯穿与草稿状态迁移；
2. 补六类异常 E2E（拒绝/无答案/越权/取消/断线恢复/服务重启），数据以 `test_run_id` 隔离；
3. 实现故障注入，跑通故障矩阵七类注入 × 五维度验证，重点验证"Java 成功后超时 → 查幂等不重试"；
4. 定义工作负载并产出性能报告，分并发、分桶统计 P50/P95/P99、首 Token、各依赖、Token/成本、错误与降级率；
5. 记录一次"单一改动 → 复测"的优化循环，附质量/费用回归检查。

## 7. 常见错误与诊断顺序

### 7.1 E2E 依赖执行顺序

错误：场景 A 建的工单被场景 B 复用。诊断顺序：每个场景以 `test_run_id` 隔离数据并在 teardown 清理 → 随机打乱顺序验证仍绿 → 不共享任何跨场景状态。

### 7.2 用 Fake Model 却当成真实模型吞吐

错误：把 Fake 压测数字当线上吞吐。诊断顺序：明确 Fake 压测只测自有 API/Graph/数据库/流协议 → 真实供应商延迟单独小规模实测并分开报告，不混在一张表。

### 7.3 只看平均延迟

错误：平均 2 秒就认为体验好。诊断顺序：改看 P95/P99、首 Token、错误率和不同任务分组——尾延迟可能很高，且长尾来自工单流程而非只读问答。

### 7.4 压延迟删安全校验

错误：为降 P95 砍掉 scope 检查或引用校验。诊断顺序：任何优化先过"是否削弱确定性防护"，越权、幂等、引用校验不可妥协，性能问题靠缓存/批处理/异步解耦解决。

## 8. 练习题与答案

### 练习 1：Fake Model 压测能代表真实模型吞吐吗？

**答案：**不能，但可测自有 API、Graph、数据库和流协议；真实供应商延迟需小规模实测并分开报告。

### 练习 2：平均延迟 2 秒为何仍可能体验差？

**答案：**尾延迟可能很高；应看 P95/P99、首 Token、错误和不同任务分组，不能只看平均。

### 练习 3：Java 成功后超时，第一动作是什么？

**答案：**查询幂等记录确认结果是否已落地，不能盲目重试；盲目重试会违反"同一幂等动作最多一个业务结果"的不变量，产生重复工单。

## 9. 工程挑战

1. 给"断线恢复"写一个 E2E：断线发生在审批后，恢复后断言不重复审批、不重复提交；
2. 给故障矩阵补一个"向量库空"场景，断言用户看到"无证据"而非编造引用；
3. 写一个并发幂等测试：并发提交同一工单草稿，断言 Java 侧只产生一条工单；
4. 跑一次小规模性能基线，把 P95 按"只读问答/多工具/工单流程"三桶拆开，指出尾延迟来自哪桶。

参考方向：断线恢复对应 M2 验收 §3.4 的 `run.cancelled`/恢复策略；并发幂等对应 01 章不变量的"同一幂等动作最多一个业务结果"。

## 10. 面试追问

### 10.1 "你的 E2E 为什么主要用 Fake Model？"

回答框架：E2E 验证的是我自己的系统——API、Graph、数据库、流协议、工具，不是模型。Fake Model 脚本控制轨迹可离线复跑、确定性断言；真实模型只做少量验收并单独报告，避免把供应商延迟和随机性混进系统测试。

### 10.2 "故障注入怎么证明是'安全终态'而不是碰巧没炸？"

回答框架：每类故障都验证五个维度——用户结果（安全提示）、业务事实（无变更/幂等）、Graph 终态（受控终态）、Trace（有阶段标记）、告警（有触发）。五个维度同时满足才算通过，而不是只看"没抛异常"。
