# 端到端测试、故障注入与性能

> 预计 10 小时｜产出：Release Candidate 的系统级证据。

## 1. E2E 场景

至少覆盖：登录身份上下文 → 提问 → 检索引用 → 工单草稿 → 暂停 → 审批 → 恢复 → Java 提交 → UI 收到完成。另覆盖拒绝、无答案、越权、取消、断线恢复、服务重启。

E2E 使用 Fake Model 脚本控制轨迹，测试自己的系统；只保留少量真实模型验收。每个场景隔离数据，以 `test_run_id` 清理；不要依赖执行顺序。

## 2. 故障矩阵

注入模型 429/超时/坏 JSON，向量库慢/空，MCP 断连，Checkpoint 失败，Java 成功后超时，审批重复，SSE 断线。验证用户结果、业务事实、Graph 终态、Trace 和告警五个维度。

## 3. 性能方法

先定义工作负载：80% 只读问答、15% 多工具诊断、5% 工单流程；并发从 1/5/10 递增。测端到端 P50/P95/P99、首 Token、各依赖、Token/成本、错误与降级率。低配置本机只跑小规模，CI/云临时环境跑目标规模。

优化顺序：Trace 找瓶颈 → 建基线 → 单一改动 → 复测 → 检查质量/费用回归。不要为了压延迟删除必要安全校验。

## 4. 练习与答案

### 练习 1：Fake Model 压测能代表真实模型吞吐吗？

**答案：**不能，但可测自有 API、Graph、数据库和流协议；真实供应商延迟需小规模实测并分开报告。

### 练习 2：平均延迟 2 秒为何仍可能体验差？

**答案：**尾延迟可能很高；应看 P95/P99、首 Token、错误和不同任务分组。

## 5. 验收与资料

关键链路有 E2E、六类故障有证据、性能报告可复现。参考 [FastAPI Testing](https://fastapi.tiangolo.com/tutorial/testing/)、[Locust](https://docs.locust.io/)。
