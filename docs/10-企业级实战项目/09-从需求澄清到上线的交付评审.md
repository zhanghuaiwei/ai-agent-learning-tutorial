# 从需求澄清到上线的 Agent 项目交付评审

> 建议投入：第 23～24 周 3 小时｜目标：证明你能独立完成“需求—方案—开发—验证—发布—运营”，而不是只完成一个技术 Demo。

## 1. 企业项目与 Demo 的差别

Demo 证明某条 Happy Path 能跑；企业交付还需回答：

- 谁使用、解决什么问题、不解决什么；
- 成功指标和风险是什么；
- 数据、权限、模型、Tool 和人工分别负责什么；
- 失败、重复、超时、越权和无证据时如何处理；
- 如何测试、评测、上线、观察、回滚和持续改进；
- 谁负责最终验收与运营。

Agent 的概率性让验收更难，所以需求必须同时包含业务指标、模型/Agent 质量、系统 SLO 和安全红线。

## 2. 需求澄清清单

### 2.1 用户与场景

- 一线维护人员、知识管理员、工单审批人、平台管理员分别做什么；
- 当前流程耗时、错误和成本如何；
- Agent 是建议、草拟、执行还是审批；
- 哪些任务高风险，必须转人工；
- 使用频率、峰值、终端、网络和语言环境；
- 有哪些存量 Java/API/文档/权限系统。

### 2.2 成功与失败

示例目标：

```text
业务：低风险故障信息收集完成率 ≥ 85%
RAG：引用正确率 ≥ 95%，无证据正确拒答率 ≥ 90%
Agent：受控 Tool 任务成功率 ≥ 90%
系统：API 月度可用性目标 99.5%，交互请求 P95 满足约定
安全：跨租户读取/未审批写入 = 0 容忍
运营：所有失败可由 request_id 定位到阶段
```

数值是项目目标，不是行业标准；必须由 Baseline、风险和资源校准。

### 2.3 非目标

智维 Agent 明确不做：直接控制设备、替代持证人员安全决策、无审批关闭高风险工单、从互联网自动下载未知文档、训练行业基础模型。

非目标可以阻止需求蔓延，也是面试中的产品判断证据。

## 3. 一页 RFC

在写代码前提交：

```markdown
# RFC: 有引用的故障建议与工单草稿

## 背景与问题
## 用户、场景与当前流程
## 目标/非目标/成功指标
## 方案概览与状态图
## API、数据与事件契约
## 模型/RAG/Tool 选择
## 身份、权限、租户和数据保留
## 失败、幂等、重试、审批与恢复
## 测试、评测与上线门禁
## 监控、SLO、Runbook 与回滚
## 备选方案与为何不选
## 风险、依赖、里程碑和负责人
## 未决问题
```

RFC 评审不是展示术语。每个关键决定都要说明证据、后果和可逆性。

## 4. 将需求拆成确定性与概率性验收

### 4.1 确定性测试

- API Schema、错误码、认证和资源授权；
- 幂等键与唯一约束；
- Graph 合法状态迁移；
- 未审批工具绝不执行；
- 跨租户数据不可见；
- 取消、超时、重试和恢复；
- Migration、回滚和兼容。

这些失败不能用“模型有随机性”解释。

### 4.2 概率性评测

- FaultReport 字段抽取；
- Tool 选择/参数；
- Recall@K、MRR、引用、忠实度、拒答；
- Agent 最终任务成功和路径；
- Prompt Injection/Tool Poisoning 红队；
- 不同模型/Prompt/RAG 版本的回归。

每个指标定义 Dataset、评分者、阈值、置信与人工抽样。禁止只展示三个成功截图。

## 5. 交付切片

用 Vertical Slice，每个切片都从 API 到数据/测试/观察：

1. **只读问答**：固定文档、引用、拒答；
2. **设备查询 Tool**：身份、Scope、参数与 Trace；
3. **故障 Graph**：状态、恢复、风险路由；
4. **工单草稿**：Interrupt、审批和幂等；
5. **异步摄取**：Job、Queue、重试与进度；
6. **生产门禁**：评测、负载、安全和 Runbook。

每个 Slice 定义 Definition of Done：代码合并、测试、文档、观察和演示，而不是“开发完成、待测试”。

## 6. 接口与依赖评审

### 6.1 API Contract

- 输入/输出 Schema、版本和兼容；
- 同步、SSE 或 202 Job；
- 认证、Scope、Tenant 和 Resource；
- Idempotency-Key 与冲突；
- Error Code、Retryable、Trace ID；
- 请求/响应大小与 Deadline；
- PII、日志和保留。

### 6.2 外部依赖表

| 依赖 | 用途 | 超时/重试 | 降级 | 权威负责人 |
| --- | --- | --- | --- | --- |
| Qwen/DeepSeek | 生成/Tool | 有限重试，唯一 Owner | 切模型/安全失败 | AI Service |
| Embedding | 摄取/查询 | Queue 延迟重试 | 暂停新摄取 | Knowledge Service |
| Java API | 设备/工单真相 | 查询与写分级 | 只读/人工 | Business Service |
| PostgreSQL | Job/Run/审批 | DB 策略 | 不默认放行 | Platform |
| Redis/MQ | Cache/Queue | 按用途 | Cache 可绕、Queue 不丢 | Platform |

## 7. 上线前 Readiness Review

### 7.1 产品

- 用户故事由真实角色验收；
- 无证据、风险和失败提示可理解；
- 转人工入口、审批责任和运营流程明确；
- 培训、反馈、知识更新负责人明确。

### 7.2 工程

- Lock、Migration、镜像、配置与 Secret 已验证；
- Unit/Contract/Integration/E2E/Eval/Security/Load 全部达门槛；
- 数据备份、恢复、保留和删除完成演练；
- Dashboard、Alert、Runbook、On-call/负责人存在；
- Feature Flag、灰度群体和回滚步骤可执行。

### 7.3 Agent 特有门禁

- Prompt、模型、Tool Schema、知识索引和 Evaluator 均有版本；
- 生产模型的 Tool/Structured Output 能力已真实验证；
- 步数、Token、Deadline、并发、重试有上限；
- 高风险动作携带不可篡改摘要并在执行前重校验；
- 安全拒答/降级不泄露内部 Prompt、Trace 和权限信息；
- 模型切换不会绕过 Eval Gate。

## 8. 灰度、观察和回滚

### 8.1 灰度

先内部用户、只读场景、小租户，再逐步开放写操作。灰度指标同时看：

- 业务完成率和人工接管率；
- 引用/拒答/Tool 成功；
- P95、错误率、Queue Lag、供应商 429；
- Token/费用和异常长链路；
- 越权、注入和审批拦截；
- 用户负反馈与误用。

### 8.2 回滚对象

Agent 系统有多个可独立回滚对象：

```text
application image
feature flag
prompt version
model route
tool schema
graph version
knowledge index/version
evaluator threshold
database schema/data
```

不能只写 `git revert`。例如新 Embedding 生成的索引与旧查询模型不兼容，需要保留旧索引别名并原子切换。

## 9. 项目验收会议

准备 30 分钟：

1. 3 分钟：问题、用户、价值、非目标；
2. 5 分钟：主流程演示，包含一次安全拒答；
3. 5 分钟：架构、数据、权限和状态；
4. 5 分钟：评测、负载和稳定性证据；
5. 5 分钟：失败案例、取舍和限制；
6. 5 分钟：发布、观察、回滚和下一阶段。

验收纪要保存：结论、未通过项、负责人、截止日期、证据链接和是否允许发布。

## 10. 面试表达

不要说：“我用了 LangGraph、LangSmith、MCP，技术栈很完整。”

可以说：

> 我先把设备故障协同拆成只读知识建议与高风险工单写入。模型只负责抽取和建议，业务服务负责权限与事务；写入通过 LangGraph Interrupt 和幂等 API。使用分层 Dataset 分别评估检索、引用、Tool 与路径，上线前用跨租户、重复审批和依赖超时做负向测试。一次摄取任务重复入库问题最终通过稳定 Chunk ID、唯一约束和 Job 重投测试解决。

这段话可以继续追问并有代码/报告支撑。

## 11. 练习与答案

### 练习 1：业务只说“做一个智能知识库”，先问哪五类问题？

**答案：**用户与任务、数据来源/权限/时效、成功与失败指标、风险/拒答/人工边界、规模/SLO/集成与运营。技术选型应在这些问题后。

### 练习 2：评测通过但用户仍不满意，怎么办？

**答案：**检查 Dataset 是否代表真实任务、评分是否测对目标、UI/延迟/流程是否造成失败；采集经授权的负反馈并分类。不能只调 Prompt，也不能直接把生产原文无审查加入训练集。

### 练习 3：回滚应用后为什么错误仍在？

**答案：**行为可能来自 Prompt、模型路由、知识索引、Tool Schema、配置或数据库数据。建立完整版本清单和 Trace 关联，逐层确认，不把应用 Git SHA 当作唯一版本。

### 练习 4：如何证明“独立交付”？

**答案：**提供 RFC、任务切片、代码/测试、Eval 报告、发布清单、Dashboard、Runbook、验收纪要和故障复盘；说明协作边界与本人负责部分，不冒充完整团队。

## 12. 验收标准

- [ ] 完成一页 RFC，目标/非目标和风险明确；
- [ ] 每个核心需求有确定性测试或概率性评测；
- [ ] 外部依赖有 Timeout、Retry、Fallback 和 Owner；
- [ ] Readiness Review 有真实证据链接，不是全勾空表；
- [ ] 至少完成一次 Prompt/模型/索引之一的独立回滚演练；
- [ ] 保存验收纪要与未解决限制；
- [ ] 30 分钟评审可在不看教程的情况下完成。
