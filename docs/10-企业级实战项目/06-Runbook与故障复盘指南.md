# Runbook 与故障复盘指南

> 目标：证明你考虑了系统上线后的诊断与恢复。

## 1. Runbook 模板

每个告警写：现象、影响、严重级别、前置权限、快速确认、诊断查询、止血、恢复、数据一致性检查、升级联系人、结束条件。命令使用占位符并提示生产风险，不把密钥写进文档。

项目至少准备：模型 Provider 大面积 429、检索服务异常、Checkpoint 不可用、Java 提交结果未知、费用异常增长、疑似跨租户泄露六份 Runbook。

安全事件优先隔离与保全证据；疑似数据泄露不要只重启服务。业务写结果未知先查询幂等记录，不能盲目重试。

## 2. 无责复盘

```text
摘要与影响
时间线（事实）
检测方式与为何未更早发现
根因与促成因素
处置与恢复
哪些防线有效/无效
行动项（负责人、日期、验证）
用户/数据影响与后续沟通
```

避免“开发不小心”式根因；追问为什么系统允许单点错误变成事故。

## 3. 练习与答案

### 练习 1：上游 429 的第一动作是无限扩容吗？

**答案：**不是。确认配额与流量，限流/降级/停止重试风暴，保护核心任务，再处理容量。

### 练习 2：事故修复后为何还加回归样本？

**答案：**代码修复可能被后续变更破坏，样本和告警能持续验证相同失效模式。

## 4. 验收与资料

让没参与开发的人按 Runbook 完成一次演练。参考 [Google SRE Incident Response](https://sre.google/sre-book/managing-incidents/)、[Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)。
