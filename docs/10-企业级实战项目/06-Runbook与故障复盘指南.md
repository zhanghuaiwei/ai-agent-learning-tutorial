# Runbook 与故障复盘指南

> 预计 8 小时｜目标：证明你考虑了系统上线后的诊断与恢复。

## 1. 本章从哪里开始

03 章证明了故障能被注入和观测，05 章记录了架构为什么这么定。但"能跑"到"可运维"之间还有一道鸿沟：**凌晨三点告警响了，值班的人不看代码，能不能照着文档诊断和恢复？** 事故之后，团队能不能无责地复盘，而不是甩锅给"开发不小心"？

本章承接 03 章的故障矩阵和 05 章的 ADR，产出第 10 阶段（企业级实战项目交付）的第六类证据：**Runbook 与无责复盘**。Runbook 让诊断可执行，复盘让系统持续改进。

完成后你应该能回答：

1. 上游 429 的第一动作是无限扩容吗？
2. 事故修复后为何还要加回归样本？
3. 疑似数据泄露为什么不能只重启服务了事？

## 2. 本章完成标准（通过门槛）

必须同时满足：

- 每份 Runbook 写全：现象、影响、严重级别、前置权限、快速确认、诊断查询、止血、恢复、数据一致性检查、升级联系人、结束条件；
- 命令使用占位符并提示生产风险，不把密钥写进文档；
- 至少覆盖六份：模型 Provider 大面积 429、检索服务异常、Checkpoint 不可用、Java 提交结果未知、费用异常增长、疑似跨租户泄露；
- 无责复盘按八要素模板写，避免"开发不小心"式根因，追问为什么系统允许单点错误变成事故；
- 让没参与开发的人按 Runbook 完成一次演练。

```markdown

```

命令使用占位符（如 `<tenant_id>`）并提示生产风险，不把密钥写进文档。Runbook 的目标读者是"没参与开发的值班人"，每步都要能照着做。

## 4. 项目六份 Runbook

| # | Runbook | 核心止血/恢复 | 数据一致性检查 |
| --- | --- | --- | --- |
| 1 | 模型 Provider 大面积 429 | 限流/降级/停重试风暴，保护核心任务 | 无业务变更，确认无重复提交 |
| 2 | 检索服务异常 | 降级到只读提示，暂停新摄取 | 旧索引只读可用，无脏数据写入 |
| 3 | Checkpoint 不可用 | 会话不可恢复提示，不丢业务事实 | 业务库无变更，Thread 可重建 |
| 4 | Java 提交结果未知 | **查幂等记录，不盲目重试** | 幂等键确认单条工单 |
| 5 | 费用异常增长 | 观察 Usage + 异常增长告警，定位调用来源 | 不设固定金额上限，靠告警止损 |
| 6 | 疑似跨租户泄露 | 隔离 + 保全证据，不重启了事 | 审计日志 + 影响面评估 |

安全事件优先隔离与保全证据；疑似数据泄露不要只重启服务——重启会销毁现场证据。业务写结果未知先查询幂等记录，不能盲目重试，否则违反"同一幂等动作最多一个业务结果"。

## 5. Runbook 示例（Java 提交结果未知）

```markdown
# Runbook：Java 提交结果未知

现象：Agent 调用 Java 提交工单后超时，UI 提示"结果未知"。
影响：用户不确定工单是否已创建，可能重复提交。
严重级别：P1（可能产生重复工单）
前置权限：只读审计权限 + 幂等记录查询权限
快速确认：查幂等键 <idempotency_key> 是否已有提交记录
诊断查询：SELECT status FROM work_order WHERE idempotency_key = '<key>'
止血：冻结该用户的重复提交入口，不盲目重试
恢复：确认单条工单后，向用户返回明确结果
数据一致性检查：断言 idempotency_key 唯一，工单数为 1
升级联系人：业务服务 on-call
结束条件：用户收到明确结果，且无重复工单
```

这条 Runbook 直接把 03 章故障矩阵的"Java 成功后超时"和 01 章幂等不变量连起来了。

## 6. 无责复盘

### 6.1 模板

```text
摘要与影响
时间线（事实）
检测方式与为何未更早发现
根因与促成因素
处置与恢复
哪些防线有效/无效
行动项（负责人、日期、验证）
用户/数据影响与后续沟通
```

### 6.2 原则

避免"开发不小心"式根因；追问**为什么系统允许单点错误变成事故**。例如根因写"忘了加幂等键"是无效复盘，有效写法是"缺少幂等键的 Schema 校验门禁，且 Java 超时未触发查询幂等记录的保护，两层防线都缺失"。

## 8. 常见错误与诊断顺序

### 8.1 上游 429 第一反应无限扩容

错误：一遇限流就加并发。诊断顺序：确认配额与流量 → 限流/降级/停止重试风暴 → 保护核心任务 → 最后才处理容量。重试风暴会放大 429。

### 8.2 写结果未知就盲目重试

错误：超时后直接重发。诊断顺序：先查幂等记录确认是否已落地 → 未落地才重试 → 已落地返回明确结果。盲目重试产生重复工单。

### 8.3 疑似泄露重启了事

错误：重启服务销毁现场。诊断顺序：先隔离 + 保全证据（日志、Trace、内存）→ 评估影响面 → 通知相关方 → 再处置。证据比"恢复可用"更优先。

### 8.4 复盘根因写成"开发不小心"

错误：根因归咎个人。诊断顺序：追问系统为何允许单点错误变成事故 → 找缺失的防线（校验门禁、自动告警、幂等保护）→ 行动项落到系统而非个人。

## 9. 练习题与答案

### 练习 1：上游 429 的第一动作是无限扩容吗？

**答案：**不是。确认配额与流量，限流/降级/停止重试风暴，保护核心任务，再处理容量。

### 练习 2：事故修复后为何还加回归样本？

**答案：**代码修复可能被后续变更破坏，样本和告警能持续验证相同失效模式。

### 练习 3：疑似跨租户泄露，为什么不能只重启服务？

**答案：**重启会销毁现场证据。应先隔离 + 保全证据（日志/Trace/内存），评估影响面，通知相关方，再处置。安全事件里"保全证据"优先于"恢复可用"。

## 10. 工程挑战

1. 给"费用异常增长"Runbook 写清"只观测 Usage + 异常增长告警，不设固定金额上限"的止损逻辑；
2. 为"检索服务异常"补一个数据一致性检查：向量库不可用时如何保证旧索引只读、新摄取暂停；
3. 写一次无责复盘，根因落到"缺失的系统防线"而非个人，并产出 2 个带负责人和日期的行动项；
4. 把六份 Runbook 和 03 章故障矩阵做一次映射，确认每类故障都有对应 Runbook。

参考方向：费用止损靠告警定位调用来源而非金额阈值；检索降级对应 02 章"文档 → 索引"边界的降级方案；Runbook 与故障矩阵映射保证"每类故障都有恢复文档"。

## 11. 面试追问

### 11.1 "你们上线后出问题怎么办？"

回答框架：先给 Runbook——每类告警有现象/诊断/止血/恢复/一致性检查，值班人不用看代码就能操作；再给复盘——无责、追问系统为何允许单点错误变成事故，行动项落到防线而非个人。

### 11.2 "费用异常你怎么控制？"

回答框架：只观测 Usage + 异常增长告警，定位调用来源，不设固定金额上限——固定上限会掩盖真实增长信号。止损靠告警和限流，而非金额阈值。
