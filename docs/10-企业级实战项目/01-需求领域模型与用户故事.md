# 需求、领域模型与用户故事

> 预计 8 小时｜贯穿 24 周，第 23 周收口｜目标：把一句模糊业务诉求拆成可测试、可评测、可审计的需求基线，作为本阶段后 7 章的共同输入。项目：智维 Agent——工业设备维护知识与工单协同平台。

## 1. 本章从哪里开始

第 10 阶段（企业级实战项目交付）不新增核心模块，而是把第 1～9 阶段积攒的交付物整合成一个**可投递、可评审、可运维**的完整项目。整合的第一道工序不是写代码，而是回答一个尖锐的问题：**这个系统到底为谁、解决什么问题、绝不碰什么？**

前面 9 个阶段里，"智维 Agent"的名字反复出现，但需求从未被当成一份正式基线对待——`search_manual`、`get_alarm`、`create_work_order_draft` 三个工具是零散冒出来的，领域对象散落在各章的代码注释里。本章要做的事，是把它们收敛成一份**需求基线**：领域词汇表、状态机、用户故事、验收标准、非功能需求、范围外清单。

完成后你应该能回答：

1. "回答必须 100% 正确"为什么不是一条可验收的需求？如何拆成可测的确定性/概率性门槛？
2. 领域对象的不变量（如"引用必须来自本轮允许证据"）如何翻译成后面 03 章测试、04 章评测的输入？
3. 为什么"系统不做什么"是需求的一部分，而不是可有可无的免责声明？
4. 一条用户故事里的验收条件，凭什么能一路喂给测试用例和评测 Dataset，而不是写完就扔？

## 2. 本章完成标准（通过门槛）

必须同时满足：

- 产出一份一页 RFC，目标、非目标、成功指标、风险明确；
- 领域词汇表覆盖全部核心对象，每个对象有 ID、状态机、所有者、不变量、保留期；
- 用户故事不少于 12 条，覆盖维护工程师、知识管理员、审批人、审计四类角色，以及无答案、冲突、超时、越权、取消、恢复六类异常路径；
- 每条用户故事带可验证验收条件，且验收条件能归类为"确定性测试"或"概率性评测"两类（作为 03/04 章的直接输入）；
- 非功能需求可测、可解释，涉及费用一律"只观测 Usage + 异常增长告警，不设固定金额上限"。

## 3. 业务目标与范围

### 3.1 业务目标

帮助维护人员把"查告警 → 找手册 → 形成有证据的诊断建议 → 创建工单草稿 → 人工批准提交"从分散操作变为**可审计闭环**。系统不自动控制设备、不替代安全规程和有资质人员决策。

### 3.2 非目标（范围外清单）

非目标不是免责声明，而是需求的一部分——它限制责任和攻击面，让权限、评测和用户预期可落地：

| 非目标 | 为什么明确写出 |
| --- | --- |
| 直接控制设备 | 高风险动作必须有资质人员在场，Agent 只建议不执行 |
| 替代持证人员的安全决策 | 责任边界不可让渡给概率系统 |
| 无审批关闭高风险工单 | 写入必须经 Human-in-the-loop |
| 从互联网自动下载未知文档 | 阻断供应链与数据投毒入口 |
| 训练行业基础模型 | 只做受控检索与生成，不做预训练 |

非目标能在面试中证明你的产品判断：**你知道停在哪里**，而不是把所有需求都"接下来再说"。

## 4. 角色与场景

| 角色 | 主要动作 | 关键约束 |
| --- | --- | --- |
| 维护工程师 | 查询授权设备、生成带引用诊断、提交工单草稿审批 | 只能访问有权设备的告警与文档 |
| 值班负责人 | 查看证据和动作摘要，批准/拒绝工单 | 审批是确定性动作，不是模型建议 |
| 知识管理员 | 接入、版本化、下架文档 | 下架后旧引用必须失效或标记过期 |
| 审计/运维 | 查看脱敏 Trace、指标、变更和故障 | 不读取无权业务内容 |
| 系统管理员 | 配置模型和权限 | 不读取无权业务内容 |

场景约束决定后面 02 章的数据所有权矩阵和 03 章的 E2E 场景。例如"值班负责人审批"意味着审批接口必须幂等、可审计、可恢复，而不能是模型随口一句"已批准"。

## 5. 核心领域模型

### 5.1 领域词汇表

统一命名，避免代码里 `WorkOrderDraft` 和 PRD 里"工单草稿"各说各话：

| 对象 | 含义 | 所有者 | 关键不变量 |
| --- | --- | --- | --- |
| `Asset` | 设备 | 业务服务 | 归属唯一 `tenant_id`，状态可查不可被 Agent 改写 |
| `Alarm` | 告警 | 业务服务 | 只读，跨租户不可见 |
| `Document/Chunk` | 手册/证据片段 | 知识服务 | 有版本，下架后不可作为新引用 |
| `Diagnosis` | 诊断建议 | Agent 服务 | 每个事实必须有 `evidence_id` |
| `WorkOrderDraft` | 工单草稿 | Agent 服务 | 幂等键防重复；未审批不可提交 |
| `Approval` | 审批记录 | 业务服务 | 审批人与被审批动作一一对应 |
| `WorkOrder` | 正式工单 | 业务服务 | 提交必须携带有效审批 |
| `AgentThread` | 会话/运行轨迹 | Agent 服务 | 不承载业务事实，可重建 |
| `EvaluationCase` | 评测样本 | 评测集 | 与模型/版本隔离，可复现 |

### 5.2 状态机

每个有生命周期的对象都要写清合法迁移。以 `WorkOrderDraft` 为例：

```text
DRAFT --submit_approval--> PENDING
PENDING --approve--> APPROVED
PENDING --reject--> REJECTED
APPROVED --submit--> SUBMITTED
DRAFT/PENDING --cancel--> CANCELLED
任意态 --timeout--> EXPIRED（不可再审批）
```

`AgentThread` 的终态互斥是 03 章测试的确定性断言来源；`WorkOrderDraft` 的状态迁移是"未审批工具绝不执行"这条红线的落地。

### 5.3 关键不变量

- 引用必须来自本轮允许证据（`evidence_id` 必须在当前版本索引内）；
- 工单提交必须有有效审批；
- 同一幂等动作最多一个业务结果；
- Agent State 不能改写业务事实（业务事实的唯一真相在 Java 业务服务）；
- 跨租户数据不可见（`tenant_id` 来自服务端上下文，不从模型输出取）。

这些不变量是"确定性测试"的直接来源，不能被"模型有随机性"解释掉——这是 04 章评测和 08 章 RC 验收的共同底线。

## 6. 用户故事与验收

### 6.1 故事模板

```text
作为 <角色>，我希望 <动作>，以便 <价值>。
验收：<可验证条件，标注是确定性测试还是概率性评测>
```

### 6.2 示例故事（详细版）

```text
作为维护工程师，我希望针对 EQ-001 的当前告警获得带页码引用的排查步骤，
以便快速定位故障。
验收：
- 只检索有权且有效版本（确定性：scope 检查 + 版本过滤）；
- 每个事实有 evidence_id 引用（确定性：结构校验）；
- 证据不足明确拒答（概率性：拒答率数据集评测）。
```

### 6.3 完整故事清单（12+ 条）

| # | 角色 | 故事 | 验收类别 |
| --- | --- | --- | --- |
| 1 | 维护工程师 | 带引用诊断（如上） | 确定性 + 概率性 |
| 2 | 维护工程师 | 无权设备告警返回明确拒答 | 确定性（越权 0 容忍） |
| 3 | 维护工程师 | 证据冲突时提示而非编造 | 概率性（忠实度评测） |
| 4 | 维护工程师 | 无答案时明确"不知道"而非硬编 | 概率性（拒答率评测） |
| 5 | 维护工程师 | 生成工单草稿并提交审批 | 确定性（状态机 + 幂等） |
| 6 | 维护工程师 | 审批前取消草稿 | 确定性（状态迁移） |
| 7 | 维护工程师 | 断线后恢复会话继续 | 确定性（Checkpoint 恢复） |
| 8 | 值班负责人 | 查看证据与动作摘要后批准/拒绝 | 确定性（审批接口幂等） |
| 9 | 值班负责人 | 重复提交同一审批不产生重复工单 | 确定性（幂等键） |
| 10 | 知识管理员 | 接入/版本化/下架文档 | 确定性（索引版本切换） |
| 11 | 知识管理员 | 下架文档不再作为新引用 | 确定性（版本过滤） |
| 12 | 审计/运维 | 通过 request_id 定位到阶段 | 确定性（Trace 关联） |
| 13 | 系统管理员 | 配置模型路由不泄露内部 Prompt | 确定性（安全拒答不泄内部信息） |
| 14 | 值班负责人 | 审批超时后草稿过期 | 确定性（超时终态） |

每条故事的验收条件就是 03 章测试用例和 04 章评测 Dataset 的输入，不能写完就扔。

## 7. 验收标准：确定性与概率性之分

Agent 系统需求必须同时包含两类验收，混在一起就无法管理：

| 类别 | 例子 | 落到哪一章 |
| --- | --- | --- |
| 确定性 | 越权 0 容忍、幂等、状态机合法、未审批不执行 | 03 章 E2E/单元测试 |
| 概率性 | 引用忠实度、拒答率、Tool 选择、任务成功 | 04 章评测报告 |

确定性失败不能用"模型有随机性"解释；概率性指标必须定义 Dataset、评分者、阈值、置信与人工抽样。这个二分法在第 9 章 §4 会被再次强调，本章先把需求落到位。

## 8. 非功能需求

定义 P95、可用性、RPO/RTO、单任务成本、最大步骤、数据保留和安全门禁。作品集可用较宽松数值，但必须可测、可解释：

| 维度 | 建议目标 | 可测方式 |
| --- | --- | --- |
| 交互 P95 | 满足约定（如 ≤8s） | 03 章性能报告分桶统计 |
| API 可用性 | 月度 99.5% 目标 | 监控 + 告警 |
| RPO/RTO | 演示环境可重建 | 备份/恢复演练 |
| 单任务成本 | 出报告，观测 Usage + 异常增长告警，不设固定金额上限 | 04 章费用观测 |
| 最大步骤 | 模型调用/工具调用/Deadline 有上限 | 03 章执行边界测试 |
| 数据保留 | 敏感数据定时清理 | 审计脚本 |
| 安全门禁 | 跨租户/无审批写入/重复工单均为 0 | 03 章红队 + 08 章 RC |

## 9. 项目任务

1. 写一份一页 RFC（按第 9 章 §3 模板），目标/非目标/风险明确；
2. 产出领域词汇表，每个对象填齐 ID、状态机、所有者、不变量、保留期；
3. 在示例故事基础上补齐到 12+ 条，覆盖四类角色和六类异常路径；
4. 为每条故事标注"确定性测试"或"概率性评测"类别，作为 03/04 章输入清单；
5. 写非功能需求表，费用项严格按"只观测 Usage + 异常增长告警"口径。

## 10. 常见错误与诊断顺序

### 10.1 把"正确"当验收标准

"回答必须 100% 正确"不可测。诊断顺序：先拆成数据集上的正确性/忠实度阈值 → 引用合法 100% → 无答案拒答 → 风险场景人工确认 → 残余风险说明。拆不出这几项的，说明需求还没想清。

### 10.2 只写 Happy Path 故事

12 条故事里 8 条是"正常查询、正常建单"，等于没写。诊断顺序：检查是否覆盖无答案、冲突、超时、越权、取消、恢复六类异常；缺一类补一条，否则 03 章的故障矩阵会跟着漏。

### 10.3 非目标写成空话

"系统不控制设备"如果不落到权限和接口上，就是免责声明而非需求。诊断顺序：每条非目标追问"它取消了哪个接口/工具/数据流"，写不出取消对象的就是空话。

### 10.4 验收条件与代码脱节

故事写"每个事实有引用"，代码里却整段塞手册。诊断顺序：把每条验收条件映射到具体的字段、工具、测试或评测指标，映射不上的就是未落地。

## 11. 练习题与答案

### 练习 1：需求"回答必须 100% 正确"如何改写？

**答案：**拆为数据集上的正确性/忠实度阈值、引用合法 100%、无答案拒答、风险场景人工确认和残余风险说明。概率性正确必须用 Dataset + 阈值表达，不能用绝对承诺。

### 练习 2：为何明确"系统不做什么"？

**答案：**限制责任和攻击面，让权限、评测和用户预期可落地，是企业需求的一部分。它能阻止需求蔓延，也是面试中的产品判断证据。

### 练习 3：一条用户故事怎么同时喂给测试和评测？

**答案：**把验收条件拆成两类——确定性的（越权、幂等、状态机）进 03 章测试，概率性的（引用忠实、拒答、任务成功）进 04 章评测 Dataset；每类标注可测方式，而不是笼统一句"功能正常"。

## 12. 工程挑战

1. 给 `WorkOrderDraft` 画完整状态机，标出所有非法迁移，并说明哪个迁移对应"未审批绝不执行"红线；
2. 为"证据冲突"写一条用户故事，明确冲突时 Agent 应提示而非编造，并给出评测它的数据集设计；
3. 把"跨租户数据不可见"拆成三条可测断言：读越权、伪造 `tenant_id` 注入、下架文档残留；
4. 写一份"范围外清单"并逐条标注它取消了哪个接口/工具/数据流，写不出取消对象的条目删掉重写。

参考方向：状态机非法迁移包括 `DRAFT` 直接到 `SUBMITTED`（绕过审批）、`EXPIRED` 再 `APPROVE` 等；冲突评测用"两处手册说法不一致"的输入，期望 Agent 明确提示差异并停止给出单一结论。

## 13. 面试追问

### 13.1 "你的需求文档和别人的 PRD 有什么区别？"

回答框架：我的需求每条都落到"确定性测试 or 概率性评测"两类验收，且和领域不变量一一对应。举例：越权 0 容忍是确定性断言，引用忠实度是概率性阈值，两者都不会用"模型有随机性"来解释失败。

### 13.2 "为什么把非目标写进需求？"

回答框架：非目标限制责任和攻击面，让权限、评测和用户预期可落地。直接控制设备、替代持证人员、无审批关闭高风险工单这三条一旦不写，验收边界就会漂移。
