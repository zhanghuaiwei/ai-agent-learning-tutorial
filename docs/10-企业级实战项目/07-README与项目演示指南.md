# README 与项目演示指南

> 预计 6 小时｜目标：让招聘方十分钟内理解价值、深度、运行方式和证据。

## 1. 本章从哪里开始

前六章产出了需求、架构、测试、评测、ADR、Runbook 六类证据，但它们散落在不同文档里。招聘方只有十分钟，不会先读你的评测报告再决定要不要往下看。本章承接前六章，产出第 10 阶段（企业级实战项目交付）的第七类证据：**一份 README 和一场八分钟演示**，把价值、深度、运行方式、证据压缩成可快速理解的形式。

README 是项目的门面，演示是面试的临门一脚。两者都要回答：这个项目解决什么问题、怎么跑、证据在哪、边界在哪。

完成后你应该能回答：

1. 演示应从代码目录开始，还是从业务问题开始？
2. 为何要主动展示限制，而不是等被追问才承认？
3. 为什么 Fake 模式优先，不依赖面试现场的网络和余额？

## 2. 本章完成标准（通过门槛）

必须同时满足：

- README 按九段顺序组织，一句话业务价值与边界在前，技术栈徽章不堆在业务问题前；
- 90 秒演示物料（GIF/视频/截图）覆盖引用、审批、恢复、Trace；
- 快速开始用 Fake 模式优先，不需要 Key/Docker；
- 真实模型配置说明含 Usage 与费用观测口径（仅观测 + 异常增长告警，不设固定金额上限）；
- 测试/评测结果链接完整报告，所有数字可追溯到可复现报告；
- 演示脚本含离线 Fake 备份，预置数据合法可公开。

## 3. README 九段顺序

| # | 段落 | 要点 |
| --- | --- | --- |
| 1 | 一句话业务价值与明确边界 | 先问题后技术，写清"不做什么" |
| 2 | 90 秒演示物料 | GIF/视频/截图：引用、审批、恢复、Trace |
| 3 | 架构图与数据所有权 | 用 02 章 C4 图，标注权威源 |
| 4 | 核心能力 | RAG、LangGraph、评测、安全、成本 |
| 5 | 快速开始 | Fake 模式优先，无 Key/Docker |
| 6 | 真实模型配置 | Usage 与费用观测说明 |
| 7 | 测试/评测结果 | 链接完整报告 |
| 8 | 关键 ADR、Runbook、威胁模型 | 链接 05/06/02 章产物 |
| 9 | 已知限制与路线图 | 主动展示边界 |

不要把技术栈徽章堆在业务问题前；不写无法证明的"企业级、高可用、零幻觉"——这类词没有报告支撑就是空话。

## 4. 演示脚本（八分钟）

| 环节 | 时长 | 内容 |
| --- | --- | --- |
| 问题与边界 | 45s | 设备故障协同、非目标（不控制设备） |
| 正常带引用诊断 | 90s | 查告警 → 带页码引用 → 诊断建议 |
| 审批暂停/重启恢复 | 120s | 草稿 → 暂停 → 恢复 → 审批 |
| 注入或越权拦截 | 60s | 跨租户读取被拒，安全拒答 |
| 成功后超时无重复工单 | 90s | 幂等键，不盲目重试 |
| 评测/成本/架构取舍 | 75s | 评测报告、费用观测、ADR 取舍 |

准备离线 Fake 演示，避免面试现场网络和余额失败；真实模型视频作为补充。预置数据必须合法可公开。

## 5. 演示物料规范

| 物料 | 要求 |
| --- | --- |
| 90 秒 GIF/视频 | 覆盖引用、审批、恢复、Trace 四个关键瞬间 |
| 架构图 | 用 02 章 C4 图，能白板复述 |
| 截图 | 评测报告首页、故障矩阵、Runbook 索引 |
| 真实模型视频 | 补充，不替代 Fake 演示 |

所有数字链接到可复现报告（04 章评测、03 章性能），不能出现"性能提升 3 倍"这种无来源数字。

## 6. 项目任务

1. 按九段顺序写 README，一句话业务价值与边界开头，徽章放后面；
2. 制作 90 秒演示物料，覆盖引用、审批、恢复、Trace 四个瞬间；
3. 快速开始用 Fake 模式，验证"同事只按 README 即可运行"；
4. 写八分钟演示脚本，含离线 Fake 备份和真实模型视频补充；
5. 把所有数字链接到 03/04 章报告，删除任何无法追溯的夸大数据。

## 7. 常见错误与诊断顺序

### 7.1 从代码目录开始演示

错误：开场就讲目录结构和依赖。诊断顺序：先从业务问题和用户结果开始 → 再钻架构、Trace 和关键代码。招聘方先建立上下文，才听得进技术细节。

### 7.2 隐藏限制等被追问才承认

错误：把已知限制藏着。诊断顺序：主动展示限制（只读范围、非目标、残余风险），体现边界意识和可信度，也能引导讨论下一步设计。

### 7.3 演示依赖现场网络和余额

错误：真实模型演示现场断网或余额不足。诊断顺序：Fake 模式优先，真实模型只做视频补充；预置数据合法可公开。

### 7.4 堆技术栈徽章和"零幻觉"口号

错误：README 开头全是徽章和"企业级、高可用、零幻觉"。诊断顺序：删掉无法证明的形容词，换成可追溯的报告链接和真实数字。

## 8. 练习题与答案

### 练习 1：演示应从代码目录开始吗？

**答案：**先从业务问题和用户结果开始，再钻到架构、Trace 和关键代码，招聘方更容易建立上下文。

### 练习 2：为何主动展示限制？

**答案：**体现边界意识和可信度，也能引导讨论下一步设计，而非被追问时才承认。

### 练习 3：README 里的数字为什么必须链接报告？

**答案：**"性能提升 3 倍"这类无来源数字会被面试官一眼识破。数字链接到可复现报告（评测/性能），既可信又能继续追问。

## 9. 工程挑战

1. 把 README 压缩到招聘方十分钟能读完，删掉所有无法证明的形容词；
2. 录一段 90 秒 Fake 演示，覆盖"引用 + 审批 + 恢复 + Trace"四个瞬间，不加字幕也能看懂；
3. 写八分钟演示脚本并录一次，掐表核对每个环节不超时；
4. 让一位没接触过项目的人按 README 在 Fake 模式跑通，记录卡点并回改 README。

参考方向：Fake 演示对应 03 章 Fake Model 用法；"引用 + 审批 + 恢复 + Trace"对应 01 章主链路故事和 03 章 E2E 场景。

## 10. 面试追问

### 10.1 "你这项目最值得看的部分是什么？"

回答框架：先给业务闭环——故障协同从分散操作变成可审计闭环，再给三个证据锚点：评测报告（概率性证据）、故障矩阵（确定性证据）、ADR（架构取舍）。而不是报技术栈清单。

### 10.2 "为什么你的 README 不放技术徽章？"

回答框架：徽章是次要信号，业务问题、边界、可复现证据才决定读者要不要继续。我把徽章放在能力段之后，前面留给"解决什么问题、不做什么"。

## 12. 官方资料与中文阅读指引

- [GitHub 写作指南](https://docs.github.com/get-started/writing-on-github)：重点看标题层级、表格与链接写法，用于 §3 的 README 结构；
- [Make a README](https://www.makeareadme.com/)：重点看 README 的要素顺序，用于 §3 的九段顺序；
- [Awesome README](https://github.com/matiassingers/awesome-readme)：重点看优秀项目的 README 范例，用于 §3 的表达取舍。

重点阅读：Make a README 强调"What/Why/How"顺序（先说是什么、为什么，再说怎么跑），对应 §8.1"从业务问题开始"。中文可先读 Make a README 的中文社区翻译，再对照 GitHub 官方写作指南确认 Markdown 细节。
