# Release Candidate 最终验收

> 预计 6 小时｜第 23 周收口｜目标：冻结作品集候选版本，最后一周只做面试演练和高优先缺陷。

## 1. 本章从哪里开始

前七章分别产出了需求基线、架构、测试、评测、ADR、Runbook、README。但一堆产物不等于一个可投递版本——散落的交付物可能互相矛盾，比如评测报告里说"引用忠实度达标"，而 03 章的测试还停在旧版本。本章承接前七章，做第 10 阶段（企业级实战项目交付）的收口：**汇总全部产物，执行 Release Candidate 门禁，冻结范围，形成可投递版本**，最后收口到第 9 章交付评审。

RC 验收的核心不是"再做一个功能"，而是回答一个闸门问题：**现在能不能停止加功能，把当前状态冻结成可投递的版本？**

完成后你应该能回答：

1. RC 前发现低频严重越权问题，按时冻结还是延期？
2. 还有很多想做的功能怎么办？
3. 为什么"签字清单"不能是全勾空表，必须带证据链接？

## 2. 本章完成标准（通过门槛）

必须同时满足：

- 功能、质量、工程三门禁全部有真实证据链接，不是全勾空表；
- 越权、无审批写入、重复工单三个安全指标均为 0；
- 六类故障注入都有安全终态（来自 03 章）；
- P95、每成功任务成本、费用异常增长告警可证明，费用无固定金额上限（仅观测 + 告警）；
- 数据库迁移可重建，跨租户、错误 Scope、篡改 Thread 测试为 0 成功；
- OpenTelemetry Trace 可跨 Python Agent、Java Tool 和数据库关联；
- 签字清单每项填"通过/例外/证据链接/负责人"，例外必须写风险、临时控制和截止日期；
- 明确"停止加功能"的决定，剩余想法进入路线图。

## 8. 停止加功能：范围冻结闸门

RC 的核心决定是**停止加功能**。判断标准：

```text
满足以下条件即可冻结：
- 三门禁无 P0 缺陷（安全三零达标）
- 评测/性能报告可复现且达标
- 备份/恢复/回滚演练完成
- 签字清单无"无证据的通过"

冻结后的规则：
- 剩余想法全部进入路线图，不本轮实现
- 最后一周只做：面试演练 + 高优先缺陷修复 + 文档补漏
```

这个闸门直接收口到第 9 章——第 9 章的 30 分钟交付评审，用的就是这份冻结后的 RC 版本和签字清单。

## 9. 项目任务

1. 汇总前七章产物到一张 RC 证据清单，每项链接对应文档/报告；
2. 执行功能/质量/工程三门禁，逐项填"通过/例外/证据链接"；
3. 重点验证安全三零（跨租户、无审批写入、重复工单均为 0）和六类故障安全终态；
4. 写签字清单，例外项必须含风险、临时控制、截止日期；
5. 明确"停止加功能"决定，剩余想法整理进路线图，收口到第 9 章评审。

## 10. 常见错误与诊断顺序

### 10.1 签字清单全是空勾

错误：每项都"通过"但无证据链接。诊断顺序：每项强制填证据链接 → 无链接的一律降级为"例外"并写风险 → 用真实报告替代主观判断。

### 10.2 低频严重越权也放行

错误：低频就当可接受。诊断顺序：安全硬门禁失败必须修复或禁用相关能力，不能用低频作为接受理由——越权是 0 容忍红线，与频率无关。

### 10.3 想做的功能停不下来

错误：RC 前还不断加功能。诊断顺序：进入路线图，冻结范围；优先修关键缺陷、文档和演练，业务闭环与稳定性高于功能数量。

### 10.4 简历数字夸大

错误：把"演示规模"写成"线上规模"。诊断顺序：简历每个数字都能追溯到报告 → 删掉无法追溯的夸大 → 明说"Fake 压测规模"与"真实模型小规模实测"分开。

## 11. 练习题与答案

### 练习 1：RC 前发现低频严重越权问题，按时冻结还是延期？

**答案：**安全硬门禁失败必须修复或禁用相关能力，不能用低频作为接受理由。越权是 0 容忍红线。

### 练习 2：还有很多想做的功能怎么办？

**答案：**进入路线图，冻结范围；优先修关键缺陷、文档和演练，业务闭环与稳定性高于功能数量。

### 练习 3：签字清单为什么不能全勾空表？

**答案：**空勾没有证据支撑，验收变主观。每项必须链接真实报告；无证据的降级为"例外"并写风险、临时控制、截止日期。

## 12. 工程挑战

1. 把前七章产物汇总成一张 RC 证据清单，标出哪项证据缺失或过期；
2. 跑一次"三零"验证脚本，断言跨租户、无审批写入、重复工单均为 0，任何一项非 0 自动失败；
3. 为某指标差 1% 的例外写全"风险/临时控制/截止日期"三要素；
4. 写一份"停止加功能"的范围冻结说明，把剩余想法归入路线图并收口第 9 章。

参考方向：三零验证脚本对应 03 章红队与并发幂等测试；例外三要素对应 09 章"例外必须写风险、临时控制和截止日期"；范围冻结对应第 9 章"停止加功能，形成可投递版本"。

## 13. 面试追问

### 13.1 "你的项目算完成了吗？"

回答框架：用 RC 签字清单回答——三门禁通过、安全三零达标、签字清单有证据链接，剩下的是路线图而非未完成。完成的定义是"可投递、可评审、可运维"，不是"功能加满"。

### 13.2 "你凭什么说质量达标了？"

回答框架：给证据链——评测报告（概率性）、故障矩阵（确定性）、安全三零脚本（红线）、性能报告（P95/成本）。每个数字都能追溯到可复现报告，不是主观"我觉得挺好"。

## 15. 官方资料与中文阅读指引

- [Google SRE Production Readiness Review](https://sre.google/workbook/production-readiness/)：重点看 PRR 的门禁与签字流程，用于 §3～7 的门禁设计；
- [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)：重点看安全验证级别与检查项，用于 §5 的工程门禁与 §4 的安全三零；
- [Google SRE Workbook：Deployment](https://sre.google/workbook/deployment/)：重点看灰度、回滚与发布门禁，用于 §8 的冻结闸门。

重点阅读：Production Readiness Review 强调"Readiness 是持续评估而非一次性检查"，对应 §7 签字清单的"例外带截止日期"；ASVS 的验证项对应安全三零的具体检查。中文可先读 ASVS 的中文对照版，再对照 Google PRR 英文原文确认门禁流程。
