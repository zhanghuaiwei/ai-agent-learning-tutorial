# ADR 架构决策记录指南

> 预计 6 小时｜目标：把"为什么这样设计"变成可审查的项目资产。

## 1. 本章从哪里开始

02 章画出了架构图，并标出了 8 个决策点（Python Agent + Java 业务服务、RAG 选型、模型路由等）。但架构图只说"是什么"，不说"为什么"。当面试官问"你为什么不用全 Python"或"为什么选 LangGraph 而不是继续手写循环"，如果只能回答"因为大家都这么做"，架构就不可审查。

本章承接 02 章的决策点，产出第 10 阶段（企业级实战项目交付）的第五类证据：**至少 8 份 ADR**，每份记录当时的上下文、候选方案、取舍和后果。ADR 承接第 4 阶段第 6 章的选型 ADR 骨架，把分散的选型记录收敛成统一资产。

完成后你应该能回答：

1. ADR 为什么不能只写最终方案的优点？
2. 什么情况下要复审模型选型 ADR？
3. ADR 被数据推翻时，是改旧记录还是新建替代？

## 2. 本章完成标准（通过门槛）

必须同时满足：

- 至少 8 份 ADR，每份有证据或明确待验证项；
- 每份含：状态、日期与负责人、背景与约束、决策驱动因素、候选方案、决定、正面/负面后果、验证证据、回滚或复审条件；
- 至少一份 ADR 记录了"被替代"状态，演示 ADR 的历史演进而非只保留最新；
- 每份 ADR 能对应 02 章架构图里的一个决策点，形成"图 → 决策 → 记录"的闭环。

## 3. ADR 模板

```markdown

状态：提议/接受/废弃/替代
日期与负责人：
背景与约束：
决策驱动因素：
候选方案：
决定：
正面/负面后果：
验证证据：
```

ADR 记录当时上下文，不要求"永远正确"。被数据推翻时新建 ADR 替代旧记录，保留历史——ADR 的价值正在于历史演进可追溯。

## 5. ADR 示例（详细版）

```markdown
# ADR-001：Python Agent + Java 业务服务

状态：接受
日期与负责人：2026-08，学习者本人
背景与约束：设备/工单事实已有 Java 系统；Agent 需要概率生成但必须守住业务事务。
决策驱动因素：业务真相唯一权威源、事务与幂等、安全边界、团队双栈能力。
候选方案：
  A. 全 Python 直接读写业务库 —— 简单但破坏业务真相唯一权威源
  B. Python Agent + Java 受控 API —— 概率层与确定性事务层分离
  C. 全 Java 集成 LLM —— 生成生态弱，开发慢
决定：选 B。Python 负责 Agent/RAG/生成，Java 负责设备/工单/审批/幂等。
正面/负面后果：
  + 业务真相唯一权威源，Agent 故障不污染业务
  + 越权/幂等由确定性代码保证
  - 跨语言链路更长，Trace 需跨 Python/Java 关联
验证证据：03 章 E2E 的幂等/越权用例、OpenTelemetry 跨服务 Trace。
回滚或复审条件：若团队只剩单一栈能力，或 Java 服务不可维护，复审此 ADR。
```

## 6. ADR 生命周期与复审

| 阶段 | 动作 |
| --- | --- |
| 提议 | 写"背景/候选/决定"，状态=提议 |
| 接受 | 评审通过，状态=接受，补验证证据 |
| 复审 | 触发条件满足时（见下），重新评估 |
| 替代 | 新建 ADR 替代旧记录，旧状态改"替代"并指向新 ADR |
| 废弃 | 决策不再适用，状态=废弃，写废弃原因 |

复审条件（以模型选型 ADR 为例）：价格/版本变化、质量或延迟 SLO 失守、新任务分布、供应商风险或数据合规要求改变时。ADR 不是一锤定音，而是持续演进的资产。

## 7. 项目任务

## 8. 常见错误与诊断顺序

### 8.1 只写最终方案优点

错误：候选方案栏只有被选的那个。诊断顺序：强制写候选、代价和负面后果 → 每个候选写"为何不选" → 没有代价的决策无法审查取舍。

### 8.2 把 ADR 当"一次性结论"

错误：写完就再也不看。诊断顺序：为每份 ADR 写复审条件 → 触发条件满足时新建替代而非改旧记录 → 保留历史演进。

### 8.3 验证证据栏写"待验证"却永不验证

错误：8 份 ADR 全是"待验证项"。诊断顺序：接受状态的 ADR 必须有真实证据（测试指标、评测报告），只有真正未决的才写"待验证"并标注复审日期。

### 8.4 ADR 与架构图脱节

错误：ADR 和 02 章的决策点对不上。诊断顺序：每条 ADR 标注对应 02 章 §7 的哪个决策点，形成"图 → 决策 → 记录"闭环。

## 9. 练习题与答案

### 练习 1：ADR 能否只写最终方案优点？

**答案：**不能。必须写候选、代价和负面后果，否则无法审查取舍。

### 练习 2：什么情况下复审模型选型 ADR？

**答案：**价格/版本变化、质量或延迟 SLO 失守、新任务分布、供应商风险或数据合规要求改变时。

### 练习 3：ADR 被新数据推翻时，改旧记录还是新建？

**答案：**新建 ADR 替代旧记录，旧记录状态改"替代"并指向新 ADR，保留历史。ADR 的价值正是历史演进可追溯，改旧记录会抹掉当时的上下文。

## 11. 面试追问

### 11.1 "你为什么选 LangGraph，而不是继续用 create_agent？"

回答框架：先用 ADR 说清升级边界——单 Agent 够用时不强上 Graph，只有当工单状态机、暂停/恢复、审批链路超出单循环能力时才升级。给出升级判据和对应证据，而不是"因为流行"。

### 11.2 "你的架构决策为什么值得审查？"

回答框架：每份 ADR 有候选方案和负面后果，接受状态的都有测试/评测证据支撑，被替代的保留历史。这证明架构是权衡出来的，不是拍脑袋。

重点阅读：Michael Nygard 原文强调 ADR 的价值在"上下文与后果"而非"结论本身"，这是避免"只写优点"的理论基础。中文可先读 ADR GitHub 的中文说明页，再对照 AWS ADR 流程的英文原文确认状态机。
